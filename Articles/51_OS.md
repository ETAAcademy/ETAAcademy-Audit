# Security Operations: Connecting Evidence, Protection, and Response

A phishing message, an encoded PowerShell command, a risky sign-in, and a burst of cloud downloads can appear in different systems. The central problem for a security operations center (SOC) is deciding whether those observations describe one attack, how far it has spread, and which actions will contain it.

Security portfolio addresses that problem through complementary capabilities. Defender XDR (extended detection and response) connects evidence from endpoints, email, identities, and cloud applications. Security Copilot helps analysts interpret that evidence. Purview adds data protection and investigation capabilities. Defender for Endpoint and Defender for Cloud connect prevention with device and workload security, while Sentinel brings broader telemetry into detection and hunting. Kusto Query Language (KQL) supplies a common analytical language across many of these environments.

Their value depends on the connections between evidence, permissions, and action. A correlated alert is an investigation lead; a configured policy needs effective scope; and an automated response needs a verified outcome. Understanding those distinctions makes the products useful as a security system and helps analysts produce conclusions that another investigator can assess.

## Defender XDR and the shared incident

### Describe the attack across security domains

An attacker can enter through email, execute code on a workstation, steal credentials, traverse identity infrastructure, and reach cloud data. Defending each domain independently can leave the relationships between those activities unexplored. Defender XDR provides shared investigation context so analysts can follow the affected users, devices, messages, and indicators across product boundaries.

Attack models help explain those relationships. The Cyber Kill Chain describes reconnaissance, weaponization, delivery, exploitation, installation, command and control, and actions on objectives. Its sequence helps identify opportunities to interrupt an attack, although real incidents can branch, loop, and continue extensively after initial compromise.

MITRE ATT&CK provides a more detailed vocabulary for adversary behavior. A tactic describes an objective, while a technique describes how the attacker pursues it. PowerShell execution, password spraying, and account manipulation therefore become distinct hypotheses with different evidence requirements. PETE—Prepare, Enter, Traverse, Execute Objectives—offers a simpler account for business discussions. Its emphasis on traversal makes clear why stopping initial access alone cannot address the damage caused by compromised privileges and trust relationships.

These models support a practical question: what could an attacker reach if the first defensive layer failed? The answer directs attention toward execution monitoring, credential protection, lateral movement, and sensitive data access. Coverage should reflect the attack behaviors that matter to the organization rather than the number of enabled products.

### Understand what each protection domain contributes

Defender for Office 365 contributes evidence about suspicious messages, attachments, links, and collaboration activity. Defender for Endpoint supplies device behavior and containment capabilities. Defender for Identity observes activity around supported on-premises identity infrastructure. Microsoft Entra ID Protection and Conditional Access provide cloud identity risk and access controls. Defender for Cloud Apps adds SaaS discovery, activity monitoring, and supported session controls.

Defender for Cloud and Defender for IoT extend visibility into supported workloads and industrial environments. Sentinel adds other data sources, custom analytics, and broader investigation needs. Purview supplies information about sensitive content and its handling. Their contributions overlap at an incident while retaining separate deployment requirements, permissions, and evidence semantics.

Consider a malicious attachment opened through personal webmail on a corporate device. The message can sit outside the organization's email protection boundary while its execution still produces endpoint evidence. That device evidence can support investigation of the user's account and enterprise application activity. With appropriate integrations, responders can isolate a device, restrict access, inspect mailboxes, or act on related infrastructure.

The available response depends on the relevant service, configuration, permissions, and observed activity. One detection does not guarantee every downstream control has acted. Threat intelligence can add context about files, domains, infrastructure, and adversary behavior; deception can reveal unexpected exploration through decoy assets. Analysts still need to determine what those signals establish about the particular incident.

### Distinguish alerts, incidents, and response outcomes

An alert identifies potentially malicious activity. An incident groups related alerts and evidence into a broader attack account. The shared incident helps analysts assess the apparent entry point, affected entities, timeline, and contributing detections without treating each alert as an isolated problem.

Correlation establishes a starting hypothesis. The incident's relationships need support from timestamps, process activity, authentication records, and other underlying evidence. An incident graph can suggest that events belong together, but the analyst must distinguish observed connections from inferred ones and investigate possible alternative explanations.

Automated Investigation and Response (AIR) can examine evidence, expand an investigation as related entities appear, and propose or execute supported remediation. Product configuration and automation settings determine whether an action occurs automatically or waits for approval. The Action Center makes that status visible. A pending quarantine and a completed quarantine imply different levels of remaining exposure.

Automatic attack disruption offers rapid containment in supported, high-confidence attack scenarios, including ransomware and business email compromise. A disruption indicator records protective action; the team still needs to investigate compromised credentials, persistence, remaining access, and affected data. Containment can interrupt an attack before its full scope is known.

People need equally clear responsibilities. Tier 1 commonly handles monitoring, initial classification, and authorized containment; Tier 2 performs deeper investigation and hunting; Tier 3 contributes specialist analysis, detection engineering, and architecture. Smaller teams can combine these roles while preserving clear escalation ownership. Repeated evidence collection and established response actions suit automation, while ambiguous findings and actions affecting critical services require informed judgment.

### Protect email before and after delivery

Exchange Online Protection evaluates connection reputation, spam, malware, and other message signals. Defender for Office 365 adds capabilities such as Safe Attachments, Safe Links, anti-phishing, and impersonation protection. Safe Attachments analyzes suspicious files in isolation, while Safe Links provides URL protection, including checks when supported links are opened.

Protection continues after delivery. A linked destination can change, campaign evidence can emerge, or a previously unknown file can receive a malicious verdict. Zero-hour Auto Purge can remediate messages subsequently identified as threats, subject to the relevant policies and supported workloads.

Threat Explorer and Real-time detections provide investigation views according to the available plan. Recipient information, delivery results, message identifiers, URLs, attachments, post-delivery actions, and click events help establish campaign scope. Historical delivery does not establish current inbox exposure, user interaction, or credential theft. Those conclusions require their own evidence.

Attack simulation training helps assess phishing susceptibility and reporting behavior, but simulation results depend on the exercise settings. They do not establish that production filtering would block an equivalent attack. Impersonation protection likewise needs deliberate selection of protected users and domains, especially executives, sensitive roles, and legitimate partners whom attackers might imitate.

Standard and Strict preset security policies provide protection baselines. Organizations can apply Standard broadly and Strict to selected high-value populations, while checking both the Exchange Online Protection and Defender for Office 365 recipient scopes. A mismatch can leave the intended users with different protection across those layers.

Policy precedence also matters. Strict takes precedence over Standard, and presets take precedence over applicable custom policies. Processing follows the defined order rather than combining the strongest setting from every matching policy. Built-in protection can supply Safe Links and Safe Attachments outside Standard and Strict assignments. More aggressive filtering also increases the importance of clear quarantine review and false-positive handling.

### Follow identities through hybrid environments

Identity often connects an initial compromise with wider access. Defender for Identity observes authentication and directory activity through sensors on supported infrastructure, including relevant domain controllers, Active Directory Federation Services, and Active Directory Certificate Services deployments. Kerberos and NTLM activity can reveal abuse involving tickets, hashes, and trust relationships.

Sensor coverage must match the actual identity estate. Unhealthy sensors, missing event collection, and overlooked services leave gaps that can resemble an absence of suspicious activity. Attack-path analysis adds a different perspective by showing how existing relationships could lead to privileged targets. A possible path indicates exposure; authentication, directory, and endpoint records are needed to establish actual traversal.

Cloud identity introduces two distinct risk measures. Sign-in risk concerns the likelihood that a particular authentication attempt is unauthorized. User risk concerns the likelihood that an account is compromised. Suspicious infrastructure, unfamiliar sign-in properties, leaked credentials, password spraying, and token anomalies can contribute signals. Some arise during authentication, while others appear through later analysis.

Detection becomes protection through configured access policies. Risk-based Conditional Access can require additional authentication, supported password remediation, or blocking. Self-remediation needs prerequisites such as authentication registration and an appropriate password-reset configuration. Confirmed compromise may require credential reset, session revocation, and investigation of associated activity.

Multi-factor authentication reduces important credential risks, while stolen sessions and adversary-in-the-middle phishing require additional attention. A successful sign-in records an authentication outcome without establishing that the person behind it was legitimate. Hybrid investigations need to follow the identity through both on-premises and cloud systems where relevant.

### Interpret cloud application activity in context

Defender for Cloud Apps addresses approved applications used unsafely as well as services adopted without formal oversight. Cloud Discovery can use endpoint integration or supported firewall and proxy logs to identify application use. App connectors provide activity and content visibility for supported services. Observing a connection to an application does not reveal every action or uploaded file within it.

Application risk assessments support decisions about sanctioned services, including generative AI applications, alongside the organization's data, access, and contractual requirements. Conditional Access App Control can restrict supported sessions, for example by allowing viewing while blocking downloads or applying supported protection to downloaded files. Appropriate onboarding and session routing are prerequisites. Supported non-Microsoft identity providers can also be integrated.

Purview labels and policies connect application activity with data sensitivity. Their effect depends on the configured label, application, and control. A mass-download alert, for example, can indicate exfiltration, migration, or legitimate business activity. Identity risk, destination, content sensitivity, timing, and the user's usual behavior help distinguish those possibilities.

### Match hunting questions to the available schema

Advanced hunting lets analysts test questions beyond the alert queue. `DeviceProcessEvents` supports execution analysis; `EmailEvents` describes mail delivery; `UrlClickEvents` contributes click evidence; identity and cloud application tables contribute their own observations. Each source has distinct fields and limitations. Executed processes and initiating processes describe different roles, and historical mail delivery says little about current message location.

Defender's `EntraIdSignInEvents` and Log Analytics' `SigninLogs` use different schemas and timestamp conventions. Older examples using `AADSignInEventsBeta` require migration and schema review. Cross-source queries also require relevant data, permissions, and retention in the same query context.

The Microsoft Graph security API makes hunting available programmatically. Its `runHuntingQuery` endpoint accepts KQL and supports delegated or application access with `ThreatHunting.Read.All`. Production use additionally needs appropriate authentication, credential management, error handling, and request-limit handling.

Measurement should preserve similar distinctions. Mean time to remediate concerns response speed under consistently defined start and end points; attacker dwell time concerns how long activity remains undetected. Faster post-detection action does not establish earlier discovery. Secure Score helps prioritize recommended improvements, while Threat Analytics relates threats and campaigns to organizational exposure. Neither replaces evidence that the intended assets are covered, containment works, and enabling weaknesses have been addressed.

## Security Copilot: Make AI assistance accountable to the evidence

Microsoft Security Copilot brings natural language interaction to security data. It can summarize incidents, explain scripts, draft hunting queries, and organize findings into narratives. These capabilities address a familiar bottleneck: analysts can receive more alerts and supporting records than they can quickly interpret. Assistance is valuable when it reduces the effort needed to assemble evidence while leaving the resulting conclusions open to review.

An assistant's fluency does not establish that an account was compromised, a payload executed, or containment succeeded. Those conclusions require telemetry and action records. Model behavior, retrieval, permissions, compute capacity, and analyst verification therefore belong in the same discussion. A useful implementation connects a clear question to accessible evidence and measures whether the answer helps the team reach a supported decision.

### Ground the question in the investigation

A useful security prompt specifies a **goal, context, expectation, and source**. The goal states the question; context establishes the entities and relevant period; expectation describes the required output; and source identifies the evidence to consult. These details make the result easier to assess because they define what the assistant was supposed to examine.

For example, an analyst could ask: “Identify possible persistence mechanisms associated with Jonathan Wolcott during the investigation of WS-FIN-089. Use the relevant Defender device events and return the command, timestamp, supporting evidence, and proposed ATT&CK mapping.” That request gives the assistant a bounded task. It also gives the reviewer concrete checks: whether the records concern the right identity and device, whether timestamps fit the incident, and whether the proposed technique matches the command's behavior.

Grounding supplies the logs, incident records, runbooks, or intelligence needed to answer. Retrieval-augmented generation retrieves relevant material and places it in the model's context. Filtering the evidence before retrieval can reduce irrelevant content and keep a large investigation manageable. Retrieval quality still depends on source coverage and query scope. An answer based on incomplete records can be coherent while omitting the activity that matters most.

<details><summary>The following example supplies a Windows process event alongside a system instruction and a demonstration:</summary>

```python
import os
from openai import AzureOpenAI

# Initialize enterprise client configured for Azure OpenAI Service
client = AzureOpenAI(
    azure_endpoint=os.getenv("AZURE_OPENAI_ENDPOINT"), # e.g. https://sec-copilot-aoai.openai.azure.com/
    api_key=os.getenv("AZURE_OPENAI_API_KEY"),
    api_version="2026-10-31-preview"
)

# Deployment name corresponding to GPT deployed in Azure AI Foundry
DEPLOYMENT_NAME = "gpt-secops"

# Grounding data: Raw Windows Security Event Log extracted from Microsoft Sentinel
raw_security_log = """
TimeGenerated: 2026-10-31T08:14:22Z
EventID: 5688
Computer: WS-FIN-111.corp.contoso.com
SubjectUserName: jwolcott
NewProcessName: C:\\Windows\\System32\\WindowsPowerShell\\v1.0\\powershell.exe
CommandLine: powershell.exe -nop -w hidden -enc JABjAGwAaQBlAG4AdAAgAD0AIAB...
"""

# Dynamic Prompt Construction leveraging System Message, Few-Shot Demonstrations, and Grounding
response = client.chat.completions.create(
    model=DEPLOYMENT_NAME,
    temperature=0.1,  # Low temperature to suppress hallucination and enforce determinism
    max_tokens=800,
    messages=[
        {
            "role": "system",
            "content": (
                "You are an elite Tier-3 SOC analyst. Analyze security logs strictly against "
                "the provided grounding evidence. Map findings to MITRE ATT&CK techniques. "
                "Format output as a structured JSON object."
            )
        },
        # Few-shot demonstration pair 1
        {
            "role": "user",
            "content": "Log: EventID 4688, CommandLine: cmd.exe /c whoami"
        },
        {
            "role": "assistant",
            "content": '{"assessment": "Suspicious", "technique": "T1033", "technique_name": "System Owner/User Discovery", "risk_score": 40}'
        },
        # Grounded user request
        {
            "role": "user",

        }
    ]

print(response.choices[0].message.content)
```

Direct instructions establish the task, system messages express application-level expectations, and demonstrations can guide formatting or classification. A demonstration that labels `whoami` suspicious may encourage overclassification even though administrators also use that command legitimately. Its significance comes from surrounding behavior.

Model settings do not replace evidence controls. A low temperature reduces sampling variability without guaranteeing factual accuracy or deterministic output. Asking for JSON and providing a JSON example can encourage a format without enforcing its schema. Applications consuming generated output must validate it before relying on its structure or content.

### Model mechanisms and evidential limits

A language model can relate material appearing at different positions in a script or event sequence through attention. Scaled dot-product attention is expressed as:

```math
\text{Attention}(Q, K, V) = \text{softmax}\left(\frac{Q K^T}{\sqrt{d_k}}\right) V
```

Here, $Q$ contains query representations, $K$ contains keys, $V$ contains values, and $d_k$ is the key dimension. Scaling controls the magnitude of the scores passed to softmax. This mechanism helps explain how related portions of a long input can influence the response. It does not establish that the model reconstructs every dependency correctly or that every relevant event fits within its context.

Retrieval addresses a different problem: selecting material to supply as context. Embedding-based retrieval can compare an incident description with intelligence reports or internal runbooks through cosine similarity:

```math
\text{sim}(\vec{u}, \vec{v}) = \cos(\theta) = \frac{\vec{u} \cdot \vec{v}}{\|\vec{u}\|_2 \|\vec{v}\|_2} = \frac{\sum_{i=1}^d u_i v_i}{\sqrt{\sum_{i=1}^d u_i^2} \sqrt{\sum_{i=1}^d v_i^2}}
```

The vectors represent an embedded query and candidate document. A similarity threshold selects related material, but closeness in embedding space cannot establish that a report is authoritative, current, or applicable to this incident. An old runbook can be highly relevant in wording while describing a different configuration. Source selection and evidence checking therefore remain necessary alongside retrieval.

Predictability is also separate from factuality. Perplexity describes the probability a model assigns to a sequence given its context; a familiar false statement can be highly predictable. Neither a smooth explanation nor a model-level measure can replace checks against the actual event records. These mechanisms explain aspects of model behavior without specifying Security Copilot's complete internal implementation.

### Understand retrieval and authority

Security Copilot connects requests to capabilities exposed through plugins. A plugin groups functions associated with a product or service; an orchestrator interprets the request, selects relevant capabilities, and combines their results. Connected products can include Defender XDR, Sentinel, Entra, Intune, and Purview, each contributing different evidence under its own access conditions.

This architecture explains both the value and the limits of assistance. Retrieving incident details alongside device and identity context can save repeated navigation. A missing integration, inaccessible workspace, failed query, or unavailable record can leave gaps in the answer. A natural language request does not create access to those records. Analysts should distinguish evidence that was unavailable from evidence that was searched and produced no match.

The standalone experience provides a dedicated investigation context, while embedded experiences can use the incident, device, or account already open in a product. Context saves effort but needs attention: the analyst should confirm which entity and period the assistant actually used. A separate session for each case reduces accidental mixing of accounts, hosts, and conclusions. Pinned answers preserve useful working material, but remain snapshots whose sources and retrieval times matter.

Several permission layers apply. Entra roles govern directory administration, Azure role-based access control governs Azure resources, Copilot roles govern its experience, and connected products govern their records and actions. Permission to use Copilot does not automatically authorize device isolation or access to every workspace. Directory authority also does not automatically supply the Azure permissions required to provision capacity.

A permission intersection captures the need to satisfy the applicable boundaries:

```math
\mathcal{P}_{\text{effective}} = \mathcal{P}_{\text{Entra\_User}} \cap \mathcal{P}_{\text{Copilot\_Role}} \cap \mathcal{P}_{\text{Plugin\_Scope}} \cap \mathcal{P}_{\text{Tenant\_Boundary}}
```

This expression summarizes authorization constraints rather than reproducing every detail of Azure scopes, application identities, or agent authorization. For delegated operations, the analyst's underlying access remains central. Background agents likewise need an explicit execution identity and appropriately scoped permissions. Read access sufficient for investigation may be insufficient for a requested response action.

Provisioning and privacy require the same precision. Capacity administration and product-data access are separate assignments. Storage location, processing location, retention, optional diagnostic sharing, and foundation-model training are separate questions. A statement about training use alone cannot establish compliance with every data-handling requirement.

### Verify explanations against execution

Consider an illustrative incident involving WS-FIN-089 and Jonathan Wolcott, with remote desktop activity from `10.0.0.15`, encoded PowerShell, and a file named `mimikatz.exe`. Each clue supports an investigative question. The remote session may require authorization checks; the script requires decoding and behavioral analysis; the executable requires provenance, hash, and execution evidence.

An incident summary gives orientation by relating alerts, entities, and timestamps. The analyst must check those underlying records and determine which connections are observations and which are inferences. A summary can have limited coverage, and a suggested actor label does not establish attribution. The name `mimikatz.exe` is a useful lead, but does not independently establish what the file contains or whether it executed.

Script explanation can expose operations hidden behind Base64 or string manipulation. In this example, the decoded PowerShell uses `IEX` and `Net.WebClient.DownloadString` to retrieve and invoke a script from an internal address. This describes intended behavior. A process event may establish that the command was launched, while network and subsequent execution evidence help determine whether retrieval and payload execution succeeded. Mapping the command to ATT&CK techniques organizes the hypothesis without resolving those factual questions.

Generated KQL is similarly a starting point. Analysts must check table availability, field names, account representation, timestamps, and the logic that connects records. A query written with `TimeGenerated` may need a different timestamp column on another surface. Joining remote logons and process events by device and a one-hour window establishes an association; attributing a process to a particular session requires stronger account, logon, or session identifiers where available.

<details><summary>This illustrative hunt combines remote logons with suspicious PowerShell activity:</summary>

```kql
// Advanced Hunting KQL query generated via Security Copilot in Defender XDR
// Prompt: "Find all suspicious PowerShell executions by Jonathan Wolcott after RDP"
let TargetUser = "Jonathan Wolcott";
let LookbackTime = ago(24h);
// Step 1: Identify incoming RDP logons for the target identity
let RDPLogons = IdentityLogonEvents
    | where TimeGenerated >= LookbackTime
    | where AccountDisplayName =~ TargetUser or AccountUpn has "jwolcott"
    | where LogonType == "RemoteInteractive" or AdditionalFields has "3389"
    | project RDPTime = TimeGenerated, DeviceName, AccountUpn, IPAddress;
// Step 2: Correlate with process execution events on the target machine
DeviceProcessEvents
| where TimeGenerated >= LookbackTime
| where InitiatingProcessAccountUpn has "jwolcott" or AccountName =~ TargetUser
| where FileName =~ "powershell.exe" or ProcessCommandLine has "powershell"
| where ProcessCommandLine has_any ("-enc", "-w hidden", "IEX", "DownloadString", "bypass")
| join kind=inner (
    RDPLogons
) on DeviceName
| where TimeGenerated between (RDPTime .. (RDPTime + 1h))
| project
    TimeGenerated,
    RDPTime,
    DeviceName,
    AccountUpn,
    ProcessCommandLine,
    InitiatingProcessFileName,
    InitiatingProcessCommandLine,
    SHA256
| order by TimeGenerated desc
```

</details>

Broad artifact hunts also have limits. Names and command fragments can miss renamed tools or alternative methods. Joining every process to every network event on the same device can multiply rows and associate unrelated activity. Validate the evidence population and relationships before interpreting results as exfiltration or promoting a generated query into a maintained detection.

The incident record should retain affected entities, relevant times, evidence sources, completed actions, and unresolved questions. Drafting assistance reduces documentation effort, but the investigator still checks it against the underlying records. Feedback about weak answers helps identify recurring problems; it should not be interpreted as immediate retraining of a tenant-specific model.

### Evaluate agents by their decisions and actions

Agents extend assistance into background work initiated by configured events or schedules. Potential uses include phishing triage, intelligence briefings, hunting, and correlation of weak signals. Availability, licensing, triggers, and allowed actions depend on the deployment.

Phishing triage illustrates the distinction between classification and response. Sender authentication, URL verdicts, attachment information, and impersonation cues can support an assessment. No single signal supplies a universal decision rule. An LLM-generated confidence number is also not automatically a calibrated probability. Thresholds need validation against actual cases and the consequences of false classifications.

Classifying a message as malicious does not establish that its recipient is compromised. Post-delivery message cleanup and revocation of user sessions address different exposures and need their own evidence and authorization. Action records should show what was evaluated, what decision followed, which operations were attempted, and whether they completed. A successful-looking narrative cannot substitute for those records.

Agents also encounter attacker-controlled content. An email instructing the assistant to disregard its rules remains evidence to inspect. It cannot acquire authority over tool use. Constrained permissions, technical verification, and escalation for uncertain cases help maintain that boundary.

An elementary workload model illustrates the possible effect of offloading. If alerts arrive at rate $\lambda_{\text{total}}$, agents handle proportion $\Phi_{\text{agent}}$ without human work, and $c$ analysts each serve work at rate $\mu_{\text{human}}$, utilization is:

```math
\rho = \frac{\lambda_{\text{effective}}}{c \cdot \mu_{\text{human}}} = \frac{\lambda_{\text{total}} (1 - \Phi_{\text{agent}})}{c \cdot \mu_{\text{human}}}
```

Here, $\lambda_{\text{effective}}$ is the rate of alerts requiring human work. The assumption that handled cases require no human effort is substantial. Corrections, escalations, and review can reduce the apparent savings, while bursty incidents make average arrival rates incomplete descriptions of demand. Measure the remaining work rather than inferring operational benefit from the number of cases an agent touched.

### Plan capacity around verified outcomes

Security Compute Units connect usage to capacity planning. Interactive requests, embedded assistance, and background agents can compete for compute. Ordinary demand may differ sharply from a major incident or a burst of user-reported messages. Additional capacity can help absorb peaks, while configured limits, available capacity, plugin response times, and query complexity still affect completion.

A baseline-plus-burst model expresses the budgeting principle:

```math
C_{\text{monthly}} = 730 \cdot N_{\text{res}} \cdot P_{\text{res}} + \int_0^T \max\left(0, \lambda(t) - N_{\text{res}}\right) \cdot P_{\text{burst}} \, dt
```

Here, $N_{\text{res}}$ is baseline capacity; $P_{\text{res}}$ and $P_{\text{burst}}$ are assumed hourly rates; and $\lambda(t)$ is demand expressed in equivalent SCUs. The modeled period $T$ is measured in hours. The 730-hour term is a budgeting convention, while actual billing depends on the applicable metering and period. The expression is an analytical illustration, not a current price quotation or service guarantee.

An illustrative calculation makes the model concrete. At assumed rates of \$4 per baseline SCU-hour and \$6 per burst SCU-hour, two units provisioned for a 730-hour month cost \$5,840. Three additional units used for fifty hours add \$900, producing \$6,740 in this example. These figures explain the arithmetic and are not current price quotations. The result also says nothing about whether that capacity meets a particular workload's latency needs; plugin response times and query complexity still need measurement.

Usage monitoring should connect consumption to analyst work and incident demand. Budget alerts provide visibility without necessarily enforcing a hard spending stop. Capacity decisions need measured workloads rather than an assumption that dynamic bursting eliminates delay.

Evaluation should consider time to a verified finding, analyst correction effort, query validity, handover quality, and confirmation of containment. Compare equivalent work: faster retrieval and drafting should not be credited with completing verification or remediation that remains for a person. These measures reveal whether assistance improves the decisions the security team actually needs to make.

## Protecting sensitive data and preserving evidence with Purview

Purview connects the information involved in an incident with the records needed to investigate it. Data Loss Prevention (DLP) identifies sensitive information and applies policy to its use. Insider Risk Management (IRM) evaluates patterns that warrant review. eDiscovery preserves and collects relevant content. Audit records the operations surrounding that content. Defender XDR contributes the device, identity, and threat context; supported Endpoint DLP alerts can appear in its investigation environment.

These capabilities answer related but different questions. A blocked transfer establishes that a control intervened. An unusual sequence of downloads justifies investigation. A preserved document supplies content for review, while an audit record documents an observed operation. Conclusions become stronger when investigators connect these records through the user, device, file, destination, and relevant time window.

### Classification and enforcement

Sensitive Information Types identify content through patterns and supporting evidence. A payment-card detector can combine number structure, checksum validation, and nearby financial terms. Custom classifiers and Exact Data Match address information specific to an organization. Sensitivity labels express business classifications and can apply access restrictions, encryption, or markings according to their configuration. A Confidential label alone does not establish that a document is encrypted.

DLP connects classification to an action at a supported location: sending email externally, copying a file to removable media, or uploading through a browser. Available responses include auditing, notification, justified overrides, and blocking. The enforcement result matters as much as the match. An alert about an attempted transfer cannot establish successful data loss without further evidence.

Useful policies account for legitimate work. A payroll department routinely handles financial information; destination, sensitivity, activity, and volume help distinguish ordinary processing from risky transfers. Override justifications provide context for review, while repeated exceptions can reveal a rule that needs adjustment. Coverage depends on endpoint onboarding, operating systems, browser support, extensions, and service-domain configuration. Removable media, printing, clipboard operations, and browser uploads can have different requirements.

Cloud evidence needs similar precision. A personal-storage connection near a DLP alert does not prove that the flagged file was uploaded. File hashes, process evidence, application activity, and service-side records can strengthen or disprove the relationship. Defender for Cloud Apps file policies inspect supported services through provider APIs, but Microsoft has scheduled those policies to retire on January 6, 2027, with migration to Purview DLP or auto-labeling policies. Continued coverage depends on accounting for that transition. [Microsoft's file-policy documentation](https://learn.microsoft.com/en-us/defender-cloud-apps/data-protection-policies).

### Insider risk and privacy

IRM evaluates activity against configured indicators and scenario templates, including departing-employee data theft, leaks, security policy violations, health-record misuse, and risky browsing. Each scenario requires suitable signals and integrations. Security-policy-violation templates, for example, can use Defender for Endpoint alerts. A template match directs attention; it does not determine intent. The activity might reflect malicious conduct, a mistake, or a compromised account.

Departure-related investigations depend on accurate HR context. Resignation and last-working dates must be timely and correctly associated with identities. Microsoft's documented HR connector accepts CSV-based ingestion with required fields and identity mapping. Its format needs to match that documented contract.

IRM pseudonymizes users by default, limiting identity exposure during initial review. Content and metadata can still reveal identities, and some exports disclose usernames. Role assignments, identity disclosure, content access, and export authority therefore need explicit ownership. Organizations may require legal review or several approvals before identifying an employee or sharing case material.

### Preservation, search, and collection limits

Preservation and search serve different purposes. Holds protect content within their scope; searches identify material for examination. The modern Purview eDiscovery experience incorporates Content Search and provides case management, holds, searches, and exports. Premium capabilities add review sets, advanced indexing, conversation threading, and analytics, subject to licensing. Supported content includes Exchange, SharePoint, OneDrive, and Teams.

Access depends on roles and case permissions. Ordinary eDiscovery managers operate within permitted cases; administrators have broader access. Missing case membership can explain an investigator's inability to see a case.

Custodians, locations, dates, and content conditions shape search scope. Precision measures how much returned material is relevant; recall measures how much relevant material was found. Reviewing returned samples helps assess precision, while recall requires consideration of potentially relevant material outside those results. Keyword Query Language in eDiscovery and Kusto Query Language in security hunting share an abbreviation, but their syntax differs.

Encrypted archives, unsupported formats, partially indexed items, and processing failures can leave collection gaps. Export reports should identify selected content, settings, outputs, and exceptions. Original exports and custody records preserve the relationship between the reviewed material and its source. Cryptographic hashes help detect changes after collection, but cannot establish completeness or automatic admissibility.

### Audit evidence and retention

Audit records supply workload-specific details about actors, timestamps, operations, and affected content, often within nested `AuditData` JSON. Audit Standard generally retains records for 180 days. For appropriately licensed users, Audit Premium provides one-year default retention for specified core workloads, retention policies, and higher Management Activity API bandwidth. Ten-year retention requires an additional license. Licensing and policy changes do not alter previously committed items or recover expired evidence. [Microsoft's Audit overview](https://learn.microsoft.com/en-us/purview/audit-solutions-overview).

Audit availability needs independent verification. Microsoft directs administrators to check `UnifiedAuditLogIngestionEnabled` through Exchange Online PowerShell; Security & Compliance PowerShell can report `False` even when auditing is enabled. Searchable events can also lag enablement. Enabling auditing does not reconstruct activity that was never captured, and audit availability is separate from the existence of searchable documents and messages. [Microsoft's auditing setup guidance](https://learn.microsoft.com/en-us/purview/audit-log-enable-disable).

`MailItemsAccessed` requires careful interpretation. Bind records item access without proving that a person read the message. Sync records folder synchronization by supported Outlook desktop clients, with possible later offline access. Bind records can aggregate multiple accesses. The documentation includes this operation in Audit Standard for eligible E3 and E5 users. Session context and collection completeness determine what the records establish about incident scope. [Microsoft's mailbox-investigation guidance](https://learn.microsoft.com/en-us/purview/audit-log-investigate-accounts).

Parsing exported JSON with Power Query or PowerShell makes analysis easier, provided the original export remains available. Arrays, duplicates, workload-specific fields, and retrieval limits affect the result. Across DLP, IRM, eDiscovery, and Audit, a defensible account distinguishes recorded facts from hypotheses and makes evidence limitations visible.

## Securing endpoints and cloud workloads

Defender for Endpoint observes device behavior and supports hardening, investigation, and containment. Defender for Cloud assesses configuration weaknesses and protects supported workloads across Azure, Amazon Web Services (AWS), Google Cloud Platform (GCP), and hybrid infrastructure. Together, they connect what a device did with what its identity, permissions, and network relationships could reach.

### Endpoint coverage, access, and hardening

Defender for Endpoint assumes that prevention can fail and examines the behavior following an initial foothold. Process execution, file activity, registry changes, and connections become more useful when linked to a parent process and an account. On Windows, the Sense service, associated with `MsSense.exe`, contributes endpoint detection and response telemetry.

Onboarding methods vary across Windows, macOS, Linux, servers, and mobile devices. Local scripts support evaluation; Group Policy, Configuration Manager, and Intune provide managed Windows deployment options. Feature support varies by platform. Inventory presence, healthy sensors, expected telemetry, and controlled detection tests provide stronger evidence of coverage than a completed installation job.

A missing event has several possible explanations. Connectivity problems, an unhealthy sensor, policy assignment, or query scope can prevent expected evidence from appearing. Treating an empty query result as proof that nothing happened skips those dependencies. The same concern applies to servers and devices managed through different deployment systems: enrollment establishes a management relationship, while the investigation needs evidence that the relevant protection and reporting capabilities are actually operating.

Retention differs between investigation surfaces. Microsoft documents 180 days for Defender for Endpoint (MDE) data visible across the portal and a 30-day query window in advanced hunting. Longer portal history does not extend every query. Tenant region also requires advance planning: Microsoft states that an existing Defender tenant cannot move to another region, while integrated services can follow separate storage rules. [Microsoft's endpoint data guidance](https://learn.microsoft.com/en-us/defender-endpoint/data-storage-privacy).

Unified Role-Based Access Control separates investigation from actions such as isolation, remediation, and advanced Live Response. Entra security groups associate roles with operational responsibilities. Device groups supply an asset boundary through operating systems, domains, tags, or names. Ranking determines the applicable group when rules overlap, so a domain controller matching both a specific infrastructure group and a broad server group needs the intended precedence.

Automation settings further constrain response. Supported actions can run automatically, require approval, or remain manual. The appropriate level depends on the operational consequences: quarantining a workstation file and interrupting a production service create different effects. Responders need both visibility into the asset and authority to perform the required action.

Attack Surface Reduction (ASR) rules address behaviors associated with malicious execution, credential theft, and ransomware. Examples include Office child processes, Office-based process injection, obfuscated scripts, and credential theft from LSASS. Application control, exploit protection, network protection, Controlled Folder Access, and Credential Guard provide complementary hardening.

ASR values are Off `0`, Block `1`, Audit `2`, and Warn `6`. Audit permits the behavior and records its potential impact. Warn provides a warning and bypass where supported. It is unavailable for some rules, including Microsoft's LSASS credential-theft rule. Some standard protections can begin in enforcement, so a fixed progression through every mode is inappropriate. Compatibility evidence and each rule's support determine the suitable setting. [Microsoft's ASR rule reference](https://learn.microsoft.com/en-us/defender-endpoint/attack-surface-reduction-rules-reference).

Exclusions should resolve a documented need with the narrowest supported scope. A broad temporary-directory exclusion can shelter attacker-controlled files and weaken automated inspection. In the Windows Defender Operational log, Event ID **1122** denotes an ASR audit event and **1121** a block. Reversing them produces a false account of enforcement. Audit results describe potential impact; protection depends on the intended devices receiving an appropriate enforced policy.

### Device investigation and response

A device timeline connects alerts to processes, files, connections, and identities. Health, logged-on users, software inventory, vulnerabilities, recommendations, and missing updates supply additional context. These relationships help determine whether an alert is isolated or part of broader activity.

For example, a suspicious process can be linked to the application that launched it, the file it wrote, and its network destination. A hash or account then provides a pivot across other devices. That broader scope matters when the first machine is only an entry point: deleting an executable on one host cannot establish that related activity elsewhere has stopped. Evidence should support both the immediate containment decision and the assessment of remaining access.

Device isolation interrupts network communication while preserving the supported Defender service connection. Some platforms and configurations support selective isolation that preserves certain collaboration traffic. Other responses include investigation packages, application restrictions, automated investigations, and Live Response. A package captures artifacts available at collection time; a process list collected after a reboot cannot reconstruct every earlier in-memory event.

Live Response provides commands for inspecting processes, connections, persistence, services, registry information, and files. More powerful permissions enable file collection, library-based scripts, and remediation. Available commands depend on platform and role, and the interface has its own command set. File retrieval and script execution deserve restricted roles and reviewable command records.

Automated Investigation and Remediation examines associated evidence and can propose or execute supported actions. The Action Center distinguishes pending and completed actions. That distinction determines whether exposure remains: a proposed quarantine has not removed a file. Removing the first artifact may also leave stolen credentials, scheduled tasks, or another compromised device unresolved.

Suppression rules reduce repeated alerts from verified administrative activity, but scope matters. A maintenance script can become harmful when executed through a compromised account. Custom indicators can block, audit, or allow supported files, addresses, domains, URLs, and certificates; broad allow entries and certificate blocks can affect legitimate protection or software. API submissions require valid hashes, supported action and scope fields, and supported address formats. The endpoint indicator API does not accept CIDR notation for IP indicators. [Microsoft's indicator API reference](https://learn.microsoft.com/en-us/defender-endpoint/api/post-ti-indicator).

Defender Vulnerability Management combines inventory, exposure, vulnerabilities, and recommendations to prioritize preventive work. An exploited weakness on an important server can deserve attention before a higher severity finding on an isolated test device. Security and IT share responsibility for the resulting remediation. The affected population and assigned owner matter because a recommendation cannot change a device by itself. A completed remediation request or successful deployment package provides useful implementation evidence, but the remaining exposure depends on whether the intended update or setting reached the affected systems. Fresh assessment data helps confirm remediation, allowing for processing delays. Device risk can also inform Intune compliance and Entra Conditional Access when the relevant integrations and policies are configured.

### Cloud coverage and attack paths

Defender for Cloud combines Cloud Security Posture Management (CSPM), Cloud Workload Protection (CWPP), and DevSecOps capabilities. CSPM identifies exposure, excessive permissions, and configuration gaps. CWPP detects suspicious behavior in supported running workloads. DevSecOps integrations surface secrets, vulnerable dependencies, and infrastructure weaknesses before deployment. Plans and resource scope determine which capabilities are active; subscription visibility alone does not prove complete workload protection.

Azure Arc represents non-Azure machines as manageable Azure resources. Its Connected Machine agent, Azure Monitor Agent, and MDE sensor have distinct purposes. Arc registration therefore does not establish monitoring or endpoint protection. AWS connectors use federated trust with short-lived credentials; GCP uses workload identity federation and service account impersonation. Connector scope, permissions, extension deployment, sensor health, and expected runtime signals all affect actual coverage. Authentication success cannot compensate for a connector that overlooks relevant resources or lacks permission to assess them. Foundational posture assessment and paid protection plans also serve different purposes. An organization needs to relate its required protections to the resources and plans actually selected, including hybrid machines whose registration, monitoring, and endpoint security are configured separately.

The Cloud Security Graph relates resources, identities, permissions, network exposure, and vulnerabilities. Attack path analysis highlights combinations that could allow compromise to spread. An internet-facing vulnerable VM with an overly privileged identity can expose a sensitive service beyond the original host. Actual permissions, network controls, and service settings determine the route; a role name alone cannot establish access to a particular secret.

Patching, restricting exposure, reducing privileges, or hardening a target can interrupt a necessary relationship. Removing one route does not eliminate every alternative. These findings describe potential access, while runtime evidence is needed to establish exploitation. Graph and posture updates are asynchronous, so direct resource checks help verify a change before refreshed assessments appear.

Secure Score supports broader posture planning, but Microsoft documents different models: a classic control-based score in the Azure portal and a risk-based Cloud Secure Score in the Defender portal. Their calculations and values differ. Neither a favorable score nor a benchmark mapping establishes that every important attack path has been removed.

### Workload-specific evidence

Servers, containers, databases, storage, secrets services, APIs, and resource management expose different evidence and response capabilities. Server investigations emphasize processes, credential attacks, persistence, and execution. Containers add image vulnerabilities, cluster exposure, and runtime privilege abuse. Database activity can reveal unusual authentication, queries, or possible extraction. Storage investigations focus on access, transfers, and supported malware-scanning results, while secrets services require attention to unexpected secret access and callers. API protection applies within the supported, onboarded scope. These differences shape what a finding establishes and which additional records can corroborate it. Defender for Servers Plan 1 focuses on endpoint detection and response through MDE; Plan 2 adds capabilities such as agentless scanning, file integrity monitoring, and just-in-time access, subject to deployment requirements.

Cloud investigations also need management activity. An attacker using stolen administrative access can invoke a VM extension or run-command mechanism to execute inside a workload. Caller identity, source address, operation, target resource, and subsequent endpoint behavior distinguish candidate abuse from ordinary administration. Successful extension deployment alone does not establish malicious execution.

Consumption limits can affect coverage. Defender for Storage uses storage-account pricing, separately metered malware scanning, and possible additional charges for high transaction volumes. A scanning cap may contain cost while leaving later uploads unscanned. Coverage therefore needs assessment alongside the budget.

## KQL and the quality of security evidence

An investigation question needs a defined evidence population before it needs sophisticated query logic. Which accounts experienced failed sign-ins? Which devices ran an unfamiliar process? Did the activity occur in one burst or accumulate over a month? KQL makes those choices explicit through filters, calculations, aggregations, and correlations.

In Sentinel and Azure Monitor Log Analytics, tables such as `SecurityEvent` and `SigninLogs` provide the records. Each pipe passes a logical result to another operator. These analytical queries read the underlying data; the engine can optimize execution, so the written operator sequence is not a fixed physical execution plan.

### Define the population and preserve its meaning

The core operators express the investigation directly. `where` selects rows, `let` names an expression or subquery, `extend` calculates columns, `project` selects output fields, and `order by` sorts results. Explicit projection helps preserve a stable output schema for downstream consumers. Related operators can remove, rename, or reorder columns without changing the underlying source.

Time is usually the first useful boundary. A predicate such as `where TimeGenerated >= ago(7d)` restricts the investigation and can help the engine eliminate irrelevant data. Filters near table references, particularly datetime predicates, are a recommended performance practice. The optimizer can also reorder predicates.

Other conditions should match the question precisely. `EventID in (4624, 4625)` selects successful and failed Windows logons. Adding `EventID != 4688` after that selection would be redundant. String equality also needs deliberate handling: `==` is case-sensitive, while `=~` ignores case. `AccountType =~ "user"` therefore accepts casing variations. `in` and `!in` express set membership and exclusion.

When the schema is unfamiliar, `search in (SecurityEvent, SigninLogs) "term"` can identify useful records and supplies `$table` for source attribution. Once the source and relevant field are known, a focused query offers clearer scope. Broad searches should not substitute for understanding which records the investigation includes.

Calculated severity is similarly a choice made by the analyst. Assigning a higher score to a failed logon can prioritize review, but it cannot establish that the failure was malicious. Performance estimates need the same restraint: seven days represents about 3.9% of a uniformly populated 180-day dataset, while actual ingestion and storage layout determine physical reads and runtime.

### Measure behavior at the right level

`summarize` groups records and calculates measurements for each group. The grouping key defines the unit of analysis: `Computer` describes hosts, `Account` describes identities, and `IPAddress` describes activity associated with an address. Adding `bin(TimeGenerated, 1h)` creates hourly measurements rather than a single total over the lookback period.

`count()` measures rows, while `countif()` measures rows meeting a condition. `dcount()` and `dcountif()` estimate distinct values, helping distinguish repeated activity from breadth. Ten failures against one account and ten failures against ten accounts have the same total count but different investigative implications. A useful password-spraying hypothesis therefore examines the distribution across identities, not just an application count.

An IP address associated with failures involving several applications may deserve attention, but that observation alone is narrower than evidence of spraying. Shared egress, legitimate automation, and observation length affect its meaning. A thirty-day aggregate can combine unrelated events that never formed a concentrated attack. Thresholds require evaluation against local traffic and the behavior the detection is intended to identify.

Collection functions also preserve different information. `make_list()` retains duplicate observations; `make_set()` retains distinct values. A list is not automatically chronological: its ordering is undefined unless the input to `summarize` is sorted. Microsoft documents a default and maximum list size of 1,048,576 elements, so the number and length of collected values matter.

Use `min(TimeGenerated)` and `max(TimeGenerated)` when only first and last timestamps are required. `arg_min()` and `arg_max()` return columns from a selected event, which is useful when the event's context matters. Returning entire rows adds complexity when a timestamp alone answers the question.

`dcount()` uses a variant of HyperLogLog. Its default accuracy level, `1`, has a documented 0.8% standard deviation of relative error; level `3` has 0.28%. These are probabilistic characteristics rather than guarantees of exactness. Exact counting requires a suitable approach, such as the supported `count_distinct()` function, which its documentation labels preview and subjects to limits. Measuring a set's length is exact only when that set contains every distinct value without truncation.

Time buckets expose changes at a chosen resolution. Short intervals reveal brief bursts but can produce noisy measurements; longer intervals can conceal a concentrated sequence. A process-creation spike may reflect an attacker, software deployment, or a scheduled task. The underlying events remain necessary to explain the aggregate.

### Combine records without creating false relationships

`union` assembles rows from multiple sources, while `join` combines related records. Under the default outer schema behavior, `SecurityEvent | union SigninLogs` includes columns from both tables and leaves cells empty where an input lacks a value. Same-named columns with different types can become separate columns with type suffixes.

Unlike `search`, `union` does not automatically add `$table`. Use `withsource=SourceTable` when provenance matters. Combining tables also does not normalize account formats, timestamp meanings, or event semantics. Those differences need deliberate treatment before the rows become one analytical population.

A join's flavor determines what survives. `inner` retains matching combinations. `leftouter` retains all left-side records and adds available matches. `rightouter` preserves the right side; `fullouter` preserves unmatched records from both. `leftsemi` retains left records with a match without adding right columns, while `leftanti` retains left records absent from the reference population.

KQL's default join flavor is `innerunique`, which deduplicates left-side keys before matching. Distinct events sharing an account or device can disappear, and different representative left rows can be selected. Specify `kind=inner` when every matching combination matters. [The `innerunique` reference](https://learn.microsoft.com/en-us/kusto/query/join-innerunique?view=azure-data-explorer) demonstrates the effect. Omitting the flavor can therefore change the evidence without making the query look obviously incorrect.

For example, joining high-risk sign-ins to MFA denials with an inner join removes sign-ins without matching denial records. A left outer join preserves that wider population. A missing match still does not prove successful MFA bypass: the cause can be a mismatched key, time window, collection gap, or different authentication outcome.

Join keys also control row multiplication. Ten thousand left records and ten thousand right records sharing one key can produce one hundred million matching combinations. Filter and aggregate inputs to the level the question requires. Microsoft's optimization guidance generally recommends putting the smaller input on the left, but changing sides can change the population preserved by a particular flavor. Performance choices need to preserve the analytical question.

An anti join against a process-name baseline illustrates the interpretive limit. It can identify process names newly observed within the available data. It cannot establish that the baseline was clean or the new process is malicious. Likewise, subtracting logoff counts from logon counts does not measure session duration; session-level claims require suitable identifiers and event context.

### Extract structure while retaining original context

Text fields often hold several useful facts. `extract(regex, captureGroup, text)` isolates a value through a regular expression. `parse` works well when messages follow recurring delimiters and can assign types such as `string`, `long`, or `datetime`. Failed parsing can produce nulls, so missing extracted values should not be interpreted as missing activity without inspecting failures.

Normalization helps join differently formatted identities, but it can also erase distinctions. Reducing both `CORP\jwolcott` and `jwolcott@contoso.com` to `jwolcott` simplifies grouping while potentially merging unrelated accounts sharing that short name. Preserve the original value and domain context when attribution depends on them.

KQL's `dynamic` type represents arrays and property bags. Access properties directly when a column already contains a dynamic object; use `parse_json()` when it contains serialized JSON. Cast extracted values with functions such as `tostring()` or `tolong()` before operations that require scalar types.

Array indexing selects a particular element rather than interpreting the whole event. `AuthArray[0].authenticationMethod` reads the first authentication step and does not establish every method used in a multistep sign-in. Filtering rows before repeated extraction or JSON conversion can reduce work, although the actual performance benefit depends on execution and data characteristics.

### Treat enrichment and reusable logic as dependencies

External intelligence can connect local activity with known indicators. `externaldata` reads a reference file under a declared schema and can add threat-group labels or indicator context. Microsoft describes it as appropriate for small reference datasets up to 100 MB. Successful retrieval requires accessible storage and valid authentication.

Credential-bearing connection strings need appropriate handling. Query parameters are recommended where supported, with obfuscated literals available when necessary. An `h@` prefix can prevent a secret from appearing in traces, but the query text remains visible to people who can read it.

A failed reference-file retrieval means the intended logic was not evaluated. It cannot be treated as a successful search returning no indicator matches. Expired credentials, changed reference schemas, and inaccessible storage are operational detection failures whose health needs monitoring.

Reusable functions give recurring logic a consistent interface. Inputs, output fields, types, and filters become dependencies for every caller. Microsoft Sentinel's Advanced Security Information Model (ASIM) applies this principle through parsers that map vendor-specific events into shared schemas, including network sessions and DNS activity. Common field names reduce repeated translation while leaving source coverage and collection quality essential to interpretation.

Changes to a shared function can affect many scheduled detections. Validate dependent queries when interfaces change, preserve understandable provenance, and avoid circular dependencies. A reliable query makes its inclusion, exclusion, grouping, and matching decisions visible enough for another analyst to explain the result.

## Microsoft Sentinel: security analytics across the environment

Microsoft Sentinel extends security operations beyond the telemetry supplied by a single product family. Its foundation is an Azure Log Analytics workspace containing tables that analysts query with KQL. Connectors bring in evidence; parsers make different sources comparable; analytics rules identify patterns; and incidents connect the resulting alerts to affected accounts, devices, and resources. Hunting adds a way to investigate questions that existing detections have not answered.

The useful distinction between security information and event management (SIEM) and XDR is the evidence each contributes. Defender XDR connects supported endpoint, identity, email, and cloud application signals. Sentinel accommodates additional sources, custom analytics, and historical investigation requirements. Their integration gives analysts more context, while the collection, permissions, and correlation boundaries of each source still apply.

### Workspaces define investigation boundaries

A workspace affects data residency, access, retention, query scope, and security content management. A centralized organization may benefit from one workspace; regional requirements or separate access boundaries may justify several. Multiple tenants add delegated management and tenant-specific permissions. Extra separation can support governance, but it also increases the effort required to maintain consistent detections and investigate activity across boundaries.

Workspace region belongs in deployment planning because later regional changes require migration planning. Sentinel Reader, Responder, and Contributor roles separate operational responsibilities, while Azure and Log Analytics permissions also influence access. Workspace Manager helps distribute supported content, and Azure Lighthouse supports delegated management across tenants. Neither replaces ownership of connector health, detection changes, access decisions, or investigations.

The appropriate boundary depends on both the organization and the investigation. Regional separation can satisfy a governance requirement while making an attack spanning regions harder to examine. Delegated resource management can simplify administration without granting every analyst identical access. These tradeoffs belong in the architecture because they determine which evidence a responder can actually consult under incident pressure.

Retention determines which questions remain answerable. Investigators may need evidence of the first suspicious authentication, earlier persistence, or related activity on another device. Once the necessary records expire, a later alert cannot recreate them. Set retention according to the source and its investigative value, and verify actual table settings. Microsoft's guidance describes different treatment for Sentinel and Defender XDR data, including ninety-day retention provisions for Sentinel solution tables. [Manage data tiers and retention](https://learn.microsoft.com/en-us/azure/sentinel/manage-data-overview)

Storage availability and analytical availability are separate concerns. The analytics tier supports operational querying and detection; the data lake tier supports longer-term analysis, with retention configurable up to twelve years. Historical evidence that requires background processing serves a different purpose from evidence immediately available to a detection rule. Retention planning must account for how data will be queried as well as whether it still exists.

Ingestion, retrieval, processing, and resulting storage all affect cost. Importing alerts and incidents differs from ingesting raw event tables. A deployment should therefore identify which evidence is needed for rapid investigation and which has sufficient historical value to justify longer storage. Broad collection without a defined use can increase expenditure while leaving the important analytical questions unresolved.

### Shared investigation does not erase correlation boundaries

Sentinel's integration with the Microsoft Defender portal brings incidents, entities, and hunting into a shared investigation environment. Sentinel can also operate there without Defender XDR; the additional cross-product context depends on the Defender services and data actually available.

The portal supports a primary Sentinel workspace and multiple secondary workspaces. With Defender XDR present, its alerts and incidents synchronize with the primary workspace, whose alerts can participate in shared correlation. Secondary workspaces retain separate correlation boundaries. One incident queue consequently does not establish unrestricted correlation across all connected workspaces. [Multiple Sentinel workspaces](https://learn.microsoft.com/en-us/azure/sentinel/workspaces-defender-portal)

Integration also affects detection and automation assumptions. Legacy Microsoft incident creation rules are unsupported in the Defender portal, and correlation can change incident titles. Conditions tied to analytics rule names and relevant tags can be more dependable than conditions tied to titles. Existing deployments need to evaluate migration differences, including Fusion behavior, against the transition guidance.

Cross-source queries remain analytical claims to validate. Failed Windows logons and successful endpoint logons associated with an account can suggest a useful investigation, but account formats, timestamps, and collection coverage affect the relationship. A successful logon does not establish that preceding failures belonged to an attack. The shared interface reduces navigation effort; it does not remove the need to examine the underlying records.

### Collection quality sets the detection ceiling

The security question determines the required telemetry. Password-attack investigations need authentication outcomes and account identifiers. Execution investigations need process events and command-line context. Cloud control-plane investigations need activity records describing the relevant changes. Collecting adjacent data cannot compensate for a missing fact on which the hypothesis depends.

Common Sentinel sources include Entra sign-in and audit records, Azure activity, Defender alerts and supported event tables, Windows Security events, appliance events, syslog, and threat intelligence. Windows Security events typically arrive through Azure Monitor Agent (AMA) and a Data Collection Rule (DCR) in `SecurityEvent`. Common Event Format (CEF) appliance records commonly populate `CommonSecurityLog`, while syslog records populate `Syslog`.

Content Hub solutions package related connectors, parsers, analytics templates, hunting queries, and other content. Installing a solution makes those components available. Actual collection still depends on source configuration, permissions, agent health, forwarding, and destination settings. An installed agent or a connector that appears healthy does not prove that the required event is queryable.

A DCR controls supported collection: participating resources, streams, event selection, transformations, and destinations. Windows event scope and syslog facility or severity choices therefore change what investigators can see. Azure Arc enrollment is part of the standard AMA deployment path for supported non-Azure servers. These dependencies need to be understood when assessing apparent gaps in collection.

Ingestion-time transformations can reduce volume or prepare fields for analysis, but discarded records are unavailable to later investigations through that path. A cost-saving filter can consequently remove the evidence required by a detection. Representative records and the analytics that depend on them provide the basis for assessing such changes.

CEF supplies a defined security-event structure over syslog transport; plain syslog often needs more source-specific extraction. Current AMA forwarding details differ from older architectures. Devices typically send to a syslog daemon on configured TCP or UDP port 514. AMA versions 1.28.11 and later receive locally forwarded logs on TCP port 28330; earlier versions use a Unix domain socket. Port 25226 should not be assumed to describe the current AMA architecture. [CEF and syslog AMA architecture](https://learn.microsoft.com/en-us/azure/sentinel/cef-syslog-ama-overview)

Collection configuration and analytical content both benefit from reviewed change management. Repository integration with GitHub or Azure DevOps can maintain supported security content with an owner and review history. The relevant outcome is dependable evidence with a known scope, rather than the mere presence of deployed components.

### Normalize meaning before correlating records

Sources describe similar activity differently. A host may appear as `Computer` or `DeviceName`; an account may appear as a username, domain-qualified account, principal name, or immutable identifier. Matching display strings without accounting for these differences can miss related activity or associate unrelated entities.

The Advanced Security Information Model (ASIM) provides common schemas and parsers for categories including authentication, DNS, process creation, and network sessions. Unifying parsers combine supported sources into a shared analytical view. Built-in names include `_Im_Authentication`, `_Im_Dns`, and `_Im_ProcessCreate`, but available source parsers and fields still require verification.

Custom parsing depends on real source records and the chosen schema's field definitions. Logic that extracts one convenient sample may fail on an unusual record. Parameterized KQL functions can centralize reviewed parsing or hunting logic, reducing inconsistent copies across investigations. Their influence extends to every dependent detection, making parser changes a security-content change rather than a cosmetic adjustment.

Watchlists add organizational context such as critical hosts or privileged accounts. Maintaining that reference information separately can make detection logic easier to review. Matching still depends on normalized keys, current values, and appropriate handling of duplicates. A stale hostname or inconsistent account format can silently exclude the intended asset.

Threat intelligence adds external context through domain, IP, URL, and file-hash indicators. Current queries need the appropriate `ThreatIntelIndicators` and `ThreatIntelObjects` schemas. Legacy examples using `ThreatIntelligenceIndicator` require field-mapping changes as well as a table-name change. Indicator confidence, age, validity, and relationship to observed activity determine the strength of a match.

Context becomes useful when analytical logic consumes it. A critical-server list can alter the priority of an authentication finding, and a relevant domain indicator can change the interpretation of DNS activity. Simply importing either reference dataset does not establish coverage. Analysts need to understand which queries use it and whether the available events contain values that can be matched reliably.

### Detection quality includes configuration and interpretation

An analytics rule is a repeatable security hypothesis. Its KQL identifies the pattern, while its schedule, lookback, threshold, grouping, and entity mappings determine how that pattern reaches analysts. A valid query alone does not establish a useful detection.

Scheduled rules need compatible frequency and lookback settings. A rule running every five minutes over a day of evidence repeatedly evaluates many of the same records. Overlapping windows may be justified, but they can create duplicate results unless the detection accounts for them. Entity mapping helps preserve useful account and host context, while ATT&CK mapping helps organize coverage assessment.

Near-real-time rules run at one-minute intervals, but the interval does not guarantee containment within a minute of the original activity. Collection, ingestion, processing, incident handling, and the response itself each contribute latency. End-to-end timing matters more to an active attack than any single advertised interval.

User and Entity Behavior Analytics (UEBA) adds historical, peer, and organizational context around entities. New geography, increased activity, or unfamiliar resource access can become more meaningful against an established baseline. Legitimate responsibilities and administrative tasks can also change behavior. An anomaly supplies an investigative lead; concrete events and environmental context determine its significance.

Behavioral analytics also require time and local evaluation. The relevant training period affects what the model has learned about an entity, while testing or flighting capabilities help assess whether results are useful in the environment. A deviation that looks compelling in isolation can become ordinary once the person's role, recent responsibilities, and related administrative activity are considered.

Generic statistical examples should remain separate from product scores. A z-score can illustrate deviation, but it does not describe every Sentinel model. The documented `Anomalies` table uses `Score`, and the anomaly reference describes scores between zero and one. A statistical threshold of three is therefore not a universal threshold for those records. Anomaly rules also do not directly create alerts.

Precision indicates how many investigated positives represent actual threats; it cannot by itself reveal activity the detection missed. Reviews should also consider missed cases, entity quality, duplicate results, and the work required to reach a supported decision. Fewer alerts demonstrate improvement only when relevant threats remain visible.

### Automation authority and evidence must remain visible

Automation rules can set ownership, severity, status, tags, or tasks and invoke Logic Apps playbooks. These capabilities are useful only within explicit response authority. Sentinel needs permission to invoke a playbook, and its connected actions need suitable authentication and authorization for their target services. Managed identities can support that access where available.

Rule ordering can affect matching because later rules see changes made by earlier ones. A long-running playbook, however, may continue after the automation engine advances. Dependencies that require completed enrichment therefore need explicit handling. Run history must distinguish attempted actions from completed enrichment or containment. [Automation rule execution and ordering](https://learn.microsoft.com/en-us/azure/sentinel/automate-incident-handling-with-automation-rules)

The distinction between evidence and action remains essential during investigation. An event is a raw record; an alert marks potentially suspicious activity; an entity identifies an involved account, device, address, file, process, or application; and an incident groups related material into a case. Correlation suggests relationships, while the underlying records establish what was actually observed. Incident records should preserve the reasoning behind classification, affected scope, completed response, and unresolved questions.

### Hunting extends the questions the system can answer

Threat hunting examines plausible activity that maintained detections may have missed. A useful hypothesis names the behavior, entities, time range, and necessary telemetry. Searching for encoded PowerShell or download-related command lines during a defined period provides a testable question. A broad request for suspicious activity does not establish what evidence would support or weaken the explanation.

Bookmarks can preserve relevant query results and entity context in supported experiences. Whatever preservation mechanism is used, the query, time range, selected records, and investigative reasoning should remain available. Repeated hunts with clear value can inform maintained detections, while a hunt that finds no compromise can still expose a collection gap or eliminate a plausible explanation.

Entity context supports expansion of scope without treating every association as proof. Related accounts, hosts, commands, addresses, and time periods can suggest additional evidence to inspect. Missing evidence deserves equal attention: it can reveal an unsupported hypothesis, an overly narrow search, or a collection limitation. Recording that uncertainty makes the eventual incident classification easier for another investigator to assess.

ATT&CK coverage also requires interpretation. A technique tag shows that analytical content exists. Demonstrated coverage additionally depends on usable telemetry, correct logic, realistic validation, and the ability to respond. Counting tagged queries can otherwise conceal the same blind spots a hunt is meant to reveal.

Historical analysis may need background search or a larger analytical environment. Search jobs write results to queryable tables, whose storage and retention also need management. Log Analytics restoration and data lake processing are distinct: the current tier comparison does not list Restore as supported for the lake tier, while KQL and notebook jobs can promote data to analytics.

Notebooks support exploratory analysis through executable code and recorded reasoning. MSTICPy provides data access and security enrichment capabilities, with query results available for Python analysis. KQLmagic is a separate integration from MSTICPy's current Sentinel provider, which uses the Azure Monitor Query SDK. Authentication and workspace configuration must match the chosen provider and installed version.

Compatible assistants can also use Sentinel's MCP data-exploration integration to discover tables and query lake evidence, subject to setup, permissions, and applicable preview conditions. The access method does not change the analytical obligation: identify the source and scope, inspect the query, and support the conclusion with evidence.

The strongest improvement from an incident review is often specific: a missing command line reveals an audit-policy gap, an ambiguous identity match reveals a normalization problem, or unavailable historical evidence reveals an inadequate retention decision. Sentinel becomes more effective when those findings change the collection and analytics on which the next investigation will depend.

The shared objective across these capabilities is a security decision supported by evidence. Endpoint behavior, identity records, sensitive-content context, and cloud relationships each answer a different part of the question. KQL makes the analytical choices inspectable, while integrated investigation reduces the effort needed to connect them. AI and automation add value when their claims and completed actions remain visible. Operational progress appears in the resulting evidence: important assets report reliably, access is appropriately scoped, containment is confirmed, and the weaknesses that enabled an incident receive effective remediation.
