# Building an Elastic SOC Lab: From Endpoint Evidence to Incident Response

A security operations center (SOC) needs more than a searchable collection of logs. It needs a dependable path from activity on a host to evidence an analyst can interpret, a detection that identifies relevant behavior, and an investigation that records what happened and what response followed. A failed Windows logon can exist locally while remaining invisible in the monitoring platform because collection, transport, parsing, indexing, or the analyst’s search has failed.

An Elastic lab makes those dependencies concrete. Elasticsearch stores and searches records; Kibana provides the analyst’s interface; Fleet manages collection policies; endpoint integrations supply authentication and process evidence; and osTicket records investigation work. An isolated attack-emulation environment supplies known activity against which collection and detection can be evaluated. Each component has a distinct responsibility, and a useful lab verifies the connections between them.

This text develops that system from network design through Secure Shell (SSH) and Remote Desktop Protocol (RDP) monitoring, process reconstruction, ticket integration, and endpoint containment. Package versions, addresses, tokens, credentials, and interface identifiers must match the actual deployment.

## Design the network around the evidence path

The lab assigns six virtual machines to five connected operational functions and one exercise role. One Ubuntu VM hosts Elasticsearch and Kibana together. Separate Windows and Ubuntu endpoints supply operating-system and authentication records. Fleet Server manages enrolled agents, osTicket tracks investigations, and a Mythic command-and-control (C2) server supports attack emulation outside the management network. The analyst’s browser and the exercise operator’s workstation are additional clients. Logstash is an optional processing component, not another required VM in this inventory.

Keep three objects distinct. An **event** records an observation, an **alert** results from detection logic applied to observations, and a **ticket** tracks investigation work. Collecting an event does not automatically create an alert, and an alert does not establish that a ticket exists. Every transition needs configuration and a way to verify its result.

### Separate management connections from telemetry delivery

Fleet provides centralized agent management through Kibana, with management state stored in Elasticsearch. Fleet Server communicates with enrolled agents and accesses that management state. An endpoint’s management connection carries enrollment, policy changes, check-ins, and supported actions. Its telemetry connection carries collected records to Elasticsearch or another configured output. Fleet Server does not have to relay every endpoint event.

Agents initiate their connections to Fleet Server. Policy changes can return over those established connections, including through long polling; centralized management does not inherently require a separate inbound connection from Fleet Server to every endpoint. [Fleet Server architecture](https://www.elastic.co/docs/reference/fleet/fleet-server)

A successful enrollment therefore establishes a management relationship, not successful collection from every configured channel. An agent can check in while its event output fails. Conversely, an analyst’s connection to Kibana is separate from both endpoint paths and need not require direct public access to Elasticsearch.

The initial network plan places Elasticsearch/Kibana, Fleet Server, osTicket, and both endpoints in a private network, leaving Mythic outside. The revised design removes the Windows and Ubuntu endpoints from that network while keeping the three management VMs inside it. The reason is practical: a monitored endpoint may become compromised, and removing its private interface eliminates one potential path toward management services. Public routes, credentials, and other configured access paths still matter.

That separation creates an explicit connectivity requirement. Endpoints outside the private network must reach Fleet Server and their configured telemetry output through permitted public endpoints, controlled tunnels, or another deliberate route. The existence of a private subnet does not resolve those flows. Similarly, an intended Kibana-to-osTicket integration still needs API authentication, a valid payload, application reachability, and defined ticket behavior; the osTicket API supports ticket creation, not automatic two-way synchronization merely because the products are connected.

### Address the private subnet deliberately

A virtual private cloud (VPC) provides a logically isolated private network for attached resources. Creating it does not automatically attach every VM in an account. Select it for the intended management machines and verify their guest interfaces after deployment.

Private addresses can be reused in separate networks and are not public identities. A VM can have both public and private connectivity, so a private address alone does not establish that its services are inaccessible from the Internet. Routing supplies possible paths, firewalls permit or deny traffic, and application authentication and authorization govern service use.

Classless Inter-Domain Routing (CIDR) describes the network prefix length. IPv4 has 32 bits; a `/24` leaves eight host bits and therefore 256 addresses. The essential capacity relationships are:

$$
h = w - p = 32 - 24 = 8
$$

$$
A = 2^h = 2^8 = 256
$$

$$
U = A - 2 = 254
$$

Here $w$ is address width, $p$ the prefix length, $h$ the host-bit count, $A$ the total address count, and $U$ the conventional assignable host count. The subtraction reserves the network and broadcast addresses in this ordinary broadcast-subnet model. A cloud provider may reserve more addresses, so 254 is not a verified provider allocation limit.

The mask contains 24 one-bits followed by eight zero-bits. Each full eight-bit octet of ones represents 255, so the first three octets preserve the network portion and the last octet identifies the host portion. Treating an IPv4 address as four octets makes the range easier to inspect, while the prefix calculation operates on its complete 32-bit representation. The network and broadcast values are boundary addresses rather than additional host assignments. Provider reservations must be applied after this conventional range is understood.

Applying bitwise AND to an address and its mask identifies its network prefix:

```math
n = x \mathbin{\&} M
```

For example, `172.31.0.10` masked with `/24` produces `172.31.0.0`. Matching prefixes support an on-link addressing decision but do not prove shared VPC attachment or permitted communication. Moving endpoints out of the VPC also leaves the subnet’s arithmetic unchanged; address capacity says nothing about indexing throughput or isolation quality.

## Collect and retain evidence with the investigation in mind

Elasticsearch stores structured documents, with indexes organizing them and field mappings determining how timestamps, text, addresses, and other values are interpreted. Kibana supplies exploration and management applications. Logstash can process event streams between collection and storage. A collector must first obtain the endpoint observation before any of those services can make it useful.

Specialized Beats illustrate the available collection roles: Filebeat handles logs and journals, Metricbeat gathers measurements, Packetbeat observes network traffic, Winlogbeat reads Windows event logs, Auditbeat supplies audit-related observations, and Heartbeat performs availability checks. These roles depend on configuration: reading a file does not guarantee correct parsing, network observations do not mean every packet is retained, and an availability result applies to the check performed.

Elastic Agent provides a unified installation and configuration approach for multiple supported capabilities. Integrations determine enabled sources and functions. Platform support, privileges, output configuration, and version compatibility still determine whether a collection requirement is satisfied. Evaluate Agent integrations and existing Beats deployments against the actual evidence needed.

### Choose where processing occurs

The principal lab path sends events directly to Elasticsearch. A prepared Logstash pipeline can instead receive records, transform them, and send them onward through its input, filter, and output stages. Filters may parse, enrich, normalize, clone, retain, or discard records. Merely changing an agent’s output does not create a working Logstash listener, configure its pipeline, or establish Transport Layer Security (TLS) trust.

Parsing extracts values from a record’s structure. Normalization assigns consistent names and types to equivalent meanings. For example, `source.ip` has a defined meaning and IP type in Elastic Common Schema (ECS); renaming arbitrary text does not establish that it is a valid sender address. Define how malformed or unmatched records are handled, and avoid reparsing rendered messages when structured Windows fields already provide the required values.

Retention choices determine which questions remain answerable. Windows Security-Auditing event 24 records a successful logon, while 25 records a failed logon. Their channel is the Windows Security log and their provider is `Microsoft-Windows-Security-Auditing`; channel and provider are different concepts. A pipeline that keeps only 24 removes the failures that may explain a later success unless those failures are retained elsewhere.

A simple payload estimate helps connect retention choices to volume:

$$
V \approx \lambda r s T
$$

Here $\lambda$ is the incoming rate in events per second, $r$ the retained fraction, $s$ the average retained event size in bytes, and $T$ the interval in seconds. At 100 incoming events per second, 20% retention, and 1,000 bytes per retained event, one day produces an estimated 1.728 decimal GB of retained payload. Actual Elasticsearch disk consumption also includes indexing structures, replicas, metadata, compression, and other overhead. Filtering downstream leaves upstream collection and transport work in place; an 80% reduction in indexed occurrences does not establish an 80% reduction in total cost.

For example, retaining 2,000 of 10,000 relevant Windows Security-Auditing occurrences leaves 20% of that population. The percentage counts occurrences, not useful investigative context. It also assumes that their event-code fields were extracted correctly. A parsing failure needs its own handling rather than silently becoming an ordinary nonmatch. Restricting the calculation to the intended provider matters because event-code numbers are not globally unique across every Windows source. The same distinction applies when comparing event counts before and after a pipeline change: define which population was counted and where the selection occurred.

Query-time filtering selects from retained records without deleting the alternatives. For example, an ES|QL aggregation over successful-logon records counts matching documents, rather than unique users or human sessions. Its result depends on the selected index or data stream, compatible fields, and time scope; it changes a result, not ingestion policy.

ES|QL supports piped transformations and aggregations. Kibana Query Language (KQL) provides field-oriented filtering and is distinct from Microsoft’s Kusto Query Language. Query DSL expresses structured JSON search clauses. HTTP transports requests and JSON represents data; neither independently defines search semantics. Discover exposes collected records interactively, while other applications require their own data and configuration.

Centralization makes cross-host investigation possible because the analyst can search records from different endpoints together. Flexible integrations reduce the work of connecting sources, and distributed architecture can accommodate greater demand. These benefits still depend on workload, retention, and collection quality. An apparently clean search can hide an unread source or a missing field. Centralized logging also does not independently establish compliance: access control, record integrity, retention, and operating procedures remain part of that requirement. Product comparisons can explain broad responsibilities, but do not make their components, protocols, or configurations interchangeable.

## Deploy Elasticsearch and verify its API

Provision the management VM in the selected location and attach it explicitly to the VPC. The example Elasticsearch/Kibana host has four vCPUs and 16 GB of RAM; these are exercise selections rather than measured minimums. Confirm the assigned private address using the cloud configuration and guest interface output. Neither a planned address nor a capacity calculation establishes what the operating system actually received.

Connect to the Ubuntu host over SSH, update its packages, and install the official Elasticsearch Debian package for the selected version and architecture. Use the required administrative privileges, verify the downloaded filename, and check its published SHA-512 checksum before installation. A successful download does not establish that installation succeeded. [Elasticsearch 8.15 Debian installation](https://www.elastic.co/guide/en/elasticsearch/reference/8.15/deb.html)

Keep the operating-system and application identities separate. Linux `root` administers the VM, the Linux `elasticsearch` account runs the service, and the built-in `elastic` user authenticates to Elasticsearch. The application password is not the root password. Likewise, accepting an SSH host key concerns the SSH server’s identity rather than the Elasticsearch API.

### Inspect effective listeners and generated security

For the Debian package, configuration normally resides in `/etc/elasticsearch`, tools in `/usr/share/elasticsearch/bin`, and logs in `/var/log/elasticsearch`. Inspect the guest’s addresses with `ip a` before choosing a bind address. A cloud console’s public address may be translated externally and unavailable on the local interface.

Choose a local bind address that supports the intended client connections and explicitly configure the HTTP API port, shown as `9200` in this lab. Integrate these choices with the existing configuration rather than replacing generated security settings. Binding determines which local interfaces accept traffic; publishing advertises an address for other components. More specific `http.*` or `transport.*` settings can override shared network settings.

The HTTP API and inter-node transport are separate interfaces. Their documented default port ranges are `9200–9300` and `9300–9400`, respectively; these defaults do not require exposing every port in either range. Check the effective listener before testing a client connection.

On the supported first-install path, security auto-configuration generates authentication and TLS settings. In Elastic it can set `http.host: 0.0.0.0` while transport initially remains local. Inspect what was generated before assuming the API is restricted to localhost or that `network.host` alone determines the effective listener. Existing settings can also change whether auto-configuration occurs. [Automatic stack security configuration](https://www.elastic.co/guide/en/elasticsearch/reference/8.15/configuring-stack-security.html)

Invalid YAML, duplicate entries, and unavailable bind addresses can prevent startup. Non-local transport binding can trigger mandatory bootstrap checks. Use the logs to identify the failure. Choose interfaces that support the intended connections: binding only to a public interface can break a Fleet Server connection targeting the private address.

A leading `#` comments out a YAML setting, so an example line has no effect until it becomes active. Removing a comment marker is not sufficient if another more specific setting overrides it. Preserve the existing TLS and authentication configuration when changing network settings, and use the error output to distinguish syntax, binding, and bootstrap failures. Reinstalling the package does not explain which of those conditions prevented startup. After static configuration changes, verify the restarted process and its effective access path rather than assuming a successful edit changed the running application.

Use systemd to start Elasticsearch, enable boot-time activation, and inspect its status. Reload unit definitions when those definitions change; static Elasticsearch YAML changes require restarting the application. A running service does not prove that a remote client can reach and use its API.

Attach the intended cloud firewall group to the VM and authorize the actual service flows. An SSH-only rule preserves administration while still blocking API traffic. A rule for the analyst’s address does not authorize Fleet Server or endpoint outputs; those clients need their own permitted paths.

### Authenticate to the secured API

If the application password needs resetting, use the Elasticsearch password-reset tool for the `elastic` user. It can generate a password or accept an interactive choice. The tool connects to the running cluster using its HTTP/HTTPS configuration and a temporary file-realm user, so it requires reachability and an enabled file realm. It is not a guaranteed offline recovery method before startup.

`ES_HOST` must be reachable and match the certificate. The certificate authority (CA) file must exist on the client running the request. `--cacert` supplies the trust anchor, while `-u elastic` allows a password prompt. A certificate establishes server trust, a password authenticates a user, and enrollment tokens bootstrap other relationships; they are not interchangeable credentials.

A valid response shows that this client reached the listener, completed the relevant TLS validation, authenticated, and received an application response. Repeat the check from the intended remote source when necessary. A timeout, a certificate error, and an authentication failure point to different parts of the path.

## Configure Kibana for durable operation

Kibana serves the browser interface and connects separately to Elasticsearch. Install an official Debian package compatible with the selected Elasticsearch release and machine architecture, then inspect `/etc/kibana/kibana.yml`.

Kibana initially listens on localhost at port `5601`. For remote browser access, configure `server.host` with a suitable address present in the guest and confirm `server.port`. The listener, routing, firewalls, and browser TLS must support the same intended connection.

Start and enable Kibana through systemd, inspect both Kibana and Elasticsearch, and allow time for application initialization. Process status helps separate a stopped backend from Kibana’s own state, but an application request must establish readiness. A browser can reach Kibana’s listener while its backend connection still prevents useful work.

### Complete enrollment and check the browser path

Generate a Kibana-scoped setup token with the enrollment-token tool on the Elasticsearch host. This requires an appropriately secured, running cluster. In the Elastic setup path, the token is valid for 30 minutes and configures Kibana’s backend connection using its service account. Generate a replacement if it expires; it is separate from both an analyst’s password and an Agent enrollment token.

For browser access, check the listener, forward and return routes, provider firewall, host firewall, selected protocol, and application readiness. A provider allow rule cannot overcome a host deny. Similarly, a cloud rule has no effect until attached to the relevant VM. Restrict the browser flow to the intended source and port rather than opening every TCP destination.

Inspect whether UFW is active, then permit the intended analyst’s verified public egress address to reach TCP `5601` and configure a matching provider rule. An analyst’s egress address can change. A successful setup screen establishes a working path at that time; diagnostics are still needed to explain earlier failures.

Retrieve the instance-specific setup verification code with Kibana’s verification-code tool on the Kibana host. It confirms access during setup and is not a reusable login credential. The initial lab login uses `elastic`, but routine analyst accounts should receive privileges suited to their work. Resetting a user password does not renew a token or replace this code.

Browser-to-Kibana security and Kibana-to-Elasticsearch security are independent. Enrolling Kibana with a TLS-enabled cluster does not turn an `http://SERVER_ADDRESS:5601` browser URL into HTTPS. Configure the browser path’s TLS separately.

### Persist encryption keys before relying on alerting

Kibana stores saved objects such as dashboards, alerts, and connectors in Elasticsearch. Sensitive properties, including connector credentials, require stable encryption configuration. `xpack.encryptedSavedObjects.encryptionKey` protects sensitive saved-object properties; `xpack.reporting.encryptionKey` protects reporting-job information; and `xpack.security.encryptionKey` protects session information. Losing stable keys can block features, make existing properties unreadable, fail pending reports, or invalidate sessions. [Saved-object encryption](https://www.elastic.co/docs/deploy-manage/security/secure-saved-objects)

The configured strings must meet the documented length requirements of at least 32 characters. That is a length condition, not a claim of 32 bits of security; use appropriate random values. API keys, TLS certificates, and saved-object encryption keys have different purposes.

Each `add` command prompts for the corresponding generated value. Enter the value rather than the complete YAML line. Use the account and configuration context expected by the Kibana service; the Debian directory is normally `/etc/kibana`, while `KBN_PATH_CONF` can change it. Create a keystore if absent and preserve an existing one.

Verify the stored setting names in that same context without displaying secret values, restart Kibana, and inspect its logs. Revisit alerting and confirm that the missing-key condition has cleared. Stable keys preserve operation across restarts; the keystore does not recover lost keys. Planned rotation may require retaining old decryption keys for existing objects.

## Prepare the Windows endpoint and Agent policies

Verify operating-system readiness independently of the provider’s VM status: a running instance can still be completing deployment.

The provider console and RDP also prove different things. The console reaches the screen through the cloud management interface, while RDP depends on the guest’s network stack, listener, filtering, credentials, and account rights. One successful Remote Desktop connection establishes access for that client at that time. Network Level Authentication (NLA) authenticates before a full desktop session and can affect the context of observed authentication events.

An incoming connection, an authentication failure, a local audit event, and an indexed document remain distinct observations. A scan that never reaches authentication need not produce the same records as a logon attempt. Event 25 must be read with its account, failure details, logon context, and surrounding events; audit settings and authentication paths affect what is recorded.

Use known, authorized test logons instead of depending on an assumed arrival time for Internet traffic. Confirm the expected local record, then follow it through collection, output, indexing, and the analyst’s search. This gives later detection tests a known input and prevents missing evidence from being mistaken for a quiet endpoint.

Elastic Agent ties that collection to configuration. An input identifies a source and how to read it; an integration packages source-specific settings and supporting assets; an output defines delivery and authentication. An agent policy groups settings and can contain multiple integration policies. Each agent enrolls in one policy, allowing similarly tasked hosts to share desired configuration.

Standalone mode maintains local configuration, potentially distributed through configuration-management tools. Fleet-managed mode centralizes management through Fleet Server and is used here. Fleet Server itself runs under an Agent configured for that role; its dedicated VM is a deployment choice. Its credentials differ from Kibana setup tokens, endpoint enrollment tokens, and browser logins.

A policy change passes from Fleet’s interface into Elasticsearch, through Fleet Server to connected agents, and into their applied configuration. The inputs then independently send records to the selected output. An offline agent cannot immediately apply a change, while a healthy management status does not establish that a specific event channel is readable or indexing successfully.

Separate the policy responsibilities when diagnosing a change. Adding a Windows event source changes integration settings. Redirecting supported telemetry to an existing Logstash input changes output settings. Enabling the agent’s own logs changes self-monitoring settings. Delivery of the policy can succeed while one of those functions fails. The desired settings and observed outcome must therefore be compared at the relevant component, whether that is a readable channel, a working output, or the agent’s own monitoring records.

Policy edits, integration updates, binary upgrades, and unenrollment have different effects. Unenrollment does not itself uninstall every component or delete indexed records. Upgrade and output options depend on installation method, compatibility, privileges, artifact access, and applicable features. Check sequencing across Elasticsearch, Kibana, Fleet Server, Agent, and integrations before changing them.

For the first collection test, verify the local event, the selected input and its permissions, management and output connectivity, the expected Elasticsearch destination, and the timestamp and parsed fields in Discover. If a rule and ticket are expected, test those as additional stages. That sequence establishes what each observation actually proves and gives a specific place to investigate when evidence is missing.

## Establish endpoint visibility with Fleet and Sysmon

Endpoint monitoring becomes useful when an analyst can connect a system action to a searchable record. Fleet establishes centralized management, Sysmon adds detailed Windows activity, and Elastic Agent carries configured records to their output. Each component answers a different question: whether a host received its policy, whether it generated an event, and whether that event reached Elasticsearch with the fields needed for investigation.

Fleet Server communicates with enrolled Elastic Agents and exchanges policy and agent-state information with Elasticsearch. In this lab, agents initiate HTTPS connections to Fleet Server on port `8220` for enrollment, check-ins, policy delivery, and actions. Their collected records travel separately to Elasticsearch over HTTPS `9200`. Fleet Server also needs its own connection to Elasticsearch, while analysts use Kibana through its configured listener, shown as `5601`.

These destinations must remain distinct in configuration and troubleshooting. Fleet Server does not automatically relay every endpoint event. An enrolled Windows agent may therefore remain online while its direct Elasticsearch output fails. Adding richer telemetry before verifying both connections can produce a healthy management screen and an empty investigation.

### Configure the Fleet Server destination and trust

Provision Fleet Server on a dedicated Ubuntu VM, attach it to the intended network, and create its policy and service token through Fleet in Kibana. The advertised address must be reachable from enrolled endpoints, including endpoints outside the private management network.

<details><summary>A compatible Elastic Agent archive must already be downloaded and extracted before invoking its installer:</summary>

```bash
# Install and enroll Elastic Agent as Fleet Server
sudo ./elastic-agent install \
  --url='https://FLEET_SERVER_HOST:8220' \
  --fleet-server-es='https://ES_HOST:9200' \
  --fleet-server-service-token='FLEET_SERVER_SERVICE_TOKEN' \
  --fleet-server-policy='FLEET_SERVER_POLICY_ID' \
  --fleet-server-es-ca-trusted-fingerprint='ES_CA_FINGERPRINT' \
  --fleet-server-port=8220
```

</details>

Replace the hostnames, service token, policy identifier, and CA fingerprint with values from the intended deployment before execution. Verify that the Fleet Server address is reachable from endpoints and that the Elasticsearch address is reachable from Fleet Server.

The `--url` option identifies Fleet Server's advertised endpoint. The `--fleet-server-es` option identifies Elasticsearch. Fleet Server's service token authenticates its Elasticsearch access; it is not the enrollment token later used by endpoint agents. The CA fingerprint provides trust information for the Elasticsearch connection. Correct values must describe the same deployment.

A connection requires a usable route, matching listeners, permission through provider and host firewalls, and a successful TLS exchange. Application authentication and readiness add further requirements. In the demonstrated failure, Elasticsearch initially permitted the analyst's workstation but excluded Fleet Server. Later, the Windows endpoint needed its own permitted output connection. Authorizing one source does not authorize another simply because both participate in Fleet.

Apply rules on the hosts supplying the relevant service: Elasticsearch receives `9200`, and Fleet Server receives `8220`. A broad destination-port allow rule does not restrict sources. Provider and host rules must express the actual permitted sources and destinations.

Keep the configured port consistent with the listener. A Fleet URL using `443` cannot reach a service listening only on `8220` unless a suitable proxy or forwarding arrangement connects them. Opening another firewall port does not move the application listener. A timeout suggests investigation of routing, filtering, and other delivery conditions; a refusal can indicate an absent listener, a wrong port, or explicit rejection. Neither symptom identifies a particular firewall by itself.

Once the connection reaches Fleet Server, certificate errors become a separate problem. TLS verification checks that the server's certificate chains to trusted material, is valid for the applicable dates, and matches the requested identity, along with other requirements. A private CA or self-signed certificate can be used when its trust material is deliberately configured. Merely reaching an HTTPS port does not establish authenticated TLS.

Enroll the Windows endpoint from an elevated shell in the directory containing its extracted Elastic Agent executable. Select the reachable Fleet Server URL and an enrollment token belonging to the intended endpoint policy. Configure certificate trust for that URL.

The demonstrated enrollment used `--insecure`. With HTTPS, this retains transport encryption while disabling verification of the server’s identity. It does not repair routing, change a listener, or validate an incorrect token. Treat trust configuration as a separate requirement from connectivity and enrollment credentials.

After enrollment, establish two baselines: a Fleet check-in and an indexed endpoint event. Finding a Windows Security event `25` in Discover demonstrates delivery of a failed-logon record. It provides evidence beyond the agent's management status, while remaining a test of that record's collection path rather than every integration on the host.

### Capture process instances and their relationships

Sysmon is a Microsoft Sysinternals service and device driver that records selected system activity in Windows Event Log. Its channel is `Microsoft-Windows-Sysmon/Operational`. Process-creation records can contain executable paths, command lines, parent information, and configured hashes. Other event types record network connections, image or driver loads, process access, and DNS queries. Sysmon supplies observations; installing it does not classify activity as malicious or prevent it. [Microsoft Sysmon documentation](https://learn.microsoft.com/en-us/sysinternals/downloads/sysmon)

Process identity is central to using these observations. Windows can reuse a process ID after termination. A search for PID `4096` across a long interval can therefore combine a command shell with an unrelated service that later received the same number. Sysmon's `ProcessGuid` provides an identifier for correlating a particular process instance, while `ParentProcessGuid` supports reconstruction of its ancestry.

Build the process history around instances, their recorded parents, and their lifetimes. Use the host identity and timestamps alongside the GUID and confirm how collection pipelines map those identifiers. A child can retain its parent's identifier even when the parent's own creation record was not collected. Missing parent telemetry therefore limits the reconstructed history without proving that the child had no parent.

The relationship can be expressed as a directed edge between parent process $u$ and child process $v$:

$$
u \xrightarrow{\text{spawn}} v \iff \text{ParentProcessGuid}(v) = \gamma_u
$$

Here $\gamma_u$ is the parent's recorded process GUID. The edge represents the reported parent-child relationship; it does not establish malicious intent or recover missing events. Hashes and command lines attached to each process instance add the content needed to interpret that relationship. Reliable time ordering and retained records remain prerequisites for reconstructing execution across multiple events.

Select event types according to the questions the investigation must answer. Event `1` records process creation and can explain what executed, with which command line and parent. Event `3` associates a process with a network connection. Event `6` records driver loading, while event `7` records image loading into a process. Event `8` records creation of a remote thread, event `10` records process access, and event `22` records DNS queries.

Network-connection and image-load logging require deliberate configuration and are disabled in the documented default behavior. Broad image-load collection can generate substantial volume. An installed service therefore does not imply that every event type needed for an investigation is enabled.

These events can support hypotheses about injection, credential access, or command-and-control communication, but they need context. A remote thread is not automatically malicious. Access to `lsass.exe` does not independently prove credential theft: legitimate security software can produce overlapping behavior. Consider ancestry, access rights, command lines, hashes, and subsequent activity before classifying the event.

<details><summary>The following Event Query Language sequence connects execution in a temporary directory to a subsequent network event:</summary>

```eql
/* Correlate Process Creation (Event 1) with subsequent Network Connection (Event 3) */
sequence by process.entity_id with maxspan=1m
  [process where event.code == "1" and process.executable : "*\\Temp\\*"]
  [network where event.code == "3" and destination.port != 80 and destination.port != 443]
```

</details>

The sequence requires matching `process.entity_id` values within one minute. Its exclusion of destination ports `80` and `443` narrows coverage; suspicious communication can use either port. It also assumes appropriate event categories and normalized fields. A custom channel collector does not necessarily populate `process.entity_id` and `process.executable` correctly, so inspect indexed records before relying on the sequence.

Access-mask filters need similar care. A text condition that searches for `0x10` does not evaluate whether the numeric `PROCESS_VM_READ` bit, valued at `0x0010`, is present in a mask. An apparently plausible substring filter can therefore miss intended access or match unintended values. Validate mask conditions against the complete Sysmon configuration and real events.

DNS event `22` adds another investigative feature: the character distribution of a queried label. Its empirical entropy is:

$$
H(D) = - \sum_{i=1}^{k} P(c_i) \log_2 P(c_i)
$$

For a label of length $n$, each observed character's frequency is:

$$
P(c_i) = \frac{\text{Count}(c_i)}{n}
$$

Here $D$ is the analyzed string, $k$ counts its distinct observed characters, and the entropy is measured in bits per character. Specify which normalized label is being measured before comparing values. High entropy and unusual length can support investigation of domain generation algorithms, especially alongside process and network records. Benign service names can also have high entropy, and some DGAs generate readable words. Neither the formula nor an arbitrary threshold establishes a validated detector.

### Install, update, and verify Sysmon

Download Sysmon from Microsoft, extract the appropriate executable, and choose an XML configuration compatible with that binary. The `sysmon-modular` project provides modules that can be selected and maintained for an environment. Review the chosen configuration and supported schema before deployment.

Accepting the EULA completes the interactive installation step. Then inspect Windows Services, locate the Sysmon Operational channel, and examine recent records. A running service establishes one aspect of installation; a populated event channel establishes another. For a configuration intended to collect network connections, a recent local event `3` is a more useful verification than the service status alone.

The `-i` switch installs the service and driver with the selected configuration. Use `-c` with a file to update configuration, or without one to inspect the current configuration. The `-s` switch displays the supported schema. Configuration updates do not require repeating installation.

After a change, inspect the effective configuration and test both expected inclusions and expected exclusions. Inclusion and exclusion rules decide which observations remain available later. Exclusion matches take precedence in the simplified include-and-exclude case, but exclusion-only rules, empty filters, and combinations have their own documented semantics. A generic Boolean expression is not a substitute for checking the complete configuration.

Individual filter conditions can evaluate equality, a substring, or a prefix; those operations do not have the same meaning. Include and exclude populations can overlap, which makes precedence important. Validate the events the rules actually retain rather than inferring coverage from the number of configured rules.

Filtering high-volume activity can reduce collection and indexing demands, but it also removes evidence. Choose rules around the behavior the lab needs to investigate and verify the resulting records. An installation or update command can fail; intended transitions become established outcomes only after service state and actual event production have been checked.

### Deliver Windows channels through Elastic Agent

Sysmon initially produces local records. To collect them, add a Custom Windows Event Log integration to the Windows agent policy and specify `Microsoft-Windows-Sysmon/Operational`. Add a separate input for `Microsoft-Windows-Windows Defender/Operational` where those observations are required. Obtain channel names from the host's registered logs rather than inferring them from a display label.

Channel collection and specialized normalization remain separate concerns. The custom package can read user-defined channels, but it does not guarantee every security field required by a particular rule. Check the actual documents and rendered agent configuration before assuming raw Sysmon fields have become normalized ECS fields. Elastic distinguishes custom channel collection from integrations with specialized pipelines.

Defender filtering also depends on the correct event identifiers. Event **5001** records real-time protection being disabled. Event `1116` reports malware or potentially unwanted software detection, and `1117` reports a protection action. A selected list of `1116, 1117, 5001` can cover those observations, subject to verification on the monitored host.

Do not infer a fixed reduction percentage from an event-ID list. Savings depend on the observed population and filtering location. Health and informational events may also matter for availability checks or incident reconstruction. An inclusion-only list already removes IDs outside it, so separately excluding those same absent IDs adds no selectivity.

For a nonempty channel population $\Omega_{\text{channel}}$, let $\Psi(e)$ be one when event occurrence $e$ is retained and zero otherwise. The removed fraction is:

$$
\rho = 1 - \frac{\sum_{e \in \Omega_{\text{channel}}} \Psi(e)}{|\Omega_{\text{channel}}|}
$$

This measures the proportion of occurrences discarded from the defined population. It does not assign an evidential value to each event, and it supplies no percentage until counts have been observed. Filtering before transmission can reduce output traffic as well as indexing work. A query that merely hides records in Discover changes the displayed result without producing the same reduction in retained evidence.

When Fleet reports an online agent but expected metrics or records are missing, examine both monitoring and output delivery. In the demonstrated case, Elasticsearch allowed Fleet Server but blocked the Windows endpoint's direct connection. Missing CPU or memory metrics were a clue, not a unique diagnosis. Collection settings, TLS, credentials, permissions, indexing errors, and the search window can produce overlapping symptoms. Visible metrics likewise do not prove that every security input works.

After repairing a network or configuration problem, restarting Elastic Agent can re-establish connections, but it interrupts collection and does not guarantee that every buffered record was durably flushed. Confirm service state, then generate an expected event and find its indexed document to establish output recovery.

For a Sysmon process-creation test, constrain Discover to the intended host, interval, channel `Microsoft-Windows-Sysmon/Operational`, and event ID `1`. Inspect the returned document’s endpoint fields and mappings.

Inspect the actual dataset rather than assuming `windows.forwarded` applies to every custom channel input. A `default` namespace alone can match unrelated records. Discover's time picker can also hide a valid test: a last-15-minutes search will miss an event generated earlier. Widen the interval to include the known activity, check its timestamp and endpoint, and inspect its fields. That result establishes delivery of a particular observation with specific mappings.

## Interpret the password attacks behind authentication records

Authentication analysis depends on understanding how attempts were generated. Simple brute force enumerates candidate strings. A dictionary attack prioritizes common, leaked, or predictably modified passwords. Credential stuffing replays username-password pairs obtained from other breaches and succeeds when those credentials were reused.

A complex password can still be replayed if the same secret was exposed elsewhere. Unique passwords address that cross-service reuse path, while length and unpredictability reduce the usefulness of guessing. These controls affect different mechanisms and should not be treated as interchangeable.

For an alphabet $\Sigma$ and fixed password length $L$, the theoretical candidate count is:

$$
|\mathcal{K}| = |\Sigma|^L = \left( \sum_{i \in \{\text{lower, upper, digit, special}\}} |\Sigma_i| \right)^L
$$

The sum assumes disjoint character classes. A three-digit lock has 1,000 possible strings. Eight characters drawn from uppercase letters, lowercase letters, and digits produce $62^8$, approximately $2.18 \times 10^{14}$ possibilities. Permitting several lengths requires counting each allowed length as well.

These are counts of strings, not estimates of how evenly humans choose them. A familiar sentence or predictable modification of a common password can appear early in a dictionary even when the nominal alphabet is large. The search model must distinguish uniform random selection from biased human choices.

If a secret is uniform over the candidate space and candidates are tried without repetition, the expected number of attempts is:

$$
\mathbb{E}[\text{Attempts}] = \frac{|\mathcal{K}| + 1}{2} \approx \frac{|\mathcal{K}|}{2}
$$

At constant rate $R$ attempts per second, the approximate expected discovery time is:

$$
T_{\text{exhaust}} = \frac{|\mathcal{K}|}{2 \cdot R}
$$

Despite the symbol's name, this expression estimates discovery time under the stated assumptions, rather than worst-case exhaustion of every candidate. At a hypothetical 50 online attempts per second, the eight-character example takes about 69,127 years on average. At a hypothetical offline rate of $10^{10}$ candidates per second, the same calculation gives 10,900 seconds, approximately 3.03 hours. Neither rate is a general benchmark.

Online attempts encounter a live service, network limits, throttling, and lockouts. Offline recovery operates on a locally available verifier representation and depends on the hash algorithm, parameters, and hardware. A costly password-hashing scheme changes the offline rate substantially, while a dictionary may find a common password much sooner than uniform exhaustive search predicts.

This distinction determines what the defender can observe. An authorized online dictionary test with Hydra sends requests to the verified lab SSH endpoint and can generate failed-password records. Its concurrency settings affect how requests are issued, while service responses and logging determine the evidence available. They do not establish a guaranteed request rate.

An offline NTLM recovery exercise with Hashcat instead evaluates locally supplied hashes against a wordlist and mutation rules. It sends no corresponding SSH requests. Its result depends on candidate coverage, the verifier, and hardware; dictionary transformations do not make it uniform enumeration of the theoretical keyspace.

Multifactor authentication (MFA) reduces dependence on the password, but the factors’ properties matter. A password combined with a time-based one-time password (TOTP) adds a possession factor; a locally generated code is not necessarily an out-of-band channel. The joint probability of compromise depends on how the factors can fail together. Phishing, endpoint compromise, recovery processes, and session theft can undermine assumptions that their risks are independent.

The protection from another factor depends on whether it can fail alongside the password. A near-zero compromise probability does not follow from merely enabling MFA. This distinction matters when a successful authentication follows many failures: another factor can change the attack's requirements, but its presence does not decide whether the observed session was legitimate.

The National Institute of Standards and Technology (NIST) distinguishes ordinary one-time password (OTP) authentication from phishing-resistant cryptographic authentication and restricts public telephone-network delivery in its applicable guidance. An authenticator app is not automatically phishing-resistant. For password-only authentication, NIST SP 800-63B-4 specifies a minimum of 15 characters within its scope. Long unique passwords, password managers, appropriate additional factors, and restricted administrative access address complementary parts of the problem.

### Read and count Linux authentication evidence

On the demonstrated Ubuntu logging configuration, SSH and related authentication records appear in `/var/log/auth.log`. Other distributions or images can use another file or the system journal. Confirm the actual logging setup before interpreting an absent file as absent activity. SSH, PAM, and related services contribute records, but this location should not be assumed to contain every application's authentication events.

Messages can distinguish failed passwords, invalid users, and connections closed during authentication. Preserve original lines when extracting values: their wording supplies context that a list of addresses loses. A recorded source address identifies an apparent network origin, not necessarily a person or organization.

Build a counting workflow incrementally: inspect failure messages, select the intended account, extract source addresses, group identical values, and order the counts. Check each intermediate result against original lines before interpreting a frequency list.

Avoid relying on a fixed space-delimited field number. Adjacent spaces, timestamp formats, and invalid-user messages can shift values, while a substring match for an account can admit unrelated text. Use a parser suited to the actual message structure and preserve the originals.

The resulting totals count records under those selection and parsing assumptions, rather than unique attackers, sessions, or every authentication attempt. Follow newly appended messages for live observation, and review rotated or compressed logs separately when reconstructing an earlier interval.

The lab observed unsolicited attempts after leaving SSH exposed for roughly 30 minutes, but that delay is not a predictable arrival schedule. It does not establish a measured background rate or guarantee a failure within another half-hour. A scan is also different from an authentication attempt. Controlled attempts against an isolated authorized host provide a more definite event for collection verification.

Restrict administrative access to intended paths, use appropriately managed SSH keys, and remove unnecessary root or password-login exposure according to the access design. Changing a port can alter observed traffic but does not replace authentication or access restrictions. The investigative objective remains a traceable connection between a known action, its local record, and the indexed evidence used to assess it.

## Turn authentication records into focused detections

Authentication detection starts with a defined population: the host, account, source address, outcome, and interval under investigation. Repeated failures can identify sustained guessing, while a subsequent success changes the question from attempted access to access that actually occurred. Collection, parsing, and rule scope must support that distinction before an alert becomes useful.

### Collect Linux authentication records consistently

On typical Debian-family systems with file-based authentication logging, the relevant path is `/var/log/auth.log`. A typical Red Hat-family setup uses `/var/log/secure`. Including both paths in a shared Linux policy can cover hosts using either convention, but distribution identity is only a starting point. A machine can use the system journal, different syslog routing, or permissions that prevent the collector from reading its logs. Inspect the actual source and effective policy. The Elastic System integration supports authentication collection through files and journald, depending on its configuration and package version.

Including an alternative path does not create a missing file, and a journal-only source needs an appropriate input. A common policy reduces repeated configuration work only when its inputs match the hosts. This matters when a healthy agent appears to collect nothing: management status does not establish that the expected authentication source exists or is readable.

OpenSSH can use Pluggable Authentication Modules (PAM). A PAM failure message may contain `rhost` for the remote address, `user` for the attempted identity, and `tty` for the terminal context. These values support manual triage; automated rules should use confirmed parsed fields where available. Different authentication methods and failure stages need not produce identical messages.

Create a Linux policy in Fleet and select it when enrolling the endpoint. The agent needs working management connectivity to Fleet Server and a separate working connection to its telemetry output. An `x509: certificate signed by unknown authority` error points to certificate trust, rather than proving that the network route is broken. With an HTTPS destination, the enrollment option `--insecure` leaves transport encryption in place while disabling server-certificate verification. Configure suitable CA trust and a certificate name matching the URL when authenticated TLS is required. The Elastic Agent command reference explains those options.

Download and extract a compatible Linux Elastic Agent archive, then enroll it against the verified Fleet Server destination using the intended Linux policy’s token. Match the release and architecture consistently across the package and extracted directory. The package, destination, token, and certificate trust each need independent verification.

The policy determines which authentication inputs the installed agent runs. Confirm that the intended Linux policy was selected rather than assuming any successful enrollment selected the correct collection sources. A public Fleet destination also needs an explicitly allowed network path from the monitored host; the installation command itself does not create that route or its access rules.

After enrollment, generate or identify a known authentication record and find it in Elasticsearch. This verifies a particular collection and output path. A successful check-in alone verifies the management connection.

### Ask a precise question in Discover

In Discover, select the Linux host, observed `source.ip`, and relevant authentication-failure messages within an interval containing the known event. Replace historical exercise values with the actual observations and remove unrelated Windows filters that would exclude Linux records.

Display `@timestamp`, the host or agent name, `source.ip`, and `message` together. Selecting columns changes the presentation, while all other stored fields remain available in the document. Comparing the rendered message with parsed values helps establish whether the rule can rely on the intended field names.

A result count describes matching documents within that scope. It does not automatically equal unique sessions, individual attackers, or even distinct authentication attempts: related stages of one attempt can produce multiple records. Record the query and interval alongside any count used in an investigation.

### Define SSH thresholds and their coverage

A broad search for `failed` can match unrelated activity, such as a cloud agent failing to retrieve metadata. Narrow the population to the relevant dataset and SSH outcome. Inspect sample documents before relying on these fields. A structured filter expresses the intended population clearly, but cannot recover failures that were never collected or correctly normalized.

A threshold rule counts matching records in its search interval and alerts when a configured minimum is reached. A threshold of five means **at least five**, including exactly five. The grouping fields determine which records contribute to the same count. Grouping by `source.ip` counts failures associated with each source; grouping by both `source.ip` and `user.name` evaluates each distinct source-and-account combination separately. Five failures against five usernames would not meet a five-event threshold for any one pair. [Elastic threshold rules](https://www.elastic.co/docs/solutions/security/detect-and-alert/threshold)

Choose that grouping deliberately. A source-only rule can surface one source trying many accounts. A source-and-account rule emphasizes repeated attempts against one identity. A host field may matter when several endpoints share the rule, since otherwise failures against different machines can contribute to a common bucket.

Keep the evaluation schedule separate from the lookback. A rule that runs every five minutes with one additional minute of lookback has an effective six-minute search interval. That overlap gives some late-arriving records another opportunity for evaluation, but cannot guarantee coverage of every ingestion delay.

Low thresholds can include typing errors and stale service credentials. High thresholds, short windows, and narrow source-and-user grouping can miss sparse, distributed, or slowly paced guessing. State the actual scope, grouping, timing, and exclusions so analysts understand the behavior covered by the rule.

Search successful authentication alongside failures on the same host and interval. The parsed `system.auth.ssh.event` values `Failed` and `Accepted` distinguish those outcomes when populated by the integration. `Accepted` establishes authentication success; authorization still depends on the account, source, method, timing, and subsequent activity.

A known administrator login can validate collection and establish a baseline. An unfamiliar success deserves investigation even when preceding failures stayed below the alert threshold.

## Interpret Windows logons before naming the alert

Remote Desktop Protocol (RDP) provides graphical remote access to Windows, commonly through TCP `3389`; supported configurations can also use UDP. Exposed access and compromised credentials can support initial access or movement between systems. Credential theft and ransomware are possible later developments, but an RDP connection does not establish that the entire sequence occurred. Likewise, a Sysmon process-access event alone does not prove a successful memory dump.

### Verify the effective RDP controls

Network Level Authentication (NLA), using the Credential Security Support Provider (CredSSP), requires authentication before a full remote desktop session is established. It reduces particular pre-authentication opportunities without proving that no RDP-related component processes network input before authentication.

For the legacy BlueKeep vulnerability, CVE-2019-0708, Microsoft describes NLA as a partial mitigation: valid credentials can still permit exploitation of an affected, unpatched system. Patching remains necessary. The vulnerability affected particular older Windows versions; its existence does not establish that a modern lab host is vulnerable.

Inspect the effective NLA requirement and security layer for the intended RDP listener. `UserAuthenticationRequired` and `SecurityLayer` govern different aspects of session security. Verify listener configuration, certificates, and applicable Group Policy rather than assuming that changing one listener establishes the state of all remote access.

Review effective user rights as well as group membership. Removing the built-in Administrator account from `Remote Desktop Users` does not reliably deny that account RDP access, because Administrators membership and effective logon rights can still permit it. Review the applicable Allow and Deny rights together.

A possible intrusion path begins with exposed remote access and successful authentication, then proceeds to credential access or lateral movement before impact. Incidents can skip or revisit stages; credential access is not always privilege escalation, and ransomware can arrive through other routes. These possibilities guide the search for corroborating evidence after an unexpected logon.

Restricted management paths, suitable authentication, patching, and monitored account policies address different opportunities for abuse. Changing the listener port may alter background traffic, but cannot replace those controls. Internal RDP activity also warrants attention because an authorized protocol can carry unauthorized movement.

### Distinguish logon mechanism from protocol

Windows Security event **25** records a failed logon. Relevant fields include `TargetUserName`, `IpAddress`, `IpPort`, `LogonType`, `Status`, and `SubStatus` under `winlog.event_data`, alongside `event.code`. Their availability and values depend on the event and collection path.

Logon type **2** means local interactive access; **3** means network authentication; **4** means batch execution; **5** means a service logon; **7** means workstation unlock; and **10** means RemoteInteractive access, including Remote Desktop or Terminal Services. NLA-stage RDP failures can appear as type 3, so a type-10-only investigation may miss relevant records. Type 3 also covers other network services, including SMB, and cannot identify RDP on its own. Correlate authentication context with service or network evidence.

Status codes refine the failure interpretation. `0xC000006D` indicates a general logon failure, `0xC0000064` an unknown or nonexistent account, and `0xC000006A` an incorrect password. The last code does not mean that the password must change. Repeated nonexistent-user results and repeated bad-password results against existing identities support different investigative hypotheses, but neither proves intent by itself.

Assess the spread of usernames, sources, hosts, and attempt times together. A high proportion of bad-password results can fit repeated guessing, password spraying, or benign stale credentials. A ratio of two failure classes would omit other classes and become undefined if neither occurred; it should not substitute for examining the underlying population.

### Apply the threshold to the intended entities

As with SSH, grouping by source address and target username creates independent buckets for every pair. A five-event threshold requires five matching failures within one pair's search window. The source port in `IpPort` is the reported client-side port, rather than the server's RDP listener. Grouping on an ephemeral source port can split a burst across many buckets and prevent it reaching the threshold.

Handle absent, unavailable, and loopback source values explicitly. Known scanners and service accounts can explain failures, but broad exclusions also risk hiding a compromised internal system. Tune exclusions against observed behavior and document what they remove from the rule's coverage.

When indexed results are surprising, compare them with the host’s Security log. Extract the target username from each event’s named XML fields and summarize the selected failures. Align the host, timestamps, and event population before comparing local totals with Elasticsearch; a bounded sample can differ from the incident’s complete interval.

Use the actual host or agent value consistently across searches and rules. Abbreviated and longer hostnames are not interchangeable unless the indexed data establishes that relationship. A failure search and a success search that accidentally select different endpoints cannot support a reliable conclusion about the outcome of an attempted intrusion.

## Use geographic enrichment as investigative context

GeoIP enrichment can associate an observed source address with an estimated infrastructure location. `source.ip` alone does not guarantee geographic fields. Verify that the intended ingest pipeline runs, has a suitable database, and populates fields such as `source.geo.country_iso_code` for the records under investigation.

Where geographic context is used, the event field's two-letter country code must match a compatible key in the selected country dataset. A full country name cannot join to a two-letter code merely because both describe countries. Kibana term joins combine event aggregations and geographic features through a shared key; another dataset can use another compatible key.

Keep the population consistent. A data view containing raw authentication records measures records, while an alert data view measures alerts produced under particular grouping and scheduling settings. Those counts can differ substantially. Align the host scope, outcome filter, and time window before comparing geographic distributions or successful and failed activity.

An estimated source country identifies network infrastructure, rather than an operator's nationality. Proxies, VPNs, hosting services, and compromised machines can separate an observed connection from the person controlling it. Database changes and address reassignment can also alter the geographic label. A large share of records associated with one country describes the selected observations; it does not establish state sponsorship or a universal targeting pattern.

Compare successful logons with expected administrative locations, while retaining the original address and account context. An unfamiliar country is a lead to investigate the gateway or VPN path and subsequent actions. A familiar country does not clear a suspicious login. Missing enrichment needs separate handling so that absence of a country value does not silently look like expected activity.

A concentration statistic can summarize how unevenly records are distributed, provided its population is explicit. The Herfindahl-Hirschman Index squares each country's share of the geolocated total and sums those squared shares. With positive total volume, its fractional-share form ranges from one divided by the number of included countries for an even distribution to one when all records belong to a single country. It is not automatically normalized to remove that lower bound.

In an illustrative set of 45,000 records, assigning 39,000 to one country gives that country approximately 86.7% of the total. Its squared share alone contributes about 0.751 to the index; the remaining countries add further terms. This is a lower bound on concentration, rather than an estimate of the probability that the activity came from a particular government or operator.

Missing geographic results and unequal observation intervals change what such a statistic represents. Check whether the denominator includes only successfully geolocated records, and keep that choice consistent when comparing populations. The useful finding is that observed infrastructure locations are concentrated under stated filters, rather than that a numeric threshold proves a campaign. Historical exercise totals also do not establish that RDP is universally targeted more frequently than SSH.

A country-baseline check also differs from impossible travel. The latter would require comparing logins across distance and elapsed time; simply identifying a login outside an expected country set contains neither calculation. Keep the stated conclusion proportional to the actual check.

Compare source addresses in a local Security-log sample with indexed documents from the same host and interval. Extract `IpAddress` by its XML field name and handle missing values explicitly. Inspecting raw addresses establishes the event’s content; checking the ingest pipeline establishes enrichment; an aggregation counts selected records sharing that enrichment. Keeping those questions distinct makes a geographic conclusion easier to audit.

## Extend access investigations to command and control

Command and control (C2) describes communication through which an adversary directs systems under their control. MITRE ATT&CK groups these behaviors under tactic TA0011. Such communication can support discovery, credential access, lateral movement, exfiltration, or ransomware staging, but those are separate behaviors requiring their own evidence.

Several frameworks help explain the architectural roles. Metasploit includes payloads and session handling, including Meterpreter. Cobalt Strike Beacon supports adversary simulation with configurable communications. Sliver supports several communication transports. Mythic separates payload support, communication profiles, and operational tracking. These descriptions explain roles without implying identical features across every release or payload.

### Interpret timing alongside endpoint evidence

An endpoint can initiate its outbound connection through a permitted proxy or redirector, with responses returning over that established connection. This does not require the server to open an independent inbound connection to the endpoint. Distinguish those application relationships from a verified routed topology. The proxy, TLS inspection, and redirector capabilities must actually exist in the environment; their appearance in an architectural explanation does not establish deployment or visibility. Check management access separately from the communication profile that receives endpoint traffic, since one functioning interface does not prove that the callback path works.

A polling implant can sleep, contact its server, retrieve tasks, return results, and sleep again. Other communication modes exist, so neither an open connection nor one repeated request proves maliciousness.

A simple symmetric jitter model varies a baseline sleep interval by a fractional amount. With a 60-second baseline and 50% jitter, modeled intervals range from 30 to 90 seconds. Actual frameworks can define jitter differently, and observed timings also include task duration, network delays, and missing records. Treat that range as an explanatory example, rather than a contract for every implant.

Regular connections can create a periodic signal, but real observations also contain finite sampling effects, harmonics, and legitimate scheduled activity. Randomized intervals do not imply a perfectly flat spectrum. Timing therefore becomes more useful when correlated with destination history, DNS activity, TLS metadata, and the process responsible for the connection.

An implant operating in memory can still leave observable artifacts. Absence of a dropped executable does not establish absence of process, network, or other host evidence. Correlating those sources can reveal activity that an authentication-only view misses.

### Evaluate transport and service assumptions

Frameworks can use transports or related mechanisms such as HTTPS, DNS, mutual TLS, WireGuard, and SMB named pipes. They are not equivalent concepts: mutual TLS is an authentication mode layered on TLS, and internal named-pipe communication is not automatically an Internet egress channel. MITRE Protocol Tunneling, T1572 describes tunneling behavior, rather than every use of a named pipe.

A framework supporting several options does not establish that an implant can use each one in a particular deployment. Routes, proxies, identity requirements, destination controls, and available payload profiles determine actual connectivity. Blocking probabilities for different transports also need not be independent, because those channels can share controls and infrastructure.

Mythic's server, database, communication profiles, and payload-support components have separate roles. Server-side support containers are distinct from implants executing on monitored endpoints. Container separation can help organize or isolate services, but does not establish complete failure independence. Use the selected release's installation workflow and verify service connectivity, management access, and endpoint callbacks separately.

### Understand a network signature's actual coverage

A Suricata signature can select visible HTTP requests to a particular heartbeat path and require ten matching requests per source within 60 seconds. That is a count condition, rather than a measurement of periodicity or jitter. Validate the rule’s syntax and inspection buffers against the intended Suricata version.

The HTTP content must be visible to the sensor. Ordinary encrypted HTTPS hides the URI and parameters without suitable decryption or equivalent visibility. A legitimate application can also use a heartbeat endpoint, while a configurable C2 profile can change its strings. Combine signature matches with process and destination evidence before concluding that they identify command and control.

## Test the investigation through controlled attack emulation

An authorized emulation exercise connects detection engineering with incident response. The operator follows a defined intrusion scenario, the analyst reconstructs it from telemetry, and the incident record documents ownership, decisions, and verification. Each stage should produce a specific observation: an authenticated session, a process event, a connection, an alert, or evidence that the exercise reached its objective.

The scenario uses Kali Linux, Mythic and its Apollo agent, a monitored Windows server, Sysmon, and osTicket. It begins with password guessing against an exposed Remote Desktop Protocol (RDP) service, continues through discovery and executable delivery, and ends with retrieval of a synthetic `passwords.txt` document. Use only systems and infrastructure authorized for the exercise. The published addresses and credentials are historical demonstration values, not targets or deployment settings to reuse.

The objective file makes completion testable. Populate it with synthetic material, preserve the transferred artifact, and retain the operator's task result. Creating a document does not automatically enable auditing of its reads, and a network connection alone cannot establish which document contents were transferred. Define the evidence required for success before starting the intrusion.

The exercise also provides several opportunities to interrupt the modeled path. Preventing an initial login, stopping execution, restricting a callback, or preventing document retrieval can each change its outcome. A sequence of necessary transitions explains that logic, but it is not a measured compromise probability. No transition probabilities are supplied, and an actual intrusion can branch or revisit stages. Installing one control therefore does not justify assigning a transition a probability of zero. The useful question is which required action the control demonstrably prevented under the tested conditions.

Translate the scenario into investigative questions. Authentication records should establish access attempts and successful logons. Process creation and command lines should explain discovery. File and process events should connect delivery with execution. Process-associated network observations should support communication, while transfer results and available file or network auditing should support the objective. MITRE ATT&CK provides labels for these behaviors, but an exercise phase is not necessarily the tactic assigned to its technique: password guessing can enable access while T1110.001 belongs to Credential Access.

Inbound RDP access and outbound callbacks require different network paths. RDP depends on permitted access to the server's listener. The executed agent initiates a connection to its configured destination. Stateful filtering may allow replies to that outbound connection without exposing a new unsolicited inbound listener on the endpoint, but egress controls, proxies, destination restrictions, and application checks can still prevent it. Permitting RDP does not imply that callbacks will work, and allowing common web ports does not guarantee a C2 bypass.

Mythic's browser-management interface on HTTPS port `7443` is separate from the HTTP or HTTPS listener used for payload delivery and callbacks. Treat management access, artifact delivery, and agent communication as independently configured services. An available management page does not prove that a payload listener serves the intended file or that the Windows endpoint can reach it.

### Prepare and verify the emulation services

The operator's Kali Linux VM and Mythic's Ubuntu cloud host have distinct roles. For a prebuilt local appliance, identify the VM configuration and disks before starting it, and verify its actual accounts rather than assuming a particular image's demonstration defaults. On the cloud host, Mythic separates operational state, database storage, messaging, browser access, communication profiles, and payload-support components. A server-side Apollo support container is distinct from the Apollo implant executed on Windows. Component dependencies vary with the selected release.

Follow the selected Mythic release’s repository instructions to prepare its dependencies, build the CLI when required, and start the core services. Install compatible HTTP-profile and Apollo support before building the Windows exercise artifact; starting the core alone does not supply every payload type or communication profile. [Mythic repository instructions](https://github.com/its-a-feature/Mythic)

The example host has one vCPU, 4,096 MB of RAM, and 55 GB of disk. Those selections describe a lab configuration rather than measured requirements. Resource planning must include operating-system use, the running containers, payload compilation peaks, and concurrent workloads. Assumed per-container memory footprints cannot establish a universal minimum or guarantee protection from out-of-memory failures. Observe the deployment while it performs the work the exercise actually requires.

Inspect service and container state, and compare actual port mappings with the intended access rules. A running container is not necessarily a healthy application: validate management authentication and the chosen communication profile separately. Bypassing a self-signed certificate warning permits the browser session to proceed, but does not independently verify server identity or configure the agent’s certificate trust.

### Record the access conditions and distinguish each result

The exercise deliberately weakens the Windows password policy and selects a predictable seasonal password. Its observed change from a fourteen-character minimum to five characters with complexity disabled describes the prepared system, not a universal Windows Server default. The example password, `Winter2024!`, is eleven characters long and contains several character classes. It succeeds in the demonstration because it appears in the candidate wordlist. A hypothetical exhaustive keyspace says little about the time needed to test an early dictionary entry.

The authorized exercise tests a candidate-password file against one verified RDP host. A reported credential success establishes authentication under those conditions, rather than a general guessing rate or bypass of all account controls. Preserve attempts, timestamps, source, account, and result for comparison with collected authentication records.

The later interactive RDP connection is a separate observation. Correlate it with preceding failures and successful-logon evidence; a credential-testing tool’s success message alone does not establish a complete Windows desktop session.

After access, native Windows utilities inspect identity, privileges, network configuration, accounts, and group membership. Domain queries require the corresponding domain context and may fail on a standalone server. These programs also support legitimate administration, so interpret their command lines, sequence, account, ancestry, and host context together.

### Separate delivery, execution, callback, and objective

PowerShell can evaluate downloaded script text or write an executable to disk and start it. Those paths leave different evidence. In this exercise, it writes the Apollo artifact `svchost-stevenrocks.exe` into the public Downloads directory before requesting execution. ## Reconstruct execution and communication from Sysmon

Start with the known artifact name, the affected host, and an interval containing the exercise. Inspect results in ascending event-time order while allowing for late ingestion. Three Sysmon observations provide the central chain: Event 11 records a file being created or overwritten, Event 1 records process creation, and Event 3 records a process-associated network connection. Collection depends on the configured Sysmon rules and a functioning pipeline; network events are not guaranteed simply because Sysmon is installed.

The process GUID in a file-create event belongs to the process writing the file. In this example, that writer is PowerShell. When Apollo executes, it receives a different process GUID. Apollo's process-creation event and subsequent network events can share that new identifier. Joining all three events on one GUID would therefore omit or misattribute the download stage.

Connect the file event's target path to the executed image, inspect the actual parent-child relationship, and include host and time context. Then follow the executed process's GUID into its network events. This approach distinguishes process instances despite recycled numeric PIDs and avoids assuming that every file write, launch, and connection belongs to one process.

A search restricted to one process GUID returns retained records attributed to that process instance. It does not automatically include an earlier write performed by its parent or another downloader. This distinction changes how to pivot through the evidence: inspect the writer's context to explain delivery, then switch to the executed program's identifier to explain its own activity. Matching the resulting file path supplies a relationship between those views, while the actual process-creation fields establish whether the assumed ancestry is present.

For the download-before-execution sequence, the expected order is file creation, process creation, then the process's later connection. The selected events and available timestamps must support that account. It is not a universal ordering rule for unrelated events, and missing records should remain explicit gaps rather than silently completed steps in a narrative.

### Use embedded metadata as an investigative lead

### Measure detection quality on a defined population

Precision is the fraction of detections that are truly relevant; recall is the fraction of relevant events detected. Their harmonic mean is:

$$
F_1 = 2 \cdot \frac{\text{Precision} \cdot \text{Recall}}{\text{Precision} + \text{Recall}}
$$

These quantities require a labeled population and explicit treatment of empty cases. An exact-hash detector does not inherently have low recall: its performance depends on which relevant artifacts appear in the known set. Likewise, matching Apollo metadata does not justify near-perfect precision and recall without a benchmark containing relevant malicious samples and ordinary administrative activity.

Use the exercise to evaluate specific coverage and false positives, then identify the obvious evasion boundaries. Metadata can change, paths can vary, and legitimate activity can resemble parts of the sequence. Complementary observations can improve an investigation without guaranteeing a perfect detector. Keep estimated quality separate from the fact that one known sample generated an alert.

## Give the investigation an owner and a durable record

An alert describes a detection result; a ticket organizes the work that follows. Record an owner, supporting evidence, decisions, escalation, remediation, and verification so another analyst can continue the investigation or assess why it closed. Ticket history contributes to accounting and auditing, but it does not by itself establish immutable evidence, non-repudiation, or compliance. Those assurances depend on permissions, retention, audit configuration, and operating procedures.

osTicket supplies forms, departments, routing, assignments, and service-level settings for that work. Installation leaves these features to be configured. A practical lifecycle moves a new ticket through assignment and investigation, allows escalation and return to investigation, records remediation, and closes only after verification. Reopening must remain possible when the result is incomplete. These are operational states to represent with the platform's features, not a claim that every label is a built-in status.

Resolution should say what changed and which observations support the result. Host isolation, for example, needs evidence of a completed action rather than only a ticket status. Define who can authorize closure and what remains outstanding. Keep the underlying event and alert references available even when several related observations share a ticket.

Assignment and escalation also need operational meaning. Routing a new report to a team is different from an analyst accepting responsibility. Escalation can transfer the difficult parts of an investigation to a more senior analyst without erasing the original evidence or leaving ownership ambiguous. Remediation records the change intended to address the threat; verification assesses whether that change achieved the desired result. Keeping those decisions distinct makes a handoff useful and prevents a closed label from standing in for an explanation of the response.

For a defined population of $N$ incidents, mean time to acknowledge is:

$$
\text{MTTA} = \frac{1}{N} \sum_{i=1}^N \left( \tau_{\text{ack}}(i) - \tau_{\text{created}}(i) \right)
$$

Mean time to remediate, using creation-to-resolution time here, is:

$$
\text{MTTR} = \frac{1}{N} \sum_{i=1}^N \left( \tau_{\text{resolved}}(i) - \tau_{\text{created}}(i) \right)
$$

The timestamps identify ticket creation, acknowledgment, and resolution. Define whether the clocks use elapsed time or a business calendar, how pauses are handled, and how unresolved tickets appear in reporting. Averages based only on resolved incidents can conceal a backlog. Service-level targets also need explicit severity mappings rather than assumed universal response times.

Alert-to-ticket creation is a separate integration. The osTicket API uses `X-API-Key` authentication and configured request-source restrictions. Its documented ticket API supports creation, not automatic two-way synchronization of all ticket states. A payload needs supported fields and mappings: `name` and `email` identify the submitter, `ip` describes that submitter's address, and `priority` is a configured priority ID. Put the affected host and investigation context in the message or appropriate custom fields. An `alert_id` field alone does not establish deduplication.

Aggregation should reduce duplicate work while preserving accountability. Choose a correlation key appropriate to the incident rather than treating a source IP as a complete identity or assuming every alert deserves an independent ticket. A shared incident record still needs references to its individual observations. Likewise, an Elastic severity label must map to the configured helpdesk priorities; the numeric priority ID in a sample payload does not establish that mapping for another installation.

### Deploy the helpdesk as a separate application

The Windows lab hosts osTicket with XAMPP under `C:\xampp`, using Apache, PHP, and MariaDB. Verify compatibility for the selected osTicket and PHP releases. XAMPP's defaults describe a development environment rather than a hardened production service, and browser HTTP remains unencrypted. Restricting provider access to the analyst's source address limits that route but does not complete host hardening.

Apache's effective `Listen` and host configuration determine its bindings. Editing a packaged property from `localhost` to a public address does not create a reachable listener, grant firewall access, or enable HTTPS. Verify the local application before interpreting remote connection failures.

The application request crosses several service responsibilities. Apache resolves the requested URI through its configured routing and filesystem-access rules. PHP executes the application with the loaded runtime configuration, and database queries read or update the stored state. A read-only request may leave that state unchanged, while creating or modifying a ticket changes it. This explains why a successful web response, functioning PHP extensions, and a working database connection are related but separate checks. It is not an instruction to concatenate arbitrary request text into filesystem paths.

Enable the PHP features required by the chosen release and intended functions. The example discusses `gd`, `imap`, `intl`, and `mysqli`; an uncommented directive works only when the corresponding extension can actually load. Confirm the active `php.ini`, compatible binaries and dependencies, and the effect of restarting the service. IMAP support alone does not configure email collection or replies. OPcache requires the appropriate `zend_extension` configuration rather than treating `extension=opcache` as equivalent.

Separate mandatory installation prerequisites from optional capabilities. Graphics, internationalization, database access, and mail handling serve different application functions, and the release's actual prerequisite checks determine what must be available. Inspect successful module loading rather than inferring readiness from an edited configuration line. This also prevents a runtime failure from being misdiagnosed as a network problem merely because the browser cannot complete the intended application operation.

Start the web and database services, verify local access, create the `osticket` database, and copy the release archive's `upload/` contents into `C:\xampp\htdocs\osticket\`. Prepare `include\ost-config.php` from the supplied sample with temporary installer write access. Resolve the setup page's prerequisite checks, enter the helpdesk and administrator details, and connect the database account. Use an account scoped to the application database; the official installation guide requires full privileges on that database for installation, so do not assume that four data-manipulation privileges cover installation and upgrades. After successful installation, delete `C:\xampp\htdocs\osticket\setup`.

Remove configuration write access and verify effective NTFS permissions rather than relying on a read-only file attribute. Determine the actual web-service identity and inspect its file and directory access before concluding that it cannot rewrite the configuration. The application must retain the access it needs while its configuration secrets remain protected. Finish by verifying application login, ticket creation, staff access, routing, and notifications. A completed installer provides the platform for an investigation record; it does not establish that Elastic can create a ticket successfully.

## Connect alerts to a verified ticketing path

A detection starts an investigation; a ticket gives that work an owner and preserves evidence, decisions, and handoffs. A webhook can transfer alert context into osTicket, but the rule must have an enabled action, the connector must reach the API, and the application must accept the request. An alert in Elastic establishes none of those downstream results by itself.

The example sends an HTTP POST to osTicket’s ticket-creation API. Its authentication uses an `X-API-Key` header associated with a permitted client address and ticket-creation permission. Registering the Elastic host’s private address, `172.31.0.3`, expresses which client the key permits. Selecting no built-in Basic authentication in the webhook does not make the request unauthenticated: the custom header supplies the credential.

Verify the source address osTicket actually evaluates. A proxy, address translation, or a connection to a public destination can make it differ from the VM’s private address. Registering a private source neither selects the destination route nor encrypts the request. The historical connector initially uses `http://155.138.137.117/osticket/upload/api/tickets.xml`; that public destination must be reconciled with the private-address registration. The `/osticket/upload/` portion also reflects a specific application layout rather than a universal API path.

Treat the destination, connection source, and investigated address as three separate values. The destination identifies the osTicket API. The connection source identifies the client evaluated against the registered API key. The suspected attack source belongs to the investigation context carried in the ticket. Substituting the attack address into a body field does not make the request originate there, and registering the Elastic VM’s private address does not force a connection toward the private osTicket interface. This distinction explains why a correct-looking key and payload can still fail authorization on an unexpected route.

### Test the payload before attaching a live rule

Separate application acceptance from authentication success as well. The relevant service ports in this layout are Kibana `5601`, Elasticsearch `9200`, and Fleet Server `8220`. ## Investigate authentication outcomes before closing an alert

Authentication triage can be organized around four questions: what context exists for the source, which hosts and accounts were targeted, whether authentication succeeded, and what occurred during or after access. The alert’s trigger and the incident’s outcome are different. Repeated failures may precede a successful attempt, while a successful login may belong to an authorized administrator.

### Use reputation as context for local evidence

In the historical SSH case, `194.50.201.5` has 1,816 AbuseIPDB reports and a displayed 100% abuse-confidence score. These are observations from the exercise, not current findings. Infrastructure ownership and reporting history change. A high score supplies external context about reported abuse; it is not the probability that this endpoint was compromised. Total reports also differ from the number of independent reporters.

For a fresh reputation check, query the service for the observed address and record the lookup time, requested reporting lookback, abuse-confidence score, report total, and available country context. A lookup provides external context; it does not submit an abuse report or block the address. Distinguish failed requests from genuinely empty results.

Read report totals alongside recency and the number of distinct reporting users. Repeated reports and independent reporters are different forms of context, and the lookback defines which history was requested. A displayed 100% score can summarize a reporting service’s assessment without establishing certainty about local outcomes. The same limitation applies in reverse: an unfamiliar or low-reputation address can still be responsible for important malicious activity. Reputation helps prioritize the investigation; endpoint records establish what reached the monitored host.

Avoid converting reputation and scanner classifications into unsupported certainty. In the Windows case, `81.163.20.41` has 55 reports, a displayed 48% score, and GreyNoise context about scanning. GreyNoise’s Unknown classification does not mean benign or conclusively untargeted. External scanning context and harmful activity against the monitored host can coexist.

A reputation percentage and a scanning classification are not interchangeable probabilities. Combining them into a numerical compromise likelihood requires a defined and validated model; the supplied observations do not justify a precise fused confidence score. Preserve their qualitative value and use local records to establish what the source actually did.

### Scope sources, accounts, hosts, and time

Begin with all retained activity from the suspected source, scoped to the relevant endpoint, dataset, and time range. Then inspect successful authentication within that same population. Verify the parsed fields and review an interval wider than the detection’s threshold window, since a threshold identifies one concentration of activity rather than the source’s full history. Elastic Timelines can preserve selected records and entities as an investigation workspace.

The SSH exercise finds attempts against `root` and no matching `Accepted` records in the reviewed interval. The defensible conclusion is that no successful SSH authentication from that source was observed in the available, scoped telemetry. That is narrower than declaring the host secure. Verify collection coverage, timestamp handling, and alternative access evidence before interpreting an empty search.

The Windows case examines six failed logons targeting Administrator from `81.163.20.41`. Reuse the successful remote-interactive baseline, adding that source and the relevant account, host, and interval. Event 24 with type 10 identifies a successful RemoteInteractive logon, while other authentication stages can generate other types. An empty type-10 result therefore does not prove that all authentication failed; inspect the broader successful-logon population and relevant authentication path.

Event 25 records an authentication failure; it does not establish that a network firewall blocked the connection. The attempt reached an authentication path capable of producing the record. Similarly, success plus ordinary process activity does not by itself establish unauthorized access. Account ownership, expected administration, process context, and corroborating behavior determine whether the session represents compromise.

When closing an alert, identify the actual prevention or mitigation mechanism. A high reputation score is context, not a response action. A familiar or authorized source can itself be compromised, and an unknown source can conduct important malicious activity. Record what was observed, what was searched, why the disposition follows, and what remains unresolved.

A useful disposition separates detection correctness from incident outcome. Repeated unauthorized password failures can accurately match a brute-force rule even when the reviewed evidence contains no successful authentication. Calling that detection a false positive would discard the behavior the rule correctly found. Calling it mitigated requires identifying the control or response that prevented or stopped the activity. Conversely, a successful login moves the inquiry toward account ownership and session behavior; it does not settle authorization. One account can have both failed and successful attempts, so an account-level label should not collapse their different outcomes.

## Reconstruct Windows sessions by their identifiers

An account name can appear in concurrent desktop, network, and service logons. Correlating one logon instance prevents those activities from being merged into a misleading session history. Windows logon IDs are locally unique identifiers (LUIDs), scoped to a computer between reboots. Include the host and boot context: another host or later boot can reuse the same hexadecimal value.

Replace the example host and identifier, and constrain the interval to the relevant boot context. `TargetLogonId` identifies the target session in a logon event, while `SubjectLogonId` can identify an actor performing another action. Their meaning depends on event type. Matching either field produces leads to interpret, not a guaranteed inventory of everything done through one desktop session. Events lacking those fields need process ancestry, account context, and time correlation.

The correlation therefore has two stages: select records bearing the scoped identifier, then interpret each event’s role in that session. The same hexadecimal text on a different computer is not a continuation of the investigated logon. A matching subject field may describe an action performed by that session, while a target field may describe the session receiving an operation. Preserve those meanings when assembling the timeline. Normalizing field representation can support matching, but it cannot replace host, boot, and event-type context.

Event 4672 records sensitive privileges assigned to a new logon. It does not prove that every listed privilege was exercised. Event 4634 indicates that a logon session ended; 4647 indicates user-initiated logoff. An RDP disconnect is distinct and can leave the session running, so disconnection, reconnection, and logoff must not be treated as equivalent endpoints.

### Pair lifecycle records before calculating duration

For a correctly paired logon and logoff, elapsed time is:

$$
\Delta \tau(\lambda) = \tau(e_{\text{logoff}}) - \tau(e_{\text{logon}})
$$

Here $\lambda$ identifies the scoped logon instance and $\tau$ returns an event’s timestamp. Duration helps prioritize investigation but does not identify a human attacker by itself. Automation can run for hours, and an interactive operator can act in seconds. Even a short successful session establishes that authentication worked under those conditions.

The corresponding initial host-and-time scope is:

```math
\mathcal{E}_{\text{investigate}} = \left\{ e \in \mathcal{E} \mid \tau(e) \in [\tau_{\text{start}}, \tau_{\text{end}}] \land e.\text{host} = \text{"my-df-win-ste"} \right\}
```

For the example, the bounds are `2026-11-14T18:56:55Z` and `2026-11-15T01:13:38Z`. This is a starting population, not a complete compromise boundary. Preparation can precede it, activity can spread to other hosts, and persistence or child processes can survive logoff. Widen the scope as evidence requires rather than equating session end with the end of adversary capability.

Host-side automation must also respect event schemas. A script grouping both 24 and 4634 by `Properties[3]` combines different meanings: that index is `SubjectLogonId` in the documented 24 layout and `TargetLogonId` in 4634. Extract XML fields by name for each event, then correlate the intended target logon ID with host and boot context.

Selecting the first record in an unbounded collection does not establish the correct chronological pair. Handle ordering, duplicates, missing logoffs, and reconnections before reporting a duration. Otherwise, a precise-looking result can rest on an incorrect join.

Define the interval before calculating it. A user-initiated logoff, a recorded session termination, and an RDP disconnection describe different milestones. Pairing whichever endpoint appears first can change the meaning of the reported duration. A missing logoff leaves an incomplete pair rather than demonstrating that the session ended at the last available event. Reconnection records may add further activity to interpret within the same investigation. Preserve the original timestamps and event meanings so another analyst can reproduce the calculation and distinguish an observed session duration from the wider period selected for compromise analysis on that host.

## Make the disposition match the evidence

A dependable SOC lab connects architecture, collected records, detection logic, and response results. A running service establishes process state. Enrollment establishes a management relationship. An indexed test event demonstrates a collection path. A rule match identifies configured behavior, while a ticket records the work required to determine its significance.

The investigation must then establish outcomes: whether authentication succeeded, whether access was authorized, what processes and connections followed, and what prevention or containment actually occurred. Closure should identify the reviewed hosts, accounts, addresses, time range, collection checks, reputation context, outcome searches, and response results, together with remaining uncertainty. That record makes the decision reviewable and gives the next exercise a clear basis for improvement.
