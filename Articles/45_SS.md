# Security Is a System: From Passwords and Cryptography to Networks, Applications, and Privacy

Security is often presented as a catalog of tools: strong passwords, encryption, HTTPS, firewalls, private browsing, and perhaps a VPN. That framing is convenient, but it hides the question that matters most: **where does each control begin and end?** Digital security is not a collection of magic switches. Passwords and passkeys protect identity only when recovery, phishing resistance, and authorization are sound. Hashing, encryption, and signatures protect different properties at different stages of the data lifecycle. TLS, HSTS, VPNs, firewalls, sandboxing, and updates reinforce or move trust boundaries; they do not erase them. Encoding, parameter binding, server-side authorization, CSRF tokens, and memory-safe design prevent untrusted data from becoming trusted code or control. Privacy tools follow the same rule: private mode limits local persistence, HTTPS protects content in transit, encrypted DNS shifts resolver trust, and Tor distributes network knowledge. Every defense has a boundary, and attackers succeed by finding the gaps between them.

A more useful model treats security as a connected system with five layers:

- **Identity:** how users prove who they are and how services resist credential theft.
- **Cryptography:** how systems protect data at rest, in transit, and throughout its lifecycle.
- **Networks:** how packets cross untrusted infrastructure and where trust shifts between intermediaries.
- **Applications:** how software keeps untrusted data separate from executable code and privileged state.
- **Privacy:** how browsers, servers, trackers, providers, and operating systems observe different parts of the same activity.

Those layers from a four-digit PIN to passkeys, from password hashing to post-quantum migration, from packet sniffing to defense in depth, and from browser injection to anonymous routing are not to crown one perfect security product, but to understand how the pieces reinforce one another—and what remains exposed when any one of them is used alone.

The practical habit is to ask four questions of every system: **What asset is being protected? From which observer or attacker? Across which boundary? For how long?** When those answers are explicit, controls can be composed deliberately. When they are vague, even strong technology can leave a predictable gap. Effective protection comes from preserving boundaries, minimizing unnecessary trust, and building enough independent layers that one failure does not become total compromise.

**The domains, accounts, payloads, and commands in the following snippets are hypothetical examples. They do not assert vulnerabilities in the named services, and destructive command strings must never be executed.**

## 1. Identity: Why Strong Passwords Aren’t Enough

A four-digit PIN has only 10,000 possible combinations. A random eight-character password drawn from 94 printable, non-space ASCII characters has roughly six quadrillion. Yet neither number matters if the credential was reused after a breach or entered into a convincing phishing site. Password math matters, but authentication security depends on the entire system around the password.

### Authentication Is Not Authorization

Authentication proves who a user is. Authorization determines what that authenticated user may access. A username and password might establish that a person is Lily; the authorization system then decides whether Lily may enter a particular account, file, or administrative area.

This distinction matters because a successful authentication attack gives an adversary the victim's identity and therefore the victim's authorized access. If those privileges are broader than necessary, weak authorization design increases the damage. Secure systems must protect both stages, but authentication is where most users encounter security directly.

### Password Security Begins with Search-Space Math

A brute-force attack systematically tests possible passwords until one works. If a password contains $n$ positions and each position may contain any of $k$ symbols, the total search space is:

$$
N = k^n
$$

Here, $N$ is the number of possible passwords, $k$ is the size of the available alphabet, and $n$ is the password length. The multiplication principle gives the result: the count is $k \times k \times \cdots \times k$, with one factor for each independent position.

For a four-digit PIN, the calculation is:

$$
N_{\text{PIN}} = \underbrace{10}_{\text{digit 1}} \times \underbrace{10}_{\text{digit 2}} \times \underbrace{10}_{\text{digit 3}} \times \underbrace{10}_{\text{digit 4}} = 10^4 = 10{,}000
$$

If an attacker can test $r$ guesses per second, the worst-case time to exhaust the space is:

$$
T_{\text{crack}} \approx \frac{N}{r} = \frac{k^n}{r}
$$

For a uniformly random password, the correct value will be found after roughly $N/2$ guesses on average. The formula still captures the decisive relationship: search time falls in inverse proportion to the guessing rate but grows exponentially with password length.

#### What brute force looks like in code

<details><summary>The mechanics are not mysterious. Four nested loops enumerate every four-digit PIN:</summary>

```python
from string import digits

for i in digits:
    for j in digits:
        for k in digits:
            for l in digits:
                print(i, j, k, l)
```

</details>

Replacing the ten digits with all upper- and lowercase English letters expands the space from $10^4$ to $52^4$; adding digits and punctuation produces 94 printable, non-space ASCII choices per position.

This example is deliberately simple. Its nested-loop design has $O(k^n)$ work and merely enumerates candidates; it does not submit them to a login service or test them against password hashes. Online attacks may be constrained by rate limits and lockouts, while an offline attacker with stolen password-verification data is limited primarily by the hash design and available hardware. A practical cracker would avoid the cost of printing, use optimized compiled code, and often run massively parallel workloads on GPUs. It might also use `itertools.product(charset, repeat=n)` instead of hard-coding one loop per character. More importantly, attackers rarely begin with a perfectly uniform search. They prioritize common words, leaked passwords, keyboard patterns, dates, substitutions, and other human habits.

That is why length and randomness matter more than cosmetic complexity. A long random value creates a large search space; a predictable password can appear near the beginning of an attacker's dictionary regardless of which symbols it contains.

### A Second Factor Changes the Attack

Authentication evidence falls into three broad categories:

- **Knowledge:** something the user knows, such as a password or PIN.
- **Possession:** something the user has, such as a phone, authenticator, or hardware security key.
- **Inherence:** something the user is, represented by biometrics such as a fingerprint or face scan.

True multi-factor authentication combines evidence from different categories. Two passwords may create two steps, but both remain knowledge factors and can fail in similar ways.

Possession factors commonly use one-time passwords. A time-based OTP changes at a fixed interval, while an event-based HOTP advances when its shared counter is incremented. Separately, services may generate a login code and deliver it by SMS. Authenticator apps and hardware devices generally provide a stronger channel than text messages, because a SIM-swapping attacker may persuade a carrier to move the victim's number to another SIM and receive SMS codes instead.

An idealized model expresses the benefit of independent factors as:

$$
P(\text{attack success}) = P(\text{factor}_1 \text{ compromised}) \times P(\text{factor}_2 \text{ compromised})
$$

This multiplication applies only to the extent that the compromise events are independent. A compromised endpoint, a malicious login proxy, or a recovery process that bypasses both factors can connect the risks. Even so, requiring an attacker to obtain both a password and a separate possession or inherence factor substantially raises the cost of most account-takeover attempts.

OTP-based MFA is not the endpoint. Malware can capture a code as the user types it, and an adversary-in-the-middle phishing site can relay the password and current OTP to the legitimate service in real time. The code expires quickly, but the attacker needs it to work only once—long enough to obtain an authenticated session. Phishing-resistant hardware keys and passkeys address this problem by binding authentication to the legitimate web origin.

### Credential Reuse Turns One Breach into Many

Brute force is only one route to a password. Credential stuffing uses username-and-password pairs leaked from one service and automatically tries them against other services. It succeeds because people often reuse both their email address and password.

Credential stuffing bypasses password-strength math. A long random password is extremely difficult to guess, but if the identical value has already leaked from another site, an attacker may need only one attempt. Success depends on password reuse, a matching username, possession of the leaked credential, and whether the target detects the automated traffic. Password strength and password uniqueness are therefore separate properties, and an account needs both. From the attacker's perspective, a known matching credential can turn an exponential $O(k^n)$ search into what is conceptually an $O(1)$ attempt against that one account, although a campaign's total work still grows with the number of credentials and targets.

Rate limiting and lockouts can slow repeated guesses against one user, but distributed stuffing campaigns rotate across accounts, IP addresses, and credential pairs. Defenders therefore combine rate controls with breached-password screening, bot detection, MFA, anomaly detection, and user notifications. For individuals, the essential defense is to use a unique password for every service—something that is realistic only with a password manager or a passwordless credential.

### The Human Layer: Social Engineering and Phishing

Some attacks ignore password math entirely. Social engineering manipulates trust, authority, urgency, familiarity, and social pressure until a person voluntarily reveals information or performs an unsafe action. Publicly available information—often called open-source intelligence, or OSINT—makes the deception more convincing. A pet's name, employer, colleague, recent purchase, or travel plan may help an attacker answer a security question or construct a believable pretext.

The attack becomes more effective when perceived legitimacy, available personal context, and a target's willingness to comply reinforce one another. A strong password provides no protection if its owner hands it to someone impersonating technical support.

Phishing operationalizes the same psychological pressure through email, messages, and cloned websites. An attacker may register a look-alike domain such as `paypa1.com`, replace letters with visually similar Unicode characters, or hide the destination behind a redirect. Spear phishing adds personal context gathered through OSINT. A more advanced adversary-in-the-middle site acts as a live reverse proxy, relaying credentials and one-time codes to the real service and stealing the resulting session.

A conventional phishing attack succeeds through a sequence of stages: the message is opened, the link is clicked, and credentials are entered. An attacker tries to maximize each stage by making the message look relevant, the link feel urgent, and the landing page look authentic. At scale, even a small final conversion rate can compromise many accounts.

```html
<!-- Adversary hosts this at paypa1.com -->
<!-- Visually identical to paypal.com login page -->

  <input type="password" name="password" placeholder="Password" />
  <button type="submit">Log In</button>
</form>
```

</details>

The visible interface can copy the legitimate site's HTML and CSS, while the form sends the victim's data elsewhere. The attacker may then redirect the browser to the real service so that the failure looks routine.

Useful habits reduce exposure: inspect the actual domain, preview link destinations, avoid logging in through unsolicited messages, and navigate to sensitive services through a trusted bookmark or manually entered address. These checks are imperfect—look-alike domains and small screens make visual inspection difficult—but they introduce friction into the attack. Password managers add a technical check by associating a credential with its legitimate domain and declining to fill it on an unrelated origin. Passkeys make that origin relationship part of the authentication protocol itself.

### The Network Can Also Be Hostile

Internet traffic crosses intermediate routers, access points, service providers, and other infrastructure. A machine-in-the-middle attacker controls or influences part of that path, allowing passive observation or active modification of inadequately protected traffic.

Correct TLS certificate and hostname validation normally authenticate the server and protect the connection. Application-specific certificate pinning can add protection in some deployments, but it is not required for ordinary secure web browsing. An on-path attacker can expose application data when authenticated encryption is absent, defeated, or bypassed.

HTTPS uses TLS to encrypt traffic and validate the server's certificate. A properly configured client that rejects invalid certificates prevents a hostile Wi-Fi access point or router from silently reading or changing application data. The remaining danger lies in plain HTTP, faulty TLS implementations, certificate warnings that users bypass, compromised endpoints, or attacks on the trust infrastructure itself.

A VPN can protect traffic from a hostile local network by moving the encrypted tunnel's endpoint, but it also shifts trust to the VPN provider. It does not replace HTTPS or make a fraudulent destination trustworthy.

### Centralizing Trust with Single Sign-On

Single sign-on reduces password sprawl by separating the identity provider from the relying party. The identity provider—such as an organization or major platform—authenticates the user. A relying website or application accepts a signed assertion from that provider instead of collecting the user's identity-provider password.

OAuth 2.0 and OpenID Connect serve related but distinct roles. OAuth 2.0 is an authorization framework for delegated access to resources. OpenID Connect adds an identity layer and an ID Token that allows a client to authenticate the user. That token is commonly a JSON Web Token, whose three encoded components are often represented conceptually as:

$$
\text{JWT} = \text{Base64url}(\text{Header}) \cdot \text{Base64url}(\text{Payload}) \cdot \text{Base64url}(\text{Signature})
$$

The centered dots in that notation mean component separation, not multiplication; the actual compact serialization uses literal period characters. The header describes the token and signing algorithm. The payload contains claims such as the subject, issuer, audience, and expiration. The signature allows the relying party to detect forgery:

$$
Signature = Sign_{IdP\_private\_key}\left(Base64url(Header) \| {.} \| Base64url(Payload)\right)
$$

The relying party validates the signature with the provider's public key and also checks claims such as issuer, audience, nonce, and expiration. A valid signature alone does not make a token appropriate for every recipient or every session.

SSO keeps the identity-provider password away from relying parties and can eliminate the need for separate RP passwords, letting users concentrate security effort on one well-protected identity account. That benefit comes with a larger blast radius if the identity provider account is compromised. As more services depend on one identity, that identity deserves the strongest available MFA, secure recovery options, careful consent review, and close monitoring. Losing access to the identity provider can also complicate recovery across connected services, while the provider may gain visibility into which relying parties a user connects to and when authentication occurs.

### Password Managers Make Unique Secrets Practical

Humans are poorly suited to memorizing dozens of long, unrelated random strings. A password manager transfers that task to software: it generates a different high-entropy password for each service, stores those credentials in an encrypted vault, and fills them only where appropriate.

For a uniformly generated password, entropy connects directly to the search-space formula:

$$
H = n \cdot \log_2(k)
$$

Here, entropy is expressed in bits. Each character contributes $\log_2(k)$ bits when every symbol is independently and uniformly selected. For $k=94$, $\log_2(94) \approx 6.55$ bits per character, so a 20-character value drawn from the printable, non-space ASCII set has $H = 20 \times 6.55 = 131$ bits of theoretical entropy. That corresponds to $2^{131} \approx 2.7 \times 10^{39}$ possible values. The relationship to the earlier search-space equation is:

$$
N = k^n \Rightarrow \log_2(N) = n \cdot \log_2(k) = H \Rightarrow N = 2^H
$$

Human-created passwords do not generally achieve this theoretical entropy because their choices are neither uniform nor independent. A manager-generated value can come much closer.

The vault is protected by symmetric encryption. A key derivation function turns the master password into a cryptographic key while adding salt and deliberate computational or memory cost:

$$
\text{Key} = \text{KDF}(master\_password, \text{salt}, \text{iterations})
$$

Using that derived key, the conceptual encryption step is:

$$
\text{Ciphertext} = \text{AES}_{256}(\text{Key}, Plaintext\_vault)
$$

A production design normally uses an authenticated-encryption mode, a unique nonce or initialization value, and an authentication tag so that it protects both confidentiality and integrity. The salt prevents attackers from efficiently reusing precomputed tables, while the cost factor slows each guess against a stolen vault. Neither can add entropy to a weak master password. The precise scheme varies by manager, but the strategic trade-off is consistent: many weak or reused secrets become one high-value master secret protecting many strong, unique ones.

That concentration demands care. The master password should be long, unique, and the online vault account should be protected with MFA. Recovery information and registered devices also become part of the security boundary. MFA protects account access and synchronization, but it does not make a copied encrypted vault harder to guess offline; there, resistance depends on the master password and the manager's key-derivation settings.

### Passkeys Remove the Shared Secret

Passkeys change the architecture instead of improving the password. They use an asymmetric key pair:

- The private key authorizes signatures and remains under the control of the user's authenticator or synchronized credential ecosystem.
- The public key is stored by the service and can verify those signatures without revealing the private key.

The underlying digital-signature relationship is:

$$
\sigma = \text{Sign}(private\_key, \text{message})
$$

$$
\text{Verify}(public\_key, \text{message}, \sigma) = \text{true/false}
$$

During registration, the authenticator creates a credential for the service, and the server retains the credential identifier and public key:

$$
\text{Server stores: } (credential\_id,\ public\_key)
$$

During authentication, the server sends a fresh random challenge. After local user verification—often a biometric or device PIN—the authenticator signs data tied to that challenge and the requesting origin:

$$
\sigma = \text{Sign}(private\_key,\ \text{challenge} \| \text{origin} \| client\_data)
$$

$$
\text{Server verifies: } \text{Verify}(public\_key,\ \text{challenge} \| \text{origin} \| client\_data,\ \sigma) \stackrel{?}{=} \text{true}
$$

At the wire level, the authenticator signs structured authenticator data together with a hash of the client data; the origin and challenge are checked through the client data, while the relying-party binding is represented in the authenticator data. The simplified equations capture the security properties that matter:

- A fresh challenge prevents replay of an old response.
- Origin and relying-party binding prevent a look-alike site from using the credential for the legitimate service.
- The server stores no password or equivalent shared secret that an attacker can steal and reuse.
- Each service receives a distinct credential, so one breach cannot fuel credential stuffing elsewhere.

Biometrics serve as a local unlock mechanism; the fingerprint or face template is not sent to the relying service as the authentication secret. Some passkeys are device-bound, while synchronized passkeys can move between a user's devices through an end-to-end encrypted platform service. In either case, the relying party receives a signature, not the private key.

Passkeys are best described as phishing-resistant, not magical. Compromised devices, weak account recovery, malicious software with sufficient privileges, or attacks against a synchronization account can still matter. Yet passkeys categorically remove the attacks that depend on convincing a user to type a reusable secret into the wrong site. That is a much stronger property than asking users to detect every deception correctly.

### A Practical Authentication Checklist

- Adopt passkeys where they are supported.
- For password-based accounts, generate a long, unique password for every service and store it in a reputable password manager.
- Give the strongest protection to email, the password-manager vault, and any SSO identity-provider account because their recovery or reset powers create a large blast radius.
- Enable MFA, preferring phishing-resistant security keys or passkeys when available and authenticator apps over SMS when they are not.
- Treat recovery codes, registered devices, and account-recovery channels as credentials in their own right.
- Use properly validated HTTPS, and do not bypass certificate warnings.
- Be suspicious of unsolicited login links, urgent requests, and requests for secrets or one-time codes.

Authentication controls determine who may enter an account. The next layer determines what happens to the secrets and data on either side of that login. A password manager changes how a user creates and carries credentials; the service must still store those credentials safely, establish protected connections, encrypt readable data, and manage keys across the data lifecycle.

## 2. Cryptography: From Password Hashes to Post-Quantum Protection

Cryptography is often discussed as though it were one tool called “encryption.” In practice, modern security relies on several different tools, each designed for a different job. Hashing protects stored password verifiers. Symmetric encryption protects bulk data. Public-key cryptography helps strangers establish secure communication. Digital signatures prove integrity and origin. Passkeys turn signatures into authentication. End-to-end encryption changes who can read a message, while full-disk encryption changes what a thief can recover from a device.

Confusing these properties creates dangerous gaps. A password can be hashed correctly but still be easy to guess. A message can be encrypted in transit while remaining readable to the service carrying it. A deleted file can remain recoverable from storage. A mathematically sound cipher can become an extortion tool in ransomware. The useful question is therefore not simply, “Is this encrypted?” It is, “What is protected, from whom, at which point in its lifecycle, and under whose key?”

### Hashing Protects Passwords at Rest

The most naive authentication database stores a username next to its plaintext password. A database breach then exposes every credential immediately, including credentials that users may have reused elsewhere.

A cryptographic hash function replaces the stored password with a fixed-length digest:

$$
h = f(x)
$$

The function $f$ is deterministic, so the same input $x$ produces the same digest $h$. A secure cryptographic hash is also designed to resist preimage attacks: given $h$, an attacker should not be able to directly recover an input that produces it. Small changes in the input radically change the output, and the output length stays fixed regardless of input length.

Registration and login can then operate without persisting the plaintext password:

$$
\text{Authenticate if: } f(\text{input}) = h_{\text{stored}}
$$

At registration, the server computes the verifier and discards the submitted password. At login, it derives a verifier from the new input and compares the result with the stored value. A real system must use a password-specific key derivation function, generate a unique salt, compare values safely, protect the password while it is briefly present in process memory, and handle nonexistent accounts without leaking information.

#### One-way does not mean collision-free

A hash accepts inputs from a domain that is effectively much larger than its finite output range. The pigeonhole principle therefore guarantees that distinct inputs must sometimes share an output:

$$
|\text{Domain}| > |\text{Range}| \Rightarrow \exists\, x_1 \neq x_2 : f(x_1) = f(x_2)
$$

This does not make a well-designed hash practically reversible. Preimage resistance, second-preimage resistance, and collision resistance are related but different properties. With a large output and a secure construction, collisions exist mathematically but are infeasible to find deliberately.

Hashing also does not stop guessing. An attacker with a stolen database can hash likely passwords offline and compare the results. Common words, reused credentials, and predictable patterns fall quickly even when the verifier itself cannot be reversed. If a service can send a user their original password, that is a strong warning that it retained the password in plaintext or a reversibly protected form instead of using a one-way verifier.

### Salts Defeat Reuse Leakage and Precomputation

Unsalted hashing leaks equality. If Carol and Charlie choose the same password $x$, they receive the same digest:

$$
f(x) = h_{\text{Carol}} = h_{\text{Charlie}}
$$

An attacker can learn that the accounts share a password without knowing what the password is. The attacker can also build a precomputed password-to-hash lookup table and reuse it against every account protected by the same algorithm.

A salt is a public, per-password value combined with the password before the verifier is derived:

$$
h = f(\text{password} \| \text{salt})
$$

The concatenation symbol $\|$ means that the password and salt become one input. Two accounts with the same password but different salts now produce unrelated stored values. Because each salt changes the input domain, an attacker cannot amortize one precomputed table across the entire database.

The pairwise probability that two independently generated salts match is:

$$
P(\text{same salt collision}) = \frac{1}{|S|}
$$

where the salt space is:

$$
|S| = k_s^{l_s}
$$

Here, $k_s$ is the number of symbols available to each salt position and $l_s$ is its length. The formula describes one pair of salts; the probability of at least one collision across a large database grows according to the birthday effect. Modern systems therefore use sufficiently long salts—commonly random byte strings—rather than the two-character values used in classroom examples.

The salt does not need to be secret. It may be stored separately or encoded into a structured verifier string. A simplified prefix layout is:

$$
\text{stored} = s \| h_{\text{rest}}
$$

An illustrative two-character format can be written as:

$$
\text{stored} = \underbrace{s}_{\text{first 2 chars}} \underbrace{\ f(\text{password} \| s)_{\text{remaining chars}}}_{\text{hash body}}
$$

Modern formats are richer: they normally encode an algorithm identifier, version, cost parameters, salt, and derived verifier. That self-description allows a service to verify old accounts and upgrade their parameters after a successful login. Production systems should delegate the format and verification logic to a vetted password-hashing library.

### Password Hashing Must Be Deliberately Expensive

Fast general-purpose hashes are valuable for integrity checks, certificates, and many other protocols, but speed is a liability for password storage. A password KDF such as PBKDF2, bcrypt, scrypt, or Argon2 deliberately consumes time—and, for memory-hard designs, memory—on every guess. A modest delay is acceptable during a real login but costly when multiplied across billions of offline guesses.

A $b$-bit hash has this many possible outputs:

$$
|H| = 2^b
$$

For SHA-256, that output space is $2^{256} \approx 1.16 \times 10^{77}$. But password cracking is usually limited by the smaller and more predictable password space, not by the full digest range. An attacker needs a likely password that reproduces the verifier; they do not need to enumerate every possible digest. This is why a huge hash output cannot rescue a weak password.

A simplified KDF attack model is:

$$
T_{\text{attack}} = \frac{N_{\text{guesses}}}{r_{\text{KDF}}}
$$

with an effective rate represented as:

$$
r_{\text{KDF}} = \frac{r_{\text{raw}}}{C}
$$

The cost factor $C$ is a useful abstraction, but real KDF performance is not always a simple scalar division. Memory requirements, parallelism, hardware architecture, and time–memory trade-offs matter. The engineering goal remains the same: choose parameters that are tolerable for legitimate authentication while making offline guessing materially expensive, and raise those parameters as hardware improves.

<details><summary>Argon2 packages the salt, parameters, and verifier into one structured output:</summary>

```python
from argon2 import PasswordHasher

ph = PasswordHasher(
    time_cost=3,       # C = number of iterations
    memory_cost=65536, # Memory in KB (64 MB)
    parallelism=4      # Threads
)

# Registration: hash the password
h = ph.hash("cherry")  # Returns salt-prefixed Argon2 hash string

# Login: verify
try:
    ph.verify(h, "cherry")  # True if correct
    authenticated = True
except:
    authenticated = False
```

</details>

The library automatically creates a salt and understands its own encoded format. The broad `except` is acceptable only as compact teaching pseudocode; production code should catch the library's expected verification exceptions explicitly and treat unexpected failures separately.

The practical storage rule is straightforward: do not invent a custom construction, do not hash passwords directly with a fast general-purpose function, and do not rely on secrecy of the algorithm. Security should depend on vetted designs, carefully selected parameters, and protected secrets—not on an attacker failing to learn how the system works.

### Symmetric Encryption Protects Bulk Data

Hashing is deliberately one-way. Encryption is reversible by design. Symmetric, or secret-key, encryption uses one shared key for both directions:

$$
c = E_K(p) \quad \text{(Encryption)}
$$

$$
p = D_K(c) \quad \text{(Decryption)}
$$

The plaintext $p$ becomes ciphertext $c$ under key $K$, and the inverse operation recovers it with the same key. The algorithm need not be secret. Under Kerckhoffs's principle, a sound cryptosystem remains secure when its design is public and only the key is hidden.

#### Caesar's cipher exposes the role of key space

The Caesar cipher rotates each letter by a fixed number of alphabet positions. Encoding letters as values from 0 through 25 gives:

$$
c = (p + k) \mod 26
$$

Decryption reverses the rotation:

$$
p = (c - k) \mod 26
$$

Its nontrivial key space is tiny:

$$
|K_{\text{Caesar}}| = 25
$$

<details><summary>An attacker can enumerate every key by hand. This simple program implements both directions:</summary>

```python
def caesar_encrypt(plaintext, k):
    result = ""
    for char in plaintext.upper():
        if char.isalpha():
            p = ord(char) - ord('A')       # Convert letter to 0-25
            c = (p + k) % 26               # Apply the rotation
            result += chr(c + ord('A'))    # Convert back to letter
        else:
            result += char
    return result

def caesar_decrypt(ciphertext, k):
    return caesar_encrypt(ciphertext, -k)  # Subtraction = reverse rotation
```

</details>

The example demonstrates modular arithmetic, not modern confidentiality. It is valid only for ASCII letters A–Z: Python's `isalpha()` also accepts non-ASCII letters, which do not fit the snippet's `ord(char) - ord('A')` mapping. With $k=26$, the rotation is the identity; with $k=13$, applying the operation twice returns the original text.

Modern systems use AES with 128-, 192-, or 256-bit keys. AES is a block cipher and must be used through a secure mode of operation. GCM is an authenticated-encryption mode: it protects confidentiality and detects unauthorized modification.

Production code should use a vetted library and its documented API. GCM requires a unique nonce for every encryption performed under the same key—nonce reuse can catastrophically break its guarantees. The receiver needs the same secret key, the transmitted nonce, and the authentication tag.

That shared key creates the key-distribution problem. Two parties that have never communicated securely need a way to establish a secret without first sending that secret across an exposed channel.

### Public-Key Cryptography Solves Key Establishment

Asymmetric cryptography assigns each participant a public key and a related private key. Others can encrypt to a recipient with the public key, while only the private-key holder can decrypt. In deployed protocols, asymmetric operations usually establish or protect a symmetric session key; efficient symmetric encryption then carries the bulk data.

Simplified RSA key generation begins with two large primes:

$$
n = p \times q
$$

$$
\phi(n) = (p-1)(q-1)
$$

Choose $e$ such that $1 < e < \phi(n)$ and $\gcd(e, \phi(n)) = 1$. The private exponent is the modular inverse of $e$:

$$
d \equiv e^{-1} \pmod{\phi(n)}
$$

The public key contains $(e,n)$, while the private key contains secret information sufficient to apply $d$. Encryption and decryption are:

$$
c = m^e \mod n
$$

$$
m = c^d \mod n
$$

<details><summary>But raw RSA is deterministic and insecure in practice. Real encryption uses an encoding and padding scheme such as OAEP, validates message sizes, and relies on mature libraries:</summary>

```python
from cryptography.hazmat.primitives.asymmetric import rsa, padding
from cryptography.hazmat.primitives import hashes

# Key generation: choose p, q, compute n, e, d
private_key = rsa.generate_private_key(public_exponent=65537, key_size=2048)
public_key = private_key.public_key()

# Encryption: c = m^e mod n (sender uses receiver's public key)
message = b"Hello"
ciphertext = public_key.encrypt(
    message,
    padding.OAEP(mgf=padding.MGF1(hashes.SHA256()), algorithm=hashes.SHA256(), label=None)
)

# Decryption: m = c^d mod n (receiver uses their private key)
plaintext = private_key.decrypt(
    ciphertext,
    padding.OAEP(mgf=padding.MGF1(hashes.SHA256()), algorithm=hashes.SHA256(), label=None)
)
```

</details>

#### Diffie–Hellman establishes a shared secret

Diffie–Hellman does not encrypt the application message. It lets two parties derive the same secret over a public channel. They agree openly on parameters:

$$
g, p \quad \text{(generator and large prime)}
$$

Alice selects private value $a$ and sends:

$$
A = g^a \mod p
$$

Bob selects private value $b$ and sends:

$$
B = g^b \mod p
$$

Each side then derives:

$$
s = B^a \mod p = A^b \mod p = g^{ab} \mod p
$$

An observer sees $g$, $p$, $A$, and $B$ but cannot feasibly recover $a$ or $b$ when secure parameters and implementations are used. The resulting secret is normally fed through a KDF before it becomes one or more symmetric session keys.

Unauthenticated Diffie–Hellman remains vulnerable to a machine-in-the-middle attacker who establishes a different secret with each party. Certificates, digital signatures, pre-shared authentication, or an authenticated protocol must bind the exchange to the intended identities. Modern deployments often use ephemeral elliptic-curve Diffie–Hellman to gain efficiency and forward secrecy.

### Digital Signatures Prove Integrity and Origin

Encryption aims at confidentiality; a digital signature aims at authenticity and integrity. The signer hashes a message and creates a signature with a private key:

$$
\sigma = \text{Sign}_{K_{\text{priv}}}\big(\text{Hash}(m)\big)
$$

The verifier independently hashes the received message:

$$
h_{\text{received}} = \text{Hash}(m)
$$

In a simplified RSA, verification recovers a representative using the public exponent:

$$
h_{\text{decrypted}} = \text{Verify}_{K_{\text{pub}}}(\sigma) = \sigma^e \mod n
$$

The comparison is:

$$
\text{Valid if: } h_{\text{received}} = h_{\text{decrypted}}
$$

It is tempting to describe signing as “encrypting with the private key,” but that analogy does not generalize safely. Signature schemes have their own encodings and security proofs; RSA signatures require a scheme such as PSS, and elliptic-curve signatures are not encryption run backward.

<details><summary>Code</summary>

```python
from cryptography.hazmat.primitives.asymmetric import rsa, padding
from cryptography.hazmat.primitives import hashes

# Generate a signing key pair
private_key = rsa.generate_private_key(public_exponent=65537, key_size=2048)
public_key = private_key.public_key()

document = b"I, Alice, agree to the following contract terms..."

# Step 1: Sign — σ = Sign_{K_priv}(Hash(m))
signature = private_key.sign(
    document,
    padding.PSS(mgf=padding.MGF1(hashes.SHA256()), salt_length=padding.PSS.MAX_LENGTH),
    hashes.SHA256()  # Hash function applied internally
)

# Step 2: Verify — check h_received == h_decrypted
try:
    public_key.verify(
        signature,
        document,
        padding.PSS(mgf=padding.MGF1(hashes.SHA256()), salt_length=padding.PSS.MAX_LENGTH),
        hashes.SHA256()
    )
    print("Signature valid")
except Exception:
    print("Signature invalid — document tampered or wrong signer")
```

</details>

Forgery resistance cannot be reduced to hash width alone. A signature's actual security depends on the signature scheme, key size, hash properties, implementation, and adversary model. A $b$-bit hash generally offers about $2^{b/2}$ generic collision resistance, while preimage resistance is closer to $2^b$; an RSA-2048 key also does not have 256-bit security merely because it is paired with SHA-256.

A valid signature proves that the corresponding private key authorized the signed data and that the data has not changed. Binding that key to a human, organization, or domain requires a separate trust mechanism such as a certificate authority or a verified key registry. If the private key is stolen, the signatures it creates are cryptographically valid even though the legitimate owner did not intend them, which is why revocation and protected key storage matter.

### Passkeys Turn Signatures into Authentication

Passkeys apply a site-specific signature credential to a challenge–response protocol. The server stores a public key rather than a password verifier; the user's authenticator controls the private key.

At registration, the conceptual state is:

$$
\text{Device generates: } (K_{\text{priv}}^{(s)},\ K_{\text{pub}}^{(s)}) \text{ for site } s
$$

$$
\text{Server stores: } (user\_id,\ K_{\text{pub}}^{(s)})
$$

At authentication time, the server creates a fresh challenge:

$$
c \xleftarrow{\text{random}} \text{Server}
$$

The source summarizes the response as:

$$
\sigma = \text{Sign}_{K_{\text{priv}}^{(s)}}\!\big(c \| \text{origin} \| client\_data\big)
$$

and verification as:

$$
\text{Server verifies: } \text{Verify}_{K_{\text{pub}}^{(s)}}(\sigma) \stackrel{?}{=} c \| \text{origin} \| client\_data
$$

In the actual protocol, the authenticator signs `authenticatorData || SHA-256(clientDataJSON)`; the relying-party identifier, origin, challenge, and operation type are checked through those structures. Signature verification returns success or failure over those signed bytes—it does not recover and return $c \| origin \| {client\_data}$. The abstraction nevertheless captures the main guarantees: a fresh challenge resists replay, site binding resists look-alike origins, and the server has no reusable password to leak.

Local user verification—often a biometric or device PIN—unlocks use of the credential. The biometric template is not sent to the website. A passkey can be device-bound or synchronized through a credential provider. A highly simplified synchronization model is:

$$
\text{Synced securely: } \text{Encrypt}_{K_{\text{device}}}(K_{\text{priv}}^{(s)}) \xrightarrow{\text{cloud}} \text{Other devices}
$$

Real synchronization and recovery architectures are provider-specific and more complex than this expression. The important boundary is that private credential material is not disclosed to the relying website; synced passkeys may move between authorized devices inside a protected provider ecosystem.

Passkeys are phishing-resistant, not invulnerable. Device compromise, session theft, insecure recovery, malicious fallback flows, and compromise of a synchronization account remain relevant. Their architectural advantage is narrower and powerful: users no longer type a site-reusable authentication secret that a phisher can capture and replay elsewhere.

### Encryption in Transit Is Not End-to-End Encryption

TLS protects a connection between two endpoints, such as a browser and a service. If a service terminates TLS, processes plaintext, and opens another protected connection to a recipient, both network legs may be secure while the service still sees the content.

End-to-end encryption moves content encryption to the communicating clients so that the intermediary relays ciphertext without holding the content-decryption key. The difference can be summarized as:

$$
\text{Plaintext Access}_{\text{Server } E} = \begin{cases} m & \text{Point-to-Point Encryption (In Transit)} \\ \emptyset & \text{End-to-End Encryption (E2EE)} \end{cases}
$$

In a simplified public-key example, Alice encrypts for Bob:

$$
c = E_{K_{\text{pub, Bob}}}(m)
$$

The intermediary cannot use its own private key to recover that message:

$$
\text{Server } E \text{ holds } c, \text{ but } D_{K_{\text{priv, Server}}}(c) = \text{Error}
$$

Production messaging protocols normally use hybrid encryption and evolving symmetric session keys rather than applying public-key encryption directly to every message. The simplified relationship still makes the trust boundary clear.

E2EE protects content, not every observable fact. Servers may still learn metadata such as account identifiers, timing, frequency, and message size. Endpoint malware can read plaintext before encryption or after decryption. Secure key verification and recovery also matter: encryption to the wrong public key can create confidentiality against everyone except the attacker.

### Deletion, Disk Encryption, and the Data Lifecycle

Cryptography must protect data after it leaves active use as well. On many file systems, ordinary deletion removes a directory entry and marks storage space reusable without immediately overwriting the underlying bytes:

$$
\text{Block Data}_{\text{Standard Delete}} = B_{\text{original}}
$$

A simplified secure-overwrite model is:

```math
\text{Block Data}_{\text{Secure Delete}} = \text{OverwritePattern} \quad (\text{where } \text{OverwritePattern} \in \{00^*, 11^*, \text{random}\})
```

That model fits a directly addressable magnetic block better than modern storage in general. Journaling, copy-on-write file systems, snapshots, RAID controllers, SSD flash translation layers, and wear leveling can leave old physical pages outside the application's control. Secure disposal must therefore account for the actual storage medium: repeatedly overwriting a file path cannot guarantee removal of every physical or historical copy.

#### Full-disk encryption and crypto-shredding

Full-disk encryption keeps storage blocks in ciphertext form, but a simple screen lock may leave an unlocked volume mounted and its keys resident in memory. The strongest theft protection generally applies at power-off or pre-boot, or after the platform has evicted the relevant keys; lock-state behavior depends on the device and configuration. Destroying all usable copies of the media-encryption key can render the remaining ciphertext inaccessible without rewriting every block—a technique known as crypto-shredding. Its assurance depends on the cipher, key hierarchy, backups, snapshots, escrow, recovery keys, and whether any plaintext copies exist elsewhere.

The same primitives can be turned against the owner. Ransomware commonly uses fast symmetric encryption for files and protects the local key with an attacker-controlled public key:

$$
c_{\text{file}} = E_{K_{\text{AES}}}(m_{\text{file}})
$$

$$
c_{\text{key}} = E_{K_{\text{pub, Attacker}}}(K_{\text{AES}})
$$

Only the attacker-controlled private key can ordinarily unwrap the file-encryption key. The defensive lesson is operational: maintain tested, isolated, versioned backups; reduce malware execution paths; patch systems; segment important assets; and protect backup credentials. Strong cryptography can make ransomware recovery without a clean backup or a key genuinely difficult.

### Quantum Computing Changes the Long-Term Threat Model

A classical bit holds one of two values at measurement. An $n$-bit register therefore occupies one of $2^n$ possible bit strings at a given moment:

$$
\text{Classical State} = 1 \text{ state out of } 2^n
$$

An $n$-qubit pure state is described by amplitudes over $2^n$ computational basis states:

$$
\text{Quantum Superposition State} = \sum_{x=0}^{2^n - 1} \alpha_x |x\rangle, \quad \text{where } \sum_{x=0}^{2^n - 1} |\alpha_x|^2 = 1
$$

This state-space description does not mean a quantum computer exposes the results of $2^n$ ordinary computations at once. Measurement produces limited classical information. Quantum advantage comes from algorithms that manipulate amplitudes so useful outcomes become likely.

Shor's algorithm is important because it solves the number-theoretic problems underlying RSA, finite-field Diffie–Hellman, and elliptic-curve cryptography in polynomial time on a sufficiently capable fault-tolerant quantum computer. Grover's algorithm gives a quadratic improvement for unstructured search, reducing the idealized work factor of a symmetric key search from $N$ to roughly $\sqrt{N}$. This is why public-key migration requires new mathematical families, while increasing symmetric key sizes can retain a large security margin.

Post-quantum cryptography uses algorithms designed to run on conventional computers while resisting known classical and quantum attacks. Lattice-based key establishment and signatures are leading examples. Migration matters before a cryptographically relevant quantum computer exists because long-lived encrypted traffic can be collected now and attacked later—the “harvest now, decrypt later” threat model. Organizations must inventory cryptographic dependencies, account for data-retention horizons, and plan interoperable upgrades rather than attempting an abrupt replacement after a breakthrough.

Cryptographic strength answers whether protected data can be read, forged, or altered. Network architecture determines where that protection begins and ends. A strong cipher provides little comfort if an application sends plaintext before the secure channel starts, leaks an authenticated session afterward, or places trust in an intermediary the user did not expect.

## 3. Networks: Why HTTPS Isn’t Enough

A padlock beside a Wi-Fi network name does not secure a message all the way to its destination. HTTPS does not make a device trustworthy. A virtual private network does not eliminate the need for HTTPS, and a firewall cannot stop every malicious program. Each control protects a particular segment, protocol, or failure mode—and each leaves a trust boundary somewhere else.

That is the central lesson of network security. Data crosses radios, access points, routers, proxies, servers, and software processes. At every stage, defenders must ask three questions: Who can read this traffic? Who can change it? And what does the next system trust as proof of identity? Following a packet from a user's device to an internet service reveals how technologies such as WPA, TLS, HSTS, VPNs, SSH, firewalls, sandboxing, and automatic updates fit together—and why effective security ultimately depends on defense in depth.

### Encryption Protects a Path, Not an Abstract Connection

Wi-Fi Protected Access—whether WPA, WPA2, or WPA3—encrypts radio traffic between a wireless client and its access point. That protection matters: without it, a nearby observer may be able to capture traffic transmitted over the shared wireless medium. Its scope is also limited. Once the access point forwards the traffic, the application still needs an end-to-end transport such as HTTPS if the data is to remain confidential and tamper-resistant across the wider internet.

Network communication is divided into packets. A packet contains headers, which carry routing and transport metadata such as addresses and ports, and a payload, which carries the application data. Packets traverse multiple links and intermediate systems, with real transit affected by transmission, propagation, processing, queuing, retransmission, and protocol overhead. For security, the key point is simpler: if the application payload is unencrypted, any system with access to the traffic may inspect or alter it.

<details><summary>Plain HTTP illustrates the danger. For example, a plaintext form submission can expose sensitive fields:</summary>

```http
POST /checkout HTTP/1.1
Host: example.com
Content-Type: application/x-www-form-urlencoded

card_number=4111111111111111&exp=12/28&cvv=123&name=Alice
```

</details>

Using `POST` rather than `GET` does not make the data secret. It moves the fields into the request body, but under plain HTTP that body remains readable. A passive packet sniffer can capture search terms, account data, and form values without changing the traffic or alerting either endpoint. An active machine-in-the-middle adversary can go further by modifying an HTTP response, injecting advertisements, scripts, or other content before it reaches the browser.

WPA therefore protects the local radio link, while HTTPS protects the HTTP exchange across the network path. Confusing those scopes creates a dangerous false sense of security.

### A Stolen Session Can Be as Valuable as a Stolen Password

HTTP is stateless: one request does not inherently remember the request before it. Websites create continuity by issuing session cookies. After a successful login, the server sends a token in a `Set-Cookie` header, and the browser returns it in later `Cookie` headers.

<details><summary>The comments in this illustrative transcript separate the server's response from the browser's subsequent request:</summary>

```http
<!-- Server Response upon Login (Unencrypted HTTP) -->
HTTP/1.1 200 OK
Set-Cookie: session=1234abcd; Path=/

<!-- Subsequent Client Request (Unencrypted HTTP) -->
GET /account/dashboard HTTP/1.1
Host: example.com
Cookie: session=1234abcd
```

</details>

The token functions like a hand stamp: the server treats possession of it as evidence that authentication already occurred. On a plaintext connection, an observer can copy `session=1234abcd`, attach it to a separate request, and impersonate the user. The attacker does not need the password and may also bypass the benefit of two-factor authentication if the legitimate user completed that step before the session was issued.

One common network-side exposure occurs when an authenticated session travels over plaintext HTTP and its cookie may be sent without the `Secure` attribute. Tokens can also be stolen through compromised endpoints or application flaws. For transport protection, both controls matter: TLS encrypts the request, and the cookie's `Secure` attribute prevents a compliant browser from sending it over an ordinary HTTP connection. The `HttpOnly` attribute addresses a different risk by preventing normal client-side JavaScript from reading the cookie.

This is why protecting only the login form is inadequate. The entire authenticated session must remain on HTTPS, and its bearer token must be handled as sensitively as the credentials that created it.

### TLS Provides Confidentiality, Integrity, and Authentication

HTTPS carries HTTP inside Transport Layer Security. TLS provides three closely related guarantees:

- **Confidentiality:** intermediaries cannot read the protected HTTP content.
- **Integrity:** the endpoints can detect unauthorized modification.
- **Authentication:** the client can verify the identity represented by the server's certificate.

The authentication step relies on public-key infrastructure. An X.509 certificate binds a domain identity to a public key, and a certificate authority signs that certificate. Browsers and operating systems contain stores of trusted root CA certificates, allowing them to validate a chain from the site's certificate back to a trusted root.

For an RSA-signed certificate, a simplified verification model is:

$$
H_{\text{cert}} = \text{Hash}(\text{TBSCertificate})
$$

$$
H_{\text{decrypted}} = \text{Verify}_{K_{\text{pub, CA}}}(\sigma_{\text{cert}}) = (\sigma_{\text{cert}})^{e_{\text{CA}}} \pmod{n_{\text{CA}}}
$$

$$
\text{Valid Identity} \iff H_{\text{cert}} == H_{\text{decrypted}}
$$

`TBSCertificate` is the certificate body that was signed, $\sigma_{\text{cert}}$ is the CA's signature, and $K_{\text{pub, CA}}$ is the CA public key already trusted by the client. Conceptually, the client hashes the signed certificate data and checks that the signature authenticates the same value.

Modern signature verification depends on the certificate's declared algorithm, and RSA verification includes an encoded signature structure rather than a bare comparison after modular exponentiation. Signature validation is also only part of certificate validation: the browser must check the hostname, validity period, chain, constraints, and other policy requirements. Once the server is authenticated and the handshake succeeds, TLS establishes symmetric session keys that efficiently protect the HTTP headers and body, including session cookies.

This model concentrates trust. A compromised or improperly trusted CA may be able to issue a certificate that a browser accepts. Endpoint control matters too: whoever can change a device's root trust store can change which certificate issuers that device treats as authoritative.

### HSTS Closes the Downgrade Window

Typing a domain without a scheme has historically risked an initial plaintext request. A server might receive `http://example.com` and respond with a redirect to `https://example.com`, but an on-path attacker can interfere before the protected connection begins. In an SSL-stripping attack, the adversary keeps the client on HTTP while opening a genuine HTTPS connection to the server, then proxies and modifies traffic between the two.

HTTP Strict Transport Security moves the HTTPS decision into the browser. A site sends a `Strict-Transport-Security` response header over a valid HTTPS connection, and the browser records a rule requiring future requests to use HTTPS. A typical policy includes:

- `max-age=31536000`, which keeps the rule active for one year;
- `includeSubDomains`, which extends it to the site's subdomains; and
- `preload`, which signals the site's intention to meet the requirements for a browser-maintained preload list.

The browser enforces the policy until `max-age` expires and rewrites an attempted HTTP navigation before sending an insecure request. Ordinary HSTS still has a trust-on-first-use limitation: the browser needs one valid HTTPS encounter before it can cache the site's rule. Preloading places the rule in the browser ahead of that first visit, so a preloaded domain does not depend on an unprotected first request to learn that HTTPS is mandatory.

HSTS prevents protocol downgrade for the protected domain. It does not, however, prove that a visually similar domain is the domain the user intended to visit. An attacker may register a look-alike such as `exam1e.com`, obtain a valid certificate for that different name, and display a legitimate padlock. HSTS for `example.com` does not govern `exam1e.com`. Structural browser protections can remove the downgrade decision from the user, but careful origin validation and anti-phishing controls remain necessary for typosquatting and homograph attacks.

### VPNs and SSH Move the Trust Boundary

HTTPS secures a particular application connection. A virtual private network takes a broader approach by encapsulating routed IP traffic in an encrypted tunnel from the client to a VPN gateway. In a full-tunnel configuration, a hostile local network sees protected tunnel traffic, while internet services generally see the VPN gateway's address instead of the client's original public address. Split-tunnel configurations may send only selected traffic through the VPN.

The protection ends at the gateway. Traffic leaving the VPN server still needs HTTPS or another end-to-end secure protocol, and the VPN provider becomes a new point of trust. A VPN therefore relocates part of the network trust boundary; it does not abolish it.

Secure Shell applies authenticated encryption to remote administration. SSH commonly listens on TCP port 22 and protects commands, keystrokes, and output between a client and a remote host. The listening service is still an entry point that defenders must authenticate, patch, and restrict appropriately.

### Ports Are Addresses, Not Security Controls

TCP and UDP use a 16-bit destination-port field to direct incoming traffic to a service. Each protocol has its own port namespace, and some values have special or reserved uses, but the encoded space is fixed:

$$
N_{\text{ports}} = 2^{16} = 65,536
$$

Common conventions place SSH on port 22, HTTP on port 80, and HTTPS on port 443. An administrator can move a service to a different port, but that does not remove it from the network. A scanner can probe the full range and record which ports respond.

A basic parallel scanning model is:

$$
T_{\text{scan}} = \frac{N_{\text{ports}} \times T_{\text{probe}}}{P_{\text{parallel}}}
$$

$T_{\text{probe}}$ is the average time for one probe, and $P_{\text{parallel}}$ is the number of concurrent probes. The formula abstracts away packet loss, timeouts, rate limits, scanner strategy, and network conditions, but it shows why moving SSH from port 22 to a high-numbered port is not a strong defense. The search space contains only 65,536 possibilities and is designed to be addressable.

Changing a default port may reduce noise from simplistic automated traffic, but it cannot replace public-key authentication, patching, access-control rules, and firewalls. Treating an undisclosed port number as the primary barrier is security through obscurity.

The same discovery techniques are dual-use. Attackers scan for exposed and vulnerable services; authorized penetration testers and red teams use them to find weaknesses before an adversary does. Blue teams then harden, monitor, and defend the systems under test. Authorization and intent determine whether the activity is defensive testing or intrusion.

### Firewalls and Proxies Turn the Network Boundary into a Control Point

A firewall evaluates traffic against policy. Basic filtering considers network and transport information such as IP addresses, connection state, and ports. It can reject unwanted inbound connections, restrict outbound access, or isolate systems that should not communicate directly.

Deep packet inspection goes beyond these headers and analyzes application content. It may look for protocol violations, malicious signatures, forbidden destinations, or sensitive information leaving an organization. A forward proxy creates a similar policy point by placing an intermediary between managed clients and internet services. Proxies can aggregate requests, filter URLs, and route clicks through security scanners.

These controls are not free. Reassembling flows and scanning application content in real time requires processing capacity, especially on high-throughput networks. Encryption also limits what an ordinary network observer can inspect unless the connection terminates at, or is deliberately intercepted by, a trusted control point.

<details><summary>For example, an email service can rewrite a link so that a security system evaluates the destination at click time:</summary>

```http
<!-- Original Email HTML Link -->
<a href="http://malicious-site.com">Click Here</a>

<!-- Rewritten Link by Corporate Email Proxy -->
<a href="https://safelinks.corporate.com/scan?url=http://malicious-site.com">Click Here</a>
```

</details>

The rewritten destination first reaches the corporate scanning service, which can block a known malicious site or redirect the user onward. The technique adds a defensive checkpoint, although it also means the proxy observes and influences the user's navigation.

#### Enterprise TLS Inspection Creates a Managed Machine in the Middle

TLS normally prevents a network proxy from silently decrypting HTTPS. A managed organization can change that outcome by installing its own root CA certificate on employee or university devices and routing traffic through an inspection proxy. When the user visits a site, the proxy creates an on-the-fly certificate for that hostname, signs it with the enterprise CA, and presents it to the managed client. The client accepts the certificate because its local trust store was configured to trust that CA.

The resulting decision can be represented as:

$$
\text{Trust Decision} = \text{Verify}\!\left(\text{Cert}_{\text{Intercepted}},\ K_{\text{pub, Enterprise Root CA}}\right)
$$

$$
\text{Result} = \begin{cases} \text{Accepted (No Warning)} & \text{if Enterprise Root CA in Device Store} \\ \text{Security Error Alert} & \text{if Enterprise Root CA Missing} \end{cases}
$$

This model isolates the effect of the enterprise trust anchor. The generated certificate must still pass normal checks such as hostname matching, validity, permitted use, and a valid signature chain; merely finding a root in the store does not make every certificate acceptable.

The proxy establishes one protected connection with the client and another with the destination, decrypting the traffic between them so it can perform malware scanning or data-loss prevention. This architecture has legitimate defensive uses, but it changes the privacy model: HTTPS is no longer end-to-end with respect to the organization operating the managed device and proxy.

It also demonstrates why control of the endpoint is so important. The browser's padlock confirms that the connection is valid under the device's configured trust policy; it does not promise that no administrator has modified that policy or installed an inspection root.

### Malware Turns Individual Weaknesses into Network-Scale Attacks

Network defenses ultimately interact with the software running at each endpoint. Malware is a broad category, but the distinction between viruses and worms explains how compromise spreads:

- A **virus** infects host files or programs and replicates when that host code runs; user action commonly initiates that execution.
- A **worm** propagates automatically by scanning for reachable systems and exploiting vulnerable services, often through open ports.

Modern operating systems reduce the consequences of execution through sandboxing and least privilege. Applications receive restricted access to files, cameras, microphones, and other resources, often requiring explicit permission. Sandboxing does not make malicious code harmless, but it places another barrier between one compromised process and the rest of the system.

Many attackers preserve access to infected machines rather than immediately destroying them. A command-and-control server can coordinate those devices as a botnet. When $B$ compromised nodes each generate requests at rate $r_j$, their combined rate is:

$$
R_{\text{total}} = \sum_{j=1}^{B} r_j
$$

$$
\text{Service Denial} \iff R_{\text{total}} > C_{\text{server}}
$$

$C_{\text{server}}$ represents the target's processing or bandwidth capacity, measured in units compatible with $r_j$. Once the aggregate attack volume exceeds the service's ability to accept and process traffic, legitimate requests are delayed or dropped. The threshold model is simplified—real services have multiple bottlenecks and can degrade before a single capacity number is crossed—but it explains the scaling advantage of a distributed denial-of-service attack.

A request stream from one address is comparatively easy to identify and block. A botnet can draw on thousands of residential and internet-connected devices, making simple IP blocking both less effective and more likely to harm legitimate users. Effective mitigation therefore often relies on distributed edge capacity and dynamic filtering close to the network border.

### Zero-Days Make Defense in Depth Necessary

Antivirus tools can recognize known malicious signatures, and automatic updates reduce the time that known vulnerabilities remain exposed. Neither is absolute. A zero-day exploit targets a flaw that defenders do not yet have a patch for, so a signature-based product may not recognize it. Automatic updates also create their own trust dependency: if a software supply chain or update mechanism is compromised, the same distribution channel that rapidly delivers fixes can rapidly distribute malicious code.

Security therefore works best as a gauntlet of independent or partially independent controls. If an attack must bypass $L$ layers, a simple model for total breach probability is:

$$
P(\text{system breach}) = \prod_{k=1}^{L} P(\text{failure of layer } k)
$$

The product is valid only when all represented layers must fail and their failures can be treated as independent. Real controls often share dependencies—a compromised administrator account might weaken several at once—so the formula should not be used as a precise risk calculation. Its architectural message remains valuable: a firewall can limit reachability, a patched service can remove a known exploit, sandboxing can constrain a compromised application, TLS can protect data in transit, and strong authentication can stop stolen network access from becoming account access. One control can catch what another misses.

### A Practical Layered-Security Checklist

- Use WPA2 or WPA3 on wireless networks, but rely on HTTPS or another authenticated encrypted protocol for application traffic.
- Keep authenticated sessions on HTTPS and mark session cookies `Secure` and `HttpOnly`.
- Do not bypass TLS certificate warnings; understand that a managed device may contain organization-controlled roots.
- Deploy HSTS and consider preloading for high-value domains, while treating look-alike domains as a separate phishing risk.
- Use a VPN to protect an untrusted local path when appropriate, without treating it as a substitute for HTTPS.
- Protect SSH and other exposed services with strong authentication, patching, and network access controls; do not rely on hidden port numbers.
- Use firewalls, proxies, and deep inspection according to a transparent policy that accounts for both defensive value and privacy impact.
- Keep systems updated, sandbox applications, monitor for malware, and design for the possibility that any single layer may fail.

Network controls can restrict what reaches software and protect it on the way. They cannot make vulnerable software interpret hostile input safely. TLS can faithfully and confidentially deliver an exploit; once a packet arrives, the decisive boundary shifts from the network path to the parser, authority check, or memory region that consumes it.

## 4. Applications: Trust Boundaries Under Attack

Most application vulnerabilities begin with a boundary mistake. A browser treats attacker-controlled text as executable markup. A database parses user input as SQL. A shell interprets a domain name as a command sequence. A server trusts a restriction that exists only in the user's browser. A C function writes beyond a buffer and turns data into a new control-flow address.

These failures look different, but they share one design error: code and data, or trusted and untrusted state, were allowed to cross without a reliable boundary. Secure applications preserve that separation with context-aware output encoding, parameterized interfaces, server-side authorization, unpredictable request tokens, memory-safe operations, and layered platform defenses. Understanding where each boundary fails makes the defenses easier to reason about—and much harder to apply only cosmetically.

### The Browser Is Both a Renderer and an Execution Environment

HTML deliberately separates what a link displays from where it goes. That flexibility enables ordinary web navigation, but it also enables visual misdirection.

<details><summary>A user may read one domain while the anchor's `href` points elsewhere:</summary>

```html
<!-- Visible text claims harvard.edu; actual destination is yale.edu -->
<a href="https://yale.edu">https://harvard.edu</a>
```

</details>

Inspecting the actual destination, using trusted bookmarks, and navigating directly to sensitive services reduces the risk. Hover previews help on desktop, but they are not a universal defense—especially on touch devices, with shortened links, or against carefully crafted look-alike domains.

Cross-site scripting goes beyond misdirection. It causes a browser to interpret attacker-controlled content as active code within a trusted site's origin. A reflected-XSS flaw takes input from a request, inserts it into a response without the correct contextual encoding, and sends the resulting page to the victim.

<details><summary>The vulnerable response may look as simple as:</summary>

```html
<p>
  Results for
  <script>
    alert("attack");
  </script>
</p>
```

</details>

The browser parses the injected element as markup rather than displaying it as text. The payload may arrive through a decoded query parameter or another untrusted source; XSS occurs when attacker-controlled content reaches an executable browser context without correct context-aware handling. It does not require a literal `<script>` element: event-handler attributes, dangerous URLs, SVG, template injection, and unsafe DOM sinks can also create execution. Conversely, a script-shaped input is harmless when the application places it into a context that treats it strictly as text.

An injected script runs with the vulnerable origin's browser privileges. It can read and alter accessible DOM state, initiate authenticated actions, inspect web storage available to that origin, and read cookies that are not marked `HttpOnly`. It cannot automatically read every session cookie—`HttpOnly` exists specifically to block JavaScript access—but it may still act on behalf of the user from inside the trusted page.

### Stored XSS Turns One Payload into a Persistent Threat

Reflected XSS normally depends on a crafted request reaching a victim. Stored XSS persists the payload in a comment, profile, message, or other backend record. Every later rendering of that record can attack another viewer unless the application handles the value safely at output time.

The primary defense is context-aware output encoding. In an HTML text node, reserved characters can be represented as entities so the parser creates text rather than elements.

<details><summary>The visible difference is small, but the parser's interpretation changes completely:</summary>

```html
<!-- Unescaped Server Output (Vulnerable to Stored XSS) -->
<p>
  Email content:
  <script>
    alert("attack");
  </script>
</p>

<!-- Escaped Server Output (Secure Rendering) -->
<p>Email content: &lt;script&gt;alert('attack')&lt;/script&gt;</p>
```

</details>

Encoding is context-specific. HTML text, attribute values, URLs, JavaScript strings, CSS, and DOM APIs have different grammars. Applying HTML-body escaping inside a JavaScript program is not a general solution. Framework auto-escaping helps when developers remain within safe template APIs; deliberately inserting “raw HTML” reopens the boundary. If an application intentionally accepts a limited subset of HTML, it needs a vetted allowlist sanitizer in addition to correct output handling.

#### Content Security Policy adds a second boundary

A Content Security Policy tells the browser which resource sources and execution patterns the page accepts.

<details><summary>A minimal example is:</summary>

```http
Content-Security-Policy: script-src 'self' https://example.com
```

Under the shown policy, ordinary inline script is blocked while a script from an allowed source may load:

```html
<!-- Disallowed by CSP (Inline script blocked) -->
<script>
  alert("blocked");
</script>

<!-- Allowed by CSP (External script from trusted origin) -->
<script src="https://example.com/app.js"></script>
```

</details>

CSP is defense in depth, not a substitute for encoding. Broad host allowlists, `unsafe-inline`, unsafe dynamic script creation, compromised approved origins, or missing coverage can weaken it. Nonce- or hash-based policies can provide tighter control over which scripts execute.

### SQL Injection Confuses Query Syntax with Data

<details><summary>SQL injection occurs when an application constructs a query by concatenating or interpolating untrusted input into SQL source text:</summary>

```python
query = f"SELECT * FROM users WHERE username = '{user_input}'"
```

</details>

The database receives one string. It has no reliable way to distinguish the developer's intended syntax from quotes, comments, operators, or statement separators contributed by the user.

<details><summary>A destructive payload produces this statement:</summary>

```sql
SELECT * FROM users WHERE username = 'malan'; DELETE FROM users; --';
```

</details>

Whether stacked statements actually execute depends on the database, driver, permissions, and configuration. The underlying vulnerability does not: attacker input has entered the SQL grammar.

<details><summary>Authentication bypasses often use a Boolean tautology. A vulnerable query can become:</summary>

```sql
SELECT * FROM users WHERE username = 'malan' AND password = '' OR '1' = '1';
```

</details>

Under the illustrated precedence and query structure, its logic reduces to:

$$
\text{WHERE Clause} = (\text{user} = \text{'malan'} \land \text{pass} = \text{''}) \lor (\text{'1'} = \text{'1'})
$$

$$
\text{Evaluation} = \text{FALSE} \lor \text{TRUE} \equiv \text{TRUE}
$$

The query can return rows even though the password predicate failed. A complete authentication system should not compare plaintext passwords in SQL at all: it should retrieve the account's salted password verifier and perform the appropriate password-KDF verification in application code.

#### Parameter binding preserves the boundary

Prepared statements send query structure and values through separate channels. The placeholder remains part of the SQL program, while the bound value remains data.

<details><summary>Application code binds the values through the database driver:</summary>

```python
# Secure Python Implementation using Parameterized Queries
cursor.execute("SELECT * FROM users WHERE username = ? AND password = ?", (user_input, pass_input))
```

</details>

The security property is stronger than “automatically escaping quotes.” The driver encodes and binds a value according to the database protocol, so its characters are not reparsed as SQL syntax in the parameter position. Placeholder styles vary by library, and parameters cannot stand in for arbitrary identifiers or query keywords; dynamic table names, sort directions, and similar structural choices need strict allowlists or safe query builders.

Least-privilege database credentials limit the blast radius if a flaw survives. An application component that needs only a narrow set of reads and writes should not connect as a database administrator.

### Command Injection Crosses into the Operating System

Command injection repeats the same boundary failure at the shell. A program builds one command string from trusted text and user input, then asks a shell to parse it:

<details><summary>Code</summary>

```python
import os

# Vulnerable Code: Unescaped string passed to system shell
domain = input("Enter domain: ")  # Input: example.com; rm -rf /
os.system("nslookup " + domain)

# Executed Command in OS Shell:
# nslookup example.com; rm -rf /
```

</details>

Shell metacharacters can transform an expected hostname into additional commands. The safest remediation is usually to avoid a shell entirely: call a well-scoped library API or launch a fixed executable with a structured argument array and `shell=False`, then validate the argument against the application's expected domain. Escaping a hand-built shell string is fragile and shell-specific.

Code injection through `eval()` is related but distinct. It hands a string to a language interpreter rather than necessarily to an operating-system shell. In either case, accepting untrusted input as source code grants the attacker the parser's power.

### The Client Is Not a Security Authority

Browser validation makes forms friendlier, but the browser runs on hardware controlled by the requester. A user can change the DOM, suppress JavaScript, replay a request, or send raw HTTP without loading the page at all.

Client-side controls prevent mistakes and provide immediate feedback, but they cannot enforce a security decision against a malicious client. The server must independently validate types, lengths, formats, ranges, state transitions, ownership, permissions, and business invariants.

<details><summary>Developer tools make the trust boundary visible:</summary>

```html
<!-- Server-sent HTML form with client-side restrictions -->
<form action="/submit" method="POST">
  <input type="text" name="username" required />
  <input type="checkbox" name="agree" disabled />
  <button type="submit">Submit</button>
</form>

<!-- Attacker Modifies DOM in DevTools to: -->
<form action="/submit" method="POST">
  <input type="text" name="username" />
  <!-- 'required' removed -->
  <input type="checkbox" name="agree" />
  <!-- 'disabled' removed -->
  <button type="submit">Submit</button>
</form>
```

</details>

Removing `required` or `disabled` is only one route. A server that never receives a legitimate page request must still reject the same unauthorized payload. Client logic can improve usability; it cannot serve as the final source of truth.

### CSRF Exploits Ambient Browser Credentials

Cross-site request forgery does not inject code into the target application. Instead, it induces an authenticated browser to send an unwanted request. Cookies are ambient credentials: subject to their attributes and request context, the browser may attach them automatically even when another site initiated the navigation or form submission.

A state-changing GET endpoint is especially dangerous because many browser features, crawlers, previews, and prefetchers treat GET as safe.

<details><summary>An attacker can trigger it with an apparent image load:</summary>

```html
<img src="https://amazon.com/buy?item=123" />
```

</details>

HTTP defines GET as a safe method by intended semantics; “safe” and “idempotent” are separate properties. Applications must not attach state changes such as purchases or transfers to GET.

<details><summary>Changing the endpoint to POST is not sufficient. An attacker can submit a cross-origin form automatically:</summary>

```html
<form id="csrfForm" action="https://amazon.com/buy" method="POST">
  <input type="hidden" name="item" value="123" />
</form>
<script>
  document.getElementById("csrfForm").submit();
</script>
```

</details>

The browser's Same-Origin Policy generally prevents the attacker's script from reading the target response, but it does not by itself prevent the browser from sending the request. That send-versus-read distinction is the heart of CSRF.

<details><summary>A synchronizer token adds a value that a third-party origin should neither know nor be able to predict:</summary>

```html
<input type="hidden" name="csrf_token" value="1234abcd_secret_random" />
```

</details>

The simplified validation model is:

$$
\text{Request Authorized} \iff \text{Token}_{\text{Submitted}} == \text{Token}_{\text{Session}}
$$

For an independently uniform $b$-bit token, a single blind guess has probability:

$$
\text{Attacker Token Guess Probability} = \frac{1}{2^b}
$$

Token equality alone does not establish full authorization. The server must also validate the authenticated session, requested action, resource ownership, and all business rules. Tokens should be generated with a cryptographically secure random source, bound appropriately to the session or request, protected from leakage, and compared through a safe implementation. XSS can often defeat token-based CSRF protection because same-origin injected code may read or submit the token.

The shown token is an illustrative placeholder, not a recommended production length or generation method. Additional defenses include checking `Origin` or, carefully, `Referer`; requiring custom headers for API requests; and setting session cookies with an appropriate `SameSite` policy. `SameSite=Strict` and `SameSite=Lax` have different behavior, and Lax may still send cookies on certain top-level cross-site navigations, so the attribute should be chosen with the application's flows and threat model in mind.

### Memory Safety Extends the Boundary into Native Code

Injection vulnerabilities let a parser reinterpret data as instructions. A stack buffer overflow can change execution more directly by writing beyond an allocated object and corrupting nearby control data.

A traditional stack frame may place a local buffer before a saved frame pointer and return address. The source models the offset as:

$$
\text{Address}_{\text{Return}} = \text{Address}_{\text{BufferStart}} + \text{Size}_{\text{Buffer}} + \text{Offset}_{\text{EBP}}
$$

<details><summary>Compiler optimization, architecture, ABI, alignment, stack canaries, omitted frame pointers, and other local variables all change the actual arrangement.</summary>

```c
// Vulnerable C Code: Unchecked buffer copy
void search_function(char *input) {
    char buffer[16];          // 16 bytes allocated on stack
    strcpy(buffer, input);    // Copies input without bounds check
}

// Attack Input: 16 bytes payload + 8 bytes padding + 8 bytes Target Address
// Stack Memory Corruption Layout:
// [ Buffer (16B) ] [ Saved EBP (8B) ] [ RETURN ADDRESS (Overwritten with Shellcode Pointer) ]
```

</details>

`strcpy` has no destination-capacity argument, so a long input can write beyond `buffer`. Simply replacing it with `strncpy` is not a universal fix because truncation and null-termination semantics are easy to misuse. The stronger approaches are to carry lengths explicitly, use APIs with well-understood bounds, test boundary behavior, and prefer memory-safe languages for new components where practical. Safe-language guarantees substantially reduce ordinary out-of-bounds memory corruption, although unsafe extensions, foreign-function interfaces, native runtimes, and logic errors remain possible.

Modern exploit mitigations add layers:

- Stack canaries detect some overwrites before returning.
- ASLR makes useful addresses less predictable.
- DEP or NX prevents execution from data pages such as the stack.
- Control-flow protections constrain indirect branches and returns.

These measures raise exploitation cost but do not repair the original memory error. Attackers may use information leaks, return-oriented programming, or other techniques to work around individual mitigations.

### Provenance and Vulnerability Management Complete the Picture

Code signing does not prove that software is safe. It proves that a particular key authorized a particular artifact and that the signed bytes have not changed. Its value depends on trustworthy identity-to-key binding, protected signing keys, secure build systems, and reliable update metadata. Application stores and package managers apply different mixtures of signatures, repository metadata, hashes, review, and sandboxing; no single workflow guarantees the absence of vulnerabilities or malicious behavior.

Once a flaw is discovered, several systems answer different operational questions:

- **CVE** gives a publicly known vulnerability a stable identifier.
- **CVSS** describes technical severity, not the organization's complete risk.
- **EPSS** estimates the probability of exploitation in a defined future window.
- **KEV** records evidence that a vulnerability is known to be exploited.

Security teams should combine those signals with asset exposure, business impact, available mitigations, and their own threat intelligence. A critical score on an unreachable laboratory host may matter less immediately than a lower-scored flaw on an internet-facing system under active exploitation. Coordinated disclosure and bug-bounty programs can help researchers report defects before they become public attack paths.

Protecting an interaction does not make every observer disappear. Even when authentication, cryptography, transport security, and application validation all work correctly, ordinary browsing can still expose metadata to servers, embedded services, network operators, resolvers, and the device itself. Privacy is therefore the final trust-boundary question: who learns what, at which layer, and for how long?

## 5. Privacy: Why Private Browsing Isn’t Anonymous

Closing a private-browsing window can erase the history on a laptop without erasing a single record held elsewhere. The destination server may still retain an access log. An embedded analytics company may have linked the visit to activity on other sites. A network provider may have observed the domain lookup, and the browser itself may have revealed enough device characteristics to recognize the same user later.

Online privacy is therefore not one switch. It is the ability to understand and control which parties learn what, at which layer, and for how long. The browser, web server, third-party tracker, internet provider, DNS resolver, anonymity network, and operating system all see different parts of an interaction. Following those observers in sequence explains both why familiar privacy tools have limits and how referrer policies, anti-fingerprinting measures, HTTPS, encrypted DNS, Tor, and device permissions reduce exposure.

### Local History Is Only One Copy of the Record

Browsers keep a local history of visited URLs, page titles, and timestamps to provide autocomplete, restore sessions, and make earlier pages easy to find. Anyone who gains access to the browser profile—or to an account that synchronizes it—may gain access to that history as well. Clearing selected browsing data can remove local records, cookies, cache entries, or saved credentials, depending on which options the user chooses.

That action affects the client, not the systems already contacted. A web server commonly writes an entry for every request it handles.

<details><summary>A sample combined access-log entry contains the client address, timestamp, request, status, referrer, and user agent:</summary>

```text
192.0.2.45 - - [03/Aug/2026:21:00:00 +0000] "GET /cats.html HTTP/1.1" 200 4523 "https://google.com/search?q=cats" "Mozilla/5.0 (Macintosh; Intel Mac OS X 10_15_7)"
```

</details>

Such logs support debugging, performance analysis, security investigations, and traffic measurement. They can also reconstruct behavior: an IP address suggests a network origin, a timestamp orders events, a path reveals the requested resource, and a user-agent string describes the client software. None is a perfect identity field. An address may be shared through network address translation or represent an upstream proxy, and a user agent describes software rather than proving which person used it. Correlation across fields and repeated events is what makes the record more revealing: several moderately identifying fields can form a much more distinctive record when combined.

Server logs are not automatically permanent; retention depends on operational policy, storage, contracts, and applicable rules. They are nevertheless outside the direct control of a person clearing local browser data. Privacy begins by recognizing that the same interaction can leave several independently retained copies.

### Referrer Headers Can Reveal the Page Behind a Click

When a page causes the browser to request another resource, the browser may include a `Referer` header identifying the page that initiated the request. The protocol field is historically misspelled—`Referer`, not `Referrer`—and that spelling remains part of web infrastructure.

A permissive request could disclose a complete source URL such as `https://google.com/search?q=cats`. That information is useful for analytics because a destination can learn which site or campaign sent the visitor. It can also expose query terms, internal paths, or sensitive parameters if an application places them in a URL. This is why secrets and session identifiers should not be encoded in URLs in the first place.

<details><summary>A site can reduce the disclosure by setting an explicit response policy:</summary>

```http
Referrer-Policy: no-referrer
```

</details>

Different policies make different trade-offs. `unsafe-url` permits a full source URL, `origin` reduces the value to the source scheme and host, and `no-referrer` suppresses the field. The relationship is summarized by:

$$
\text{Header}_{\text{Referer}} = \begin{cases} \text{Scheme} \| \text{Host} \| \text{Path} \| \text{Query} & \text{Policy: unsafe-url} \\ \text{Scheme} \| \text{Host} & \text{Policy: origin} \\ \emptyset & \text{Policy: no-referrer} \end{cases}
$$

The notation is conceptual: an origin can also include a port, and actual behavior depends on the navigation context and chosen policy. A policy such as `strict-origin-when-cross-origin` keeps more information for same-origin requests, sends only the origin to a different secure origin, and omits the referrer on a secure-to-insecure downgrade.

<details><summary>The difference between a permissive full referrer and an origin-only referrer appears directly in the request:</summary>

```http
<!-- Default Unrestricted Referrer Header (Leaking Search Query) -->
GET /cats.html HTTP/1.1
Host: example.com
Referer: https://www.google.com/search?q=cats

<!-- Referrer Header Restricted by 'origin' Policy -->
GET /cats.html HTTP/1.1
Host: example.com
Referer: https://www.google.com/
```

</details>

The “default unrestricted” label is an illustration of the unsafe case, not a universal description of modern browser behavior. Site policy, browser defaults, and privacy tools may all reduce the value. Explicit policy is still important because it makes the site's disclosure choice deliberate.

Applications should not treat `Referer` as dependable proof of where a request came from. Legitimate browsers may suppress it, and privacy controls may remove it. Referrer checks can supplement other context, but robust cross-site request forgery defenses require purpose-built controls rather than assuming this optional header will always be present.

### Fingerprinting Replaces a Stored Identifier with a Statistical One

Deleting a cookie removes a value stored by the browser. Browser fingerprinting works differently: a site observes attributes that the browser and device expose and combines them into a profile. Passive signals include the public IP address and user-agent header.

<details><summary>JavaScript can add screen dimensions, color depth, time zone, language, processor concurrency, approximate device memory, and touch capabilities:</summary>

```javascript
// Script executed on client to extract environment parameters
const fingerprint = {
  userAgent: navigator.userAgent,
  screenRes: `${screen.width}x${screen.height}x${screen.colorDepth}`,
  timeZone: Intl.DateTimeFormat().resolvedOptions().timeZone,
  language: navigator.language,
  hardwareConcurrency: navigator.hardwareConcurrency, // CPU Cores
  deviceMemory: navigator.deviceMemory, // RAM in GB
  touchPoints: navigator.maxTouchPoints,
};

console.log(fingerprint);
```

</details>

Scripts can also test rendering behavior, canvas output, available fonts, and other browser capabilities. Browsers generally do not provide a simple authoritative list of installed extensions, but a site's code may infer some extensions from observable changes or exposed resources. No one attribute needs to be unique. Millions of devices may share a resolution, language, or time zone, but a rarer combination can distinguish one browser from much of the population. The attributes are correlated, noisy, and may change over time, so fingerprinting is probabilistic rather than a perfect serial number.

It can still be powerful. If a site associates a fingerprint with an account when the user eventually signs in, it may link earlier observations that produced a sufficiently similar profile. Anti-fingerprinting browsers reduce this advantage by standardizing or limiting exposed values, partitioning state, or otherwise making individual users harder to distinguish from a larger crowd.

### Embedded Trackers Build Cross-Site Profiles

Cookies solve a legitimate state problem: they let a stateless web protocol maintain a shopping cart or authenticated session. A session cookie usually lasts for a browsing session, while a persistent cookie carries an expiration or `Max-Age` and can retain an identifier much longer.

The privacy impact depends on context. A first-party cookie belongs to the site the user is visiting. A third-party cookie is associated with another domain whose image, script, analytics library, or advertisement is embedded in the page. If several unrelated sites embed the same third party and the browser allows that party to receive one unpartitioned identifier, the tracker can connect those visits.

<details><summary>The first page might include an otherwise ordinary remote image:</summary>

```html
<!-- HTML on https://harvard.edu -->
<head>
  <title>Harvard</title>
</head>
<body>
  <!-- Embedded third-party tracking asset -->
  <img src="https://example.com/ad.gif" alt="Advertisement" />
</body>
```

The browser then contacts the embedded domain, potentially revealing the first-party site in the referrer and accepting a persistent identifier in the response:

```http
<!-- Client Request to Third-Party Server -->
GET /ad.gif HTTP/1.1
Host: example.com
Referer: https://harvard.edu

<!-- Response from Third-Party Server Setting Persistent Cookie -->
HTTP/1.1 200 OK
Set-Cookie: ID=1234abcd; Max-Age=31536000; Path=/
```

</details>

On another site containing an asset from the same third party, the browser can return `ID=1234abcd`. Imagine that `harvard.edu`, `yale.edu`, and `stanford.edu` all embed the same asset. Each university may see only its own visitors, while `example.com` receives three requests carrying the same identifier and a referrer naming each embedding site. The tracker—not necessarily any one first-party publisher—can then place the events in one history. Formally:

$$
\text{Profile}(U_{\text{ID}}) = \bigcup_{k=1}^{M} \left( \text{Domain}_k, \text{Timestamp}_k, \text{Referer}_k \right)
$$

$U_{\text{ID}}$ is the shared identifier, $M$ is the number of participating sites visited, and each tuple records a site, time, and referrer. The union shows how an advertising or analytics platform with broad reach becomes a centralized observation point across otherwise independent domains.

This transcript depicts the classic unpartitioned third-party-cookie mechanism. In a modern cross-site context, cookie delivery may require attributes such as `SameSite=None; Secure`, and a browser may still block or partition it. Actual behavior depends on the browser, mode, user settings, and tracking protections. Blocking one mechanism does not end the incentive to correlate visits, however.

<details><summary>Identifiers can also travel in links:</summary>

```http
GET /ad_engagement?click_id=1234abcd&campaign_id=23 HTTP/1.1
Host: example.com
```

</details>

A query parameter is part of the request URL, so it can be processed by the destination and recorded in access logs independently of cookie storage. Link decoration is not an automatic universal bypass—the identifier must still be created, propagated, and associated with other data, and privacy tools may remove known tracking parameters—but it illustrates why blocking third-party cookies addresses only one tracking channel.

### Private Browsing Protects the Device Session, Not the Network

A private or incognito window creates a temporary browser context separated from the ordinary profile. It does not add visits to the normal local history, and it discards the private context's cookies and site storage when that private session ends. This is useful on a shared device and helpful when a user wants a clean session that is not already signed in.

The boundary is local. The server still receives requests and can write access logs. The public IP address and browser attributes remain observable, so fingerprinting may still correlate activity. The internet provider still carries the traffic, and locally installed keyloggers, management tools, or other privileged software remain outside the browser's protection. Private mode minimizes persistent client-side state; it does not promise anonymity.

### HTTPS Prevents Ordinary In-Path Header Injection

Ordinary cookies are under browser control, but a network intermediary can modify unencrypted HTTP. Some carrier tracking systems have used header enrichment: the intermediary adds a subscriber identifier to a plaintext request after it leaves the browser. Because the value is not stored in the browser, deleting local cookies or opening a private window cannot remove it.

<details><summary>The before-and-after request can look like this:</summary>

```http
<!-- Original Request Sent by Client Browser -->
GET /index.html HTTP/1.1
Host: example.com

<!-- Request Transformed by ISP Intermediate Router -->
GET /index.html HTTP/1.1
Host: example.com
X-UIDH: 1234abcd_unique_telecom_subscriber_id
```

</details>

The simplified protection condition is:

$$
\text{Header Injection} = \begin{cases} \text{Possible (Vulnerable)} & \text{if Protocol} = \text{HTTP} \\ \text{Blocked (Protected)} & \text{if Protocol} = \text{HTTPS (TLS)} \end{cases}
$$

TLS encrypts and authenticates the HTTP headers and body between the client and the TLS endpoint. An ordinary on-path carrier can still observe routing metadata, but it cannot silently insert `X-UIDH` into that protected request without breaking the connection's integrity. The model assumes correct certificate validation and uncompromised endpoints; a trusted inspection proxy or software controlling the device creates a different trust boundary.

### Encrypted DNS Moves Visibility to a Chosen Resolver

HTTPS protects an application's request content, but reaching a domain commonly begins with the Domain Name System. Classic DNS sends queries over UDP or TCP port 53 without encrypting the question between the client and its recursive resolver. A local network or provider that can observe that path may learn which names the device resolves, although caching and shared infrastructure mean a query log is not a perfect one-to-one record of page visits.

<details><summary>DNS over HTTPS carries queries inside HTTPS on port 443, while DNS over TLS uses a dedicated TLS connection, commonly on port 853. The difference is visible in these commands:</summary>

```bash
# Standard Unencrypted DNS Query (Port 53 UDP) - Visibly leaks 'harvard.edu' to ISP
$ dig @192.168.1.1 harvard.edu

# DNS over HTTPS (DoH) Query (Port 443 HTTPS) - Encrypted payload
$ curl -H 'accept: application/dns-json' 'https://cloudflare-dns.com/dns-query?name=harvard.edu&type=A'
```

</details>

Encrypted DNS prevents a passive observer on the local path from reading the query contents. It does not eliminate observation; it moves query visibility to the recursive resolver handling the encrypted request, while the network can still see that the client connected to that resolver. Resolver choice, retention policy, and trust therefore remain part of the privacy design.

### Tor Distributes Trust Across a Circuit

A VPN encrypts traffic to one gateway and makes that provider a concentrated observation point. Tor uses a circuit of relays so that, under its normal threat model, no single relay sees both the user's source address and the final destination. The entry or guard relay sees the client and the next hop. A middle relay sees neighboring relays. The exit relay connects to the destination but does not directly know the original client address.

The layered concept can be represented as:

$$
C_{\text{Onion}} = \text{Encrypt}_{K_{\text{Guard}}}\Big(\text{Node}_{\text{Middle}} \,\|\, \text{Encrypt}_{K_{\text{Middle}}}\big(\text{Node}_{\text{Exit}} \,\|\, \text{Encrypt}_{K_{\text{Exit}}}(M)\big)\Big)
$$

$M$ is the message, the $K$ values represent relay keys, and each layer contains only the forwarding information needed for the next stage. The equation captures onion routing's nested visibility, but it is not a wire-level description of Tor. Tor builds relay-specific session keys as it extends a circuit and applies layered symmetric cryptography to traffic; it does not repeatedly encrypt every data message with three public keys exactly as the notation suggests.

Distribution reduces the need to trust one provider, but it does not prove unconditional anonymity. Colluding relays or an observer capable of correlating traffic timing and volume can weaken the design. The exit path also needs application encryption: if the destination uses plain HTTP, the exit relay may read or alter the payload. HTTPS remains necessary even when Tor conceals the client's network origin from the destination.

### Operating-System Permissions Protect the Sensors Beside the Browser

Privacy extends beyond network traffic. Phones and computers contain cameras, microphones, contact databases, and location sensors that can reveal a user's physical environment and movements. Native operating-system permissions govern applications, while browsers add site-level permission decisions within the browser process. Both layers can offer choices such as allowing location only while an app or site is in use or granting broader background access.

The protection works only when the decision is meaningful. Repeated prompts can create permission fatigue, and an “always allow” choice may expose far more data than a feature needs. Users should treat sensor access as a continuing grant, not a one-time nuisance, and periodically review which applications still need it. Developers should request the narrowest access that supports the feature and make the resulting data use transparent.

### A Practical Privacy Checklist

- Treat browser-history deletion and private mode as local-device controls, not anonymity tools.
- Assume that destination servers may retain request metadata independently of browser settings.
- Keep sensitive information and session identifiers out of URLs, and set an explicit, restrictive `Referrer-Policy`.
- Limit fingerprinting surfaces where possible and prefer privacy tools that make browsers less distinguishable rather than merely deleting cookies.
- Restrict or partition third-party state, and remain aware that identifiers can also travel through decorated links and server logs.
- Use HTTPS everywhere to protect request content and integrity from ordinary network intermediaries.
- Use encrypted DNS when appropriate, while choosing the resolver with the same care given to any other trusted intermediary.
- Use Tor when the goal requires distributing network trust, and combine it with HTTPS to protect traffic beyond the exit relay.
- Review operating-system permissions regularly and grant applications only the sensor access they need.
