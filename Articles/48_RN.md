# Building Reliable Networks: Operations, Security, and Troubleshooting

A network's reliability depends on how well people can understand its behavior, control access, and restore service when something fails. An unlabeled cable delays a repair. An incomplete address history weakens an investigation. An overprivileged account extends the damage a compromised credential can cause. These problems connect network operations, security, and troubleshooting at every layer.

The same connections provide a practical way to improve the system: establish the intended behavior, enforce its boundaries, and use evidence to explain departures from it. Accurate documentation gives monitoring results context. Recovery objectives determine how much redundancy and preparation are needed. Identity and segmentation define which interactions are permitted. During an incident, focused tests distinguish failures in physical links, addressing, routing, and applications. Troubleshooting brings these practices together by tracing a reported symptom to a supported explanation and a verified remedy.

The work closes when the affected user can complete the original task, the evidence supports the diagnosis, and the records reflect the resulting network. Each resolved incident can then improve the next design decision, monitoring rule, or recovery procedure. That cycle makes reliability a maintained property of the service.

## 1. Make the network observable and recoverable

Reliable operations require records of the network's connections, equipment, service commitments, and dependencies. Documentation describes what should exist, telemetry reveals current behavior, and recovery planning provides a tested route back to service.

### Build an accurate picture of the network

Different maps answer different operational questions:

| Documentation           | What it records                                            |
| ----------------------- | ---------------------------------------------------------- |
| Physical network map    | Hardware locations, interfaces, and cable connections      |
| Logical network map     | Subnets, routing relationships, sites, and WAN connections |
| Rack diagram            | Equipment positions by rack and rack unit                  |
| Cable map or floor plan | Cable runs, wall outlets, and patch-panel ports            |

Consistent labels let a technician trace a desk outlet to a patch panel in an **intermediate distribution frame (IDF)** or **main distribution frame (MDF)**. Connect physical records with MAC addresses and switch ports at Layer 2, then IP addresses and routing at Layer 3 of the **Open Systems Interconnection (OSI)** model. These relationships help trace a reported IP address to equipment without assuming one address per interface.

Asset tags link devices to purchase dates, components, warranties, support contracts, assigned users, and recorded locations. Keep assignments current: an employee's office does not establish a mobile laptop's present location. Software inventory also supplies installation counts for licensing, interpreted under the applicable agreement.

**IP address management (IPAM)** adds subnet utilization and address history. **Dynamic Host Configuration Protocol (DHCP)** can lease the same address to different devices over time, so an investigation needs the address and timestamp. Lease records identify assignments; device and authentication records may be needed to identify a person. Together, these records support both incident investigation and capacity planning.

### Manage the entire infrastructure lifecycle

A **service level agreement (SLA)** defines service commitments, often including availability. Convert the percentage into downtime to understand its operational demands.

Maintain wireless site surveys showing access points, frequencies, coverage, and interference, including neighboring networks. Track vendor definitions and dates for **end of life (EOL)** and **end of support (EOS)**; replacement must precede the loss of required support and security updates.

Embedded equipment also needs firmware maintenance. Confirm image compatibility and a tested fallback where rollback is supported. Remediation can be slow: Cisco Talos reported three Trane ComfortLink II vulnerabilities in April 2014, and the final fix arrived in January 2016, about 21 months later. That interval measures remediation lag, without establishing exploitation. Track both fix availability and installation. [Cisco Talos disclosure](https://blog.talosintelligence.com/trane-iot/)

Change procedures should define the approved window, deployment steps, validation criteria, and rollback method. Decommissioning should remove equipment, sanitize or destroy storage as appropriate, account for retention requirements, and update inventory. A device's information remains part of its lifecycle until disposal is complete.

### Observe device health, traffic, and events together

Combine evidence sources to explain the same incident:

| Evidence               | Main question                             |
| ---------------------- | ----------------------------------------- |
| SNMP metrics           | How is the device performing?             |
| Flow records           | Who communicated, when, and how much?     |
| Packet captures        | What crossed the capture point?           |
| Syslog and SIEM events | What did devices and applications report? |

**Simple Network Management Protocol (SNMP)** lets a network management station query device agents, commonly on UDP port 161. A **Management Information Base (MIB)** defines exposed objects, identified through hierarchical **object identifiers (OIDs)**. For example, `1.3.6.1.2.1.11.28.0` identifies the scalar instance of `snmpOutGetResponses`; the final `.0` denotes that instance. Vendor MIB files explain proprietary objects.

A MIB walk discovers objects; repeated polling records behavior. A persistent fault may appear at the next poll if the measured value exposes it and the query succeeds. Retries and communication failures add delay. Unsolicited **traps**, commonly sent to UDP port 162, can report events such as a threshold increase in cyclic redundancy check (CRC) errors. They complement regular polling.

SNMPv1 and SNMPv2c use community strings without encryption; familiar names such as `public` and `private` provide no protection. SNMPv3 requires configuration: `noAuthNoPriv` supplies neither authentication nor encryption, `authNoPriv` authenticates, and `authPriv` adds encryption. Selecting version 3 alone does not enable both protections.

**Flow records and captures provide different detail.** A common flow key contains source and destination IP addresses, source and destination ports, and protocol. Counters and timestamps identify heavy conversations. Collectors store these records for reporting; analyzers such as Wireshark expose individual frames. Encrypted payloads require suitable decryption information to become readable.

**Port mirroring**, or **Switched Port Analyzer (SPAN)**, copies selected interface or VLAN traffic to a monitoring port. Remote SPAN carries copies across switches; a physical tap observes a particular link. Size the monitoring path carefully: an oversubscribed destination can lose mirrored packets. A passive sensor sees copies; blocking delivery requires enforcement in the forwarding path or a separate response mechanism.

**Baselines give measurements context.** One possible anomaly rule is:

$$
|M(t)-\bar{M}|>k\sigma_M
$$

Here, $M(t)$ is the current measurement, $\bar{M}$ the baseline mean, $\sigma_M$ its standard deviation, and $k$ the sensitivity setting. Baselines must reflect workload patterns: a scheduled backup can be normal for its hour despite differing from the day's average.

A **security information and event management (SIEM)** platform correlates events. Syslog severity runs from 0, Emergency, through Alert, Critical, Error, Warning, Notice, and Informational to 7, Debug. Facilities identify categories; timestamps establish sequence. Retain events for investigative value as well as urgency.

Authentication failures provide leads, without establishing malicious intent. Search syntax and message prefixes affect which events a query finds. Correlate account activity with firewall timestamps, endpoints, ports, and traffic volume, then compare those results with metrics and packet evidence. Missing fields may reflect logging configuration rather than absent activity.

### Define recovery before an outage happens

**Disaster recovery (DR)** planning defines how to restore a service or location within acceptable disruption and data-loss windows.

| Measure                           | Meaning                                                                       |
| --------------------------------- | ----------------------------------------------------------------------------- |
| Recovery time objective (RTO)     | Target maximum service interruption                                           |
| Recovery point objective (RPO)    | Required recovery point, commonly expressed as a tolerable data-loss interval |
| Mean time to repair (MTTR)        | Average repair or restoration duration under a consistent definition          |
| Mean time between failures (MTBF) | Average operating time per failure                                            |

RTO and RPO are planning requirements; measured recovery results must be compared with them. A one-hour RTO must cover all necessary restoration steps, including hardware replacement, application startup, and data recovery. A backup's age matters only if it is usable. Set requirements by service: transactional records and static content may justify different targets.

For $n$ incidents, calculate MTTR from the sum of restoration durations divided by $n$, using consistent start and end points. Calculate MTBF from total operating time divided by failures. An MTBF of 20 years is a statistical average, without guaranteeing an individual device's lifespan or determining the required spares.

A simplified repairable-system model estimates long-run availability:

$$
\text{Availability}=\frac{\text{MTBF}}{\text{MTBF}+\text{MTTR}}
$$

Higher MTBF and lower MTTR improve this estimate, but real service dependencies and failure modes require separate analysis.

Recovery-site choices determine how much work remains after an outage. **Cold sites** provide space and basic facilities; **warm sites** add some equipment and infrastructure; **hot sites** provide substantial production capability. Cost generally rises with preparation. A hot site's label alone establishes neither recovery time nor data freshness: replication and application dependencies still matter.

Use tabletop exercises to expose gaps in responsibilities, access, and dependencies. Full exercises must restore systems and operate through the alternate environment. Measure interruption and the recovered data point to determine whether the objectives are achievable.

### Design redundancy for the failure state

Redundancy works when the surviving infrastructure can carry the service. Check connectivity, state, capacity, and recovery timing under actual failure conditions.

In an **active-passive** firewall pair, one unit forwards traffic while the standby prepares to take over. Each needs sufficient independent connectivity. Heartbeats support detection, and supported synchronization preserves configuration or connection state. Missing heartbeats require thresholds and health checks: failure of the heartbeat link can cause **split brain**, with both units claiming the active role.

In an **active-active** pair, both units process traffic. Stateful inspection needs the context for both directions of each connection. Asymmetric routing can break connections when return traffic reaches a unit without that context.

Check the survivor's expected load:

$$
\text{Failure load ratio}=\frac{\text{Traffic}_{FW1}+\text{Traffic}_{FW2}}{\text{Capacity}_{single\ firewall}}
$$

Two equal units each running at 70% would leave the survivor facing 140% of its capacity. Reserve capacity or define how load will be reduced. Validate state synchronization, routing convergence, traffic redistribution, and application recovery together; a three-second heartbeat timeout does not establish three-second service restoration.

### Automate address assignment with DHCP and IPv6

DHCP allocates IPv4 addresses from a configured **scope**. A **lease** grants temporary use; a **reservation** associates a client identifier, often a MAC address, with a particular address.

The initial **DORA** exchange is Discover, Offer, Request, Acknowledge: the client finds servers, receives proposals, selects an offer, and receives confirmation. Clients use UDP 68; servers use UDP 67. A new client can broadcast from `0.0.0.0` to `255.255.255.255`, but offers and acknowledgments can be unicast when capabilities and flags permit.
A **DHCP relay** forwards client requests to a server on another subnet. Its `giaddr` field helps the server select the client subnet and return the response. A helper address pointing to the server therefore supports a DHCP-specific exchange, beyond merely making the server IP reachable.

Default lease timers are:

$$
T_1=0.5T_{lease},\qquad T_2=0.875T_{lease}
$$

At T1, the client attempts renewal with the original server. If unsuccessful, at T2 it broadcasts to rebind through an available server. The server can supply different timer values. An eight-day lease normally renews at day four, rebinds at day seven, and expires at day eight; the expired address can no longer be used.

DHCP options also supply masks, gateways, DNS servers, and service settings. A valid address with an incorrect resolver can still leave an application unusable.

IPv6 supports DHCPv6 and **stateless address autoconfiguration (SLAAC)**. Under SLAAC, hosts use **Neighbor Discovery Protocol (NDP)** Router Solicitations and Router Advertisements to obtain router and prefix information. A common configuration combines a 64-bit prefix with a host-generated 64-bit interface identifier.

Historical **Modified EUI-64** construction inserts `FF:FE` into a MAC address and inverts the universal/local bit. Identifiers that avoid embedding the MAC reduce tracking exposure from a stable hardware-derived value. **Duplicate Address Detection (DAD)** checks a tentative address on the link; a detected conflict prevents normal use. IPAM must account for these IPv6 behaviors alongside IPv4 leases.

### Make names resolve predictably with DNS

The **Domain Name System (DNS)** organizes names into a hierarchy of zones. A **fully qualified domain name (FQDN)** such as `www.example.com.` includes the final root dot, with additional subdomain levels possible.

An **authoritative server** publishes zone records. A **recursive resolver** retrieves and caches answers for clients. Without useful cached data or delegations, it follows referrals from root to top-level-domain servers and then the authoritative server. The client requests recursion; the resolver performs iterative queries. In a traditional primary/secondary setup, both servers answer authoritatively while updates transfer from the primary.

| Record   | Purpose                                   |
| -------- | ----------------------------------------- |
| SOA      | Zone administration and transfer metadata |
| A / AAAA | Name to IPv4 / IPv6 address               |
| CNAME    | Alias to another name                     |
| MX       | Domain to mail exchanger                  |
| TXT      | Application text, including SPF and DKIM  |
| NS       | Nameservers for zones or delegations      |
| PTR      | Name associated with a reverse lookup     |

A CNAME links an alias to another name, which may then resolve through A or AAAA records. These logical steps need not require separate round trips: a reply or cache may contain both. IPv4 reverse lookup reverses address octets under `in-addr.arpa`; `192.168.23.15` becomes `15.23.168.192.in-addr.arpa`.

Local settings also affect results. A hosts file can supply mappings before system-resolver DNS queries, although applications may resolve differently. Compare application behavior with explicit `dig` or `nslookup` queries.

A record's **time to live (TTL)** sets its ordinary cache lifetime in seconds. A TTL of 300 means five minutes; zero does not authorize ordinary caching. Lower values increase lookup work while allowing cached data to expire sooner. Lowering a published TTL does not shorten lifetimes already held in other caches.

**DNSSEC** authenticates resource-record sets through signatures and a chain of trust. DNSKEY supports verification, and a parent-zone DS record links to the child's key. Validation requires a trust anchor and appropriate proofs. It establishes origin and integrity, without encrypting queries or guaranteeing that the zone operator entered the intended value.

**DNS over TLS (DoT)** and **DNS over HTTPS (DoH)** encrypt transport between clients and their selected resolvers. DoT commonly uses TCP 853; DoH uses HTTPS, commonly port 443. Resolver selection and encrypted DNS policy affect organizational visibility and filtering.

### Keep clocks aligned and time sources trustworthy

Comparable timestamps connect address history, authentication, firewall events, and recovery measurements. Clock disagreement weakens investigations and can disrupt authentication.

**Network Time Protocol (NTP)** commonly uses UDP 123. Stratum 0 is a reference source, such as an atomic or GPS clock; stratum 1 servers connect directly to it, with higher strata downstream. Stratum describes hierarchy; source quality and network conditions determine actual accuracy.

A five-minute Kerberos skew tolerance is a common Windows default, subject to policy. Passing the clock check still leaves credential and ticket validation; excessive skew can reject otherwise valid authentication. [Microsoft clock tolerance](https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-10/security/threat-protection/security-policy-settings/maximum-tolerance-for-computer-clock-synchronization)

**Network Time Security (NTS)** establishes cryptographic material and opaque cookies through TLS-based **NTS key exchange (NTS-KE)** on TCP 4460. Subsequent NTP exchanges commonly remain on UDP 123 and use cookies with cryptographic authenticators. A cookie alone does not prove response validity.

**Precision Time Protocol (PTP)** can use hardware timestamping for finer synchronization than typical software NTP. Neither protocol name guarantees accuracy: hardware, clocks, and network conditions determine the result. Match synchronization to application needs and verify it.

### Control remote connectivity with VPNs

A **virtual private network (VPN)** protects carried traffic across an untrusted transport. A client or site tunnels to a **VPN concentrator**, implemented as an appliance, service, or firewall function. VPN encryption ends at the concentrator; application encryption such as HTTPS may continue beyond it. Some outer-connection properties remain observable.

**Client-to-site** VPNs connect individual endpoints, manually or through always-on policy. **Site-to-site** VPNs connect networks through gateways, generally without individual client tunnels. **Clientless access** exposes supported applications through a browser gateway; its scope depends on application integration.

A **full tunnel** carries covered corporate and internet traffic through the VPN. A **split tunnel** carries selected destinations through it while other traffic follows the endpoint's direct connection. Full tunneling increases concentrator demand and central inspection opportunities; split tunneling reduces that demand while limiting central visibility to the tunneled subset.

<details><summary>This Python example models destination selection without changing the host's routes:</summary>

```python
from ipaddress import ip_address, ip_network

corporate_subnets = [
    ip_network("10.0.0.0/8"),
    ip_network("172.16.0.0/12"),
    ip_network("192.168.1.0/24"),
]

def select_path(destination):
    address = ip_address(destination)
    if any(address in subnet for subnet in corporate_subnets):
        return "VPN_TUNNEL"
    return "DIRECT_INTERNET"

print(select_path("10.10.5.20"))    # VPN_TUNNEL
print(select_path("198.51.100.42")) # DIRECT_INTERNET
```

</details>

Routing still needs a path to the VPN endpoint and must account for exceptions. Gateway transit enables inspection only when controls are configured, and direct traffic may retain application encryption. Choose tunnel policy around routing, capacity, visibility, and the controls required on each path.

### Make administration secure, scalable, and recoverable

Management design determines who can reach devices, what they can change, and how they recover access during an outage. **Secure Shell (SSH)** encrypts terminal sessions; **Telnet** does not. **Remote Desktop Protocol (RDP)** and **Virtual Network Computing (VNC)** support graphical access, while **application programming interfaces (APIs)** expose structured operations.

Interactive shells suit device-level investigation; APIs integrate queries and changes with inventory and management software. Both can be automated. Define credentials, certificate validation, timeouts, error handling, retries, and logging explicitly. Structured calls alone do not guarantee concurrency or speed. Bulk changes require the same windows, validation, rollback, and recovery access as individual changes.

For read-only collection, this sequential Python loop checks HTTP errors and continues after a failed device. It requires Requests, a `NETWORK_API_TOKEN` environment variable, and device-specific hostnames, endpoints, and authentication settings. TLS certificate verification remains enabled.

<details><summary>Code</summary>

```python
import os
import requests

headers = {"Authorization": f"Bearer {os.environ['NETWORK_API_TOKEN']}"}
devices = ["switch1.example.com", "switch2.example.com"]

for device in devices:
    try:
        response = requests.get(
            f"https://{device}/api/v1/interfaces",
            headers=headers,
            timeout=(3, 10),  # Connection and read timeouts, in seconds
        )
        response.raise_for_status()
        print(device, response.json())
    except (requests.RequestException, ValueError) as error:
        print(f"{device}: {error}")
```

</details>

A **jump server**, or **bastion host**, centralizes administrative entry through a controlled path to internal devices. Harden it with restricted software, patching, **multi-factor authentication (MFA)**, and session logging. It may sit behind a VPN. MFA reduces password-misuse risk; device permissions still determine allowed actions.

**In-band management** relies on production connectivity. **Out-of-band (OOB) management** provides an independent path, such as a serial console or separately reachable management network. Console servers aggregate device consoles, with separate network, modem, or cellular transport supporting access.

Test independence against the intended failure. A console server reachable only through the failed production link cannot provide remote recovery through that link. Include management access in failover exercises, and use discovery, reachability tests, monitoring, and inventory together to confirm the resulting network.

## 2. Build security around identity and trust boundaries

Documentation and monitoring make a network understandable; security determines who may use it and how far failures can spread. An encrypted connection can still give an overprivileged account access to a flat network. Effective defenses combine identity, access, data protection, and containment.

### Start with security objectives and business risk

**Translate objectives into requirements.** The **CIA triad** describes three connected objectives:

| Objective       | Protection                                   | Representative controls                                |
| :-------------- | :------------------------------------------- | :----------------------------------------------------- |
| Confidentiality | Prevent unauthorized disclosure              | Encryption and access controls                         |
| Integrity       | Prevent unauthorized alteration              | Authenticated messages, signatures, controlled changes |
| Availability    | Keep services accessible to authorized users | Redundancy, recovery, capacity management              |

Access controls need legitimate-user recovery, encryption needs accessible keys, and redundant nodes need consistent policies. Consequences of failure determine the balance.

**Estimate loss and choose a treatment.** Single loss expectancy (SLE) multiplies asset value (AV) by exposure factor (EF), the estimated fraction lost. Annualized loss expectancy (ALE) also includes annualized rate of occurrence (ARO):

$$
\text{SLE}=\text{AV}\times\text{EF}, \qquad \text{ALE}=\text{SLE}\times\text{ARO}
$$

A USD 50,000 annual control reducing estimated annual loss from USD 200,000 to USD 20,000 yields USD 130,000 in estimated net benefit. Frequency and impact remain uncertain; comparisons require consistent periods and units. Safety, contracts, and severe-loss tolerance can also require controls.

**Inherent risk** precedes assessed controls; **residual risk** remains afterward. Controls can overlap or introduce shared dependencies, so their benefits cannot simply be added. Management can mitigate, avoid, transfer specified financial consequences, or accept risk. Insurance leaves the technical vulnerability intact.

**Assign governance responsibilities.** Record data flows, owners, third-party access, and applicable obligations. GDPR permits international transfers with applicable safeguards; it does not mandate universal EU storage. The HIPAA Security Rule covers electronic protected health information held by regulated entities; PCI DSS addresses payment-account-data environments. Each extends beyond individual technical settings. [European Commission transfer guidance](https://commission.europa.eu/law/law-topic/data-protection/international-dimension-data-protection/rules-international-data-transfers_en), [HHS Security Rule summary](https://www.hhs.gov/hipaa/for-professionals/security/laws-regulations/index.html), [PCI DSS overview](https://www.pcisecuritystandards.org/standards/pci-dss/)

### Protect data and establish cryptographic trust

**Match protection to the data’s state.** Data exists **in transit**, **at rest**, or **in use**. Copies can occupy several states simultaneously: a database row may be on disk, in memory, and crossing a network.

| State      | Example                     | Protection boundary                                       |
| :--------- | :-------------------------- | :-------------------------------------------------------- |
| In transit | Application traffic         | TLS or appropriately configured IPsec                     |
| At rest    | Files or database volumes   | Disk, volume, file, or database encryption                |
| In use     | Information being processed | Process isolation, access controls, execution protections |

Encryption transforms plaintext into ciphertext using a key. An **access control list (ACL)** supplies authorization rules, not an encryption key. Full-disk encryption protects removed storage when its keys are unavailable; decrypted files still need memory and transmission protections. Key management and endpoint security support those transitions.

**Verify integrity against a trusted reference.** Comparing a file’s hash with an expected digest detects differences only if the reference is trustworthy. An attacker replacing both can pass the check. Signatures or message authentication codes authenticate the reference.

For an ideal $n$-bit hash, two independent distinct inputs collide with probability $2^{-n}$. Finding any collision takes roughly $2^{n/2}$ trials because many pairs are compared. Matching one fixed digest is a different problem. Attempt counts and attack models determine success probabilities; collision resistance alone does not authenticate files.

**Bind identities to public keys.** **Public key infrastructure (PKI)** manages certificates, issuers, validation, and key lifecycles. A **certificate authority (CA)** signs a binding between identity information and a public key. A service’s leaf certificate typically chains through intermediate issuers to a locally trusted root.

Validation checks every signature and the trust anchor, plus hostname, validity, permitted usage, constraints, and applicable revocation requirements. A private CA serves clients provisioned with its trust anchor; publicly trusted CAs support broadly recognized chains. Importing a root alone does not guarantee acceptance.

Certificate issuance requires a private key, a **certificate signing request (CSR)**, and appropriate certificate extensions, including subject alternative names for server identities. Protect private keys on disk: OpenSSL’s `-nodes` option leaves generated keys unencrypted. [OpenSSL certificate documentation](https://docs.openssl.org/4.1/man1/openssl-x509/)

A **Web of Trust** distributes certification among peers, with participants deciding whose endorsements to accept.

### Give identities only the access they need

**Separate identity, authentication, and permission.** **Identity and access management (IAM)** coordinates account and credential lifecycles. Identification names an account, authentication verifies its identity claim, and authorization determines permitted actions.

**Least privilege** limits users, processes, and machines to necessary access. **Role-based access control (RBAC)** assigns permissions to roles and users to those roles. A user’s assigned permissions combine the permissions of every role; broad roles and accumulated memberships can still overprivilege that user.

For example, assigning a Shipping Staff group `ReadAndExecute` on warehouse files simplifies administration. Existing memberships, inherited ACLs, share permissions, deny rules, and conditional policies still affect effective access. Review obsolete memberships after job changes and avoid proliferating nearly identical roles.

**Combine distinct authentication factors.** **Multi-factor authentication (MFA)** combines recognized factors: knowledge, such as passwords; possession, such as cryptographic tokens; and inherent characteristics, such as biometrics. Two passwords remain one factor category. Location and behavior can inform risk decisions but do not automatically count as additional factors. Authenticators must also meet applicable requirements. [NIST authentication guidance](https://pages.nist.gov/800-63-4/sp800-63b.html)

**Geofencing** applies a location boundary to conditional access. Calculating distance from reported coordinates cannot authenticate those coordinates: GPS spoofing, inaccurate IP geolocation, and relayed connections can undermine the inputs.

Biometric matching trades false acceptance against false rejection. For systems where higher similarity scores indicate stronger matches, raising the threshold typically reduces false acceptance and increases false rejection. Their crossover is the **equal error rate**, also called **crossover error rate (CER)**. It helps compare systems but need not be the best operating threshold. Enrollment, presentation-attack resistance, and recovery matter: an exposed fingerprint cannot be replaced like a password.

**Connect services through AAA and federation.** **AAA** separates authentication, authorization, and **accounting**, which records access and activity. **Single sign-on (SSO)** supports multiple authorized services after authentication, subject to session lifetimes and reauthentication policies.

| Technology | Main role                                    | Common endpoint                   |
| :--------- | :------------------------------------------- | :-------------------------------- |
| RADIUS     | Network-access AAA                           | Traditionally UDP 1812/1813       |
| LDAP       | Directory queries and updates                | TCP 389; LDAPS commonly 636       |
| SAML       | Identity assertions between providers        | HTTPS workflows                   |
| Kerberos   | Ticket-based authentication                  | Key distribution center exchanges |
| TACACS+    | Administrative AAA and command authorization | TCP 49                            |

**Lightweight Directory Access Protocol (LDAP)** uses hierarchical **distinguished names (DNs)**, including common-name (`CN`) and organizational-unit (`OU`) components. Bind identity, search base, filter, and requested attributes are separate choices. TLS protects transport; directory permissions govern readable entries.

**Security Assertion Markup Language (SAML)** connects an **identity provider (IdP)** with a **service provider (SP)**. A signed assertion still requires audience, recipient, validity, and replay checks in its intended context.

**Kerberos** relies on a **key distribution center (KDC)** and **ticket-granting service (TGS)**. A **ticket-granting ticket (TGT)** contains identity, lifetime, and a client/TGS session key, encrypted under the TGS’s long-term key; client addresses are optional. The client also submits a session-key-protected authenticator. Timestamps and replay caches make clock consistency and ticket lifetimes operational dependencies.

Traditional RADIUS’s response authenticator binds response fields to the request authenticator and shared secret without encrypting the transaction. TACACS+ supports separate AAA exchanges and command authorization, but its traditional body protection is obfuscation with missing integrity protection, not an authenticated encrypted channel.

### Enforce boundaries with segmentation and firewalls

**Permit required relationships between zones.** **Network segmentation** limits communication and the paths available to a compromised account or device. Separate guests, workstations, public applications, and payment systems. A **demilitarized zone (DMZ)** separates externally accessible services from internal systems.

Treat inter-zone permissions as directional: source zone, destination, endpoint, and service must be explicit. A corporate accounting server’s permitted path into the **cardholder data environment (CDE)** remains a potential compromise path; blocking guest access alone cannot guarantee containment.

This IPv4 forwarding sketch permits one database connection:

```bash
iptables -P FORWARD DROP
iptables -A FORWARD -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT
iptables -A FORWARD -i eth1 -s 10.10.5.20 -o eth2 \
 -d 192.168.100.50 -p tcp --dport 3306 -j ACCEPT
```

Appending rules preserves earlier permits, and connection tracking can preserve existing sessions. Review the full ruleset and separately assess host traffic, IPv6, and application paths. Test required and prohibited flows.

**Read rules in evaluation order.** A **stateless filter** checks packet fields; a **stateful firewall** also tracks connections and appropriate return traffic. Under first-match evaluation, the earliest matching rule wins. A broad permit above a specific deny causes **rule shadowing**.

Default-deny policy blocks traffic without a matching permit, either implicitly or through an explicit default. Logging is separate: drops do not necessarily create records. Stateful zone policies distinguish permitted connection initiation from corresponding return traffic.

Implement zones, ACLs, inspection policies, and interface assignments using consistent target-platform syntax. Creating an ACL does not enforce it until the required policy attachment is complete. [Cisco zone-based firewall design](https://www.cisco.com/c/en/us/support/docs/security/ios-firewall/98628-zone-design-guide.html)

**URL and content filtering** adds context beyond addresses and ports. HTTPS hides complete paths and payloads from intermediaries unless endpoints or suitable inspection boundaries provide visibility. Permitting TCP 443 establishes no trust in a destination or its content.

### Protect switching at the network edge

Local attacks target address learning, trunks, and admission before reaching a routed firewall.

**Understand what a switch learns.** A traditional globally assigned 48-bit Ethernet address combines a 24-bit **organizationally unique identifier (OUI)** with 24 assigned bits. The first octet’s least significant bit distinguishes individual from group addressing. Locally administered and randomized addresses make MAC addresses unsuitable as immutable device identities.

A switch learns **source** addresses and forwards by **destination** address, associating addresses with ports and VLANs. Hardware storage is often called a **content addressable memory (CAM)** table. Unknown-unicast traffic floods eligible ports within its VLAN, respecting other controls. It neither becomes broadcast traffic nor crosses all VLANs; known destinations may continue forwarding normally.

**MAC flooding** attempts to exhaust learning capacity with many source addresses. Exhaustion depends on remaining capacity and the net rate of accepted entries after aging, which can differ from frame rate. It can increase unknown-unicast flooding without universally turning a switch into a hub.

**Limit learning on access ports.** **Port security** constrains accepted source addresses. Static or learning policies establish authorized addresses; unfamiliar addresses may become authorized while learning capacity remains.

| Violation mode | Typical response                                           |
| :------------- | :--------------------------------------------------------- |
| Protect        | Drop violating frames silently                             |
| Restrict       | Drop frames and increment counters; notify when configured |
| Shutdown       | Disable the port and generate configured notifications     |

A compact access-port example allows one learned address:

```text
interface GigabitEthernet0/2
 switchport mode access
 switchport access vlan 10
 switchport port-security
 switchport port-security maximum 1
 switchport port-security mac-address sticky
 switchport port-security violation shutdown
```

Sticky learning writes observed addresses to the running configuration; persistence requires saving it. Quotas must accommodate phones with downstream workstations and shared or virtualized endpoints. Copyable MAC addresses cannot replace cryptographic authentication.

**Prevent unintended trunks and VLAN hopping.** An **802.1Q trunk** carries multiple VLANs. Its tag includes a type identifier, priority, drop eligibility, and a 12-bit VLAN identifier. IDs 1–4094 are usable, though switch capacity may be lower.

**Switch spoofing** exploits dynamic trunk negotiation. Configure host-facing ports explicitly as access ports and disable negotiation. **Double tagging** depends on ingress handling and untagged native-VLAN transmission: removing an outer native tag can expose a target-VLAN tag to the next switch. This permits one-way injection under suitable conditions without establishing a return path.

Use a separate unused native VLAN, restrict trunk VLAN lists, and enable native tagging where appropriate. On documented Cisco IOS platforms, `vlan dot1q tag native` is a global command, not an interface command. Tags provide no cryptographic authentication.

### Defend the mappings that direct traffic

IP-to-MAC mappings, hostname resolution, and DHCP settings direct traffic. Poisoning them can redirect traffic while preserving the application’s destination name.

**Validate ARP at the local boundary.** **Address Resolution Protocol (ARP)** resolves local IPv4 addresses to link-layer addresses. An attacker advertising the gateway’s IP with the attacker’s MAC can redirect frames if the endpoint accepts that mapping. Base ARP lacks cryptographic authentication, but acceptance of unsolicited updates depends on endpoint behavior and state. Authenticated encryption can still protect applications from impersonation and payload modification.

**Dynamic ARP Inspection (DAI)** commonly checks untrusted-port ARP against DHCP-snooping bindings. Coverage requires enabled VLANs, accurate bindings, and trustworthy paths. Trusted interfaces bypass inspection; static-address devices need suitable static bindings or ARP ACLs.

**Restrict DHCP configuration sources.** A **rogue DHCP server** supplies unauthorized settings, such as gateways or resolvers. Client offer selection varies; the problem is unauthorized participation, not a universal “first offer wins” rule.

**DHCP snooping** distinguishes trusted server-facing paths from untrusted client ports. It blocks server messages such as OFFER, ACK, and NAK from untrusted ports while applying other message-validation rules. Bindings can record IP address, MAC, VLAN, interface, and lease lifetime for DAI and related controls.

Client-port rate limits reduce some starvation traffic but cannot prevent every address-pool exhaustion technique. Option 82 handling must match the relay and trust topology.

**IEEE 802.1X** authenticates network admission: the endpoint is the **supplicant**, the switch or access point the **authenticator**, and a back-end server supports authentication. Its properties depend on the EAP method and configuration. Interface commands alone are insufficient: deployments also need global enablement, AAA method lists, RADIUS connectivity, and client authentication. Define preauthentication traffic and fallback policy.

**Distinguish DNS guessing from collisions.** **DNS cache poisoning** tricks a resolver into accepting forged answers. Matching includes query context, transaction identifiers, addresses, ports, and record-acceptance rules. Independent use of complete 16-bit transaction-ID and port fields would yield $N=2^{32}$ possibilities; translation, port restrictions, and resolver behavior can reduce effective variation.

For $n$ independent guesses against one fixed uniform target:

$$
P(\text{success})=1-(1-1/N)^n
$$

With only a 16-bit identifier, 300 guesses give about 0.46% success. Birthday-collision probabilities describe different conditions involving multiple matching opportunities. Query matching, unpredictable identifiers and ports, and DNSSEC validation address different weaknesses.

### Authenticate wireless networks beyond their names

A **rogue access point** is unauthorized infrastructure connected to the organization. An **evil twin** impersonates a network and need not share its wired connection or exact BSSID.

A familiar **service set identifier (SSID)** does not authenticate its operator. Signal strength is only one selection input: clients also consider compatibility, authentication, roaming state, and implementation-specific criteria. A stronger signal cannot force a correctly configured client to trust an unauthorized enterprise authentication server. [Apple’s Wi-Fi roaming description](https://support.apple.com/guide/deployment/wi-fi-roaming-support-dep98f116c0f/1/web/1.0)

Admission controls, server-certificate validation, and endpoint policies establish network identity. TLS and appropriately configured VPNs protect subsequent traffic. **Protected Management Frames (PMF)** protect specified management exchanges against forgery, but cannot prevent every evil-twin technique or radio disruption.

### Protect availability at the point of exhaustion

**Identify the consumed resource.** **Denial of service (DoS)** exhausts resources or triggers failure; **distributed denial of service (DDoS)** combines activity from many sources. A **botnet** coordinates compromised devices through **command-and-control (C2)** infrastructure, although other DDoS architectures exist.

Bandwidth, connection-table memory, application workers, and processor time can each become bottlenecks. Operational mistakes, such as an unthrottled backup, can produce similar symptoms.

**Reflection** directs responses to a forged source address. **Amplification** makes responses larger than requests:

$$
\text{BAF}=\frac{\text{Response size}}{\text{Request size}}
$$

Measure this bandwidth amplification factor with consistent protocol-overhead accounting. Aggregate impact depends on request bandwidth, effective amplification, reflector capacity, response policy, loss, and rate limits.

**Recognize downstream filtering limits.** Resource utilization compares arrival rate with service rate: $\rho=\lambda/\mu$, including legitimate and attack arrivals. Queueing models can illustrate overload, but their traffic and service assumptions may not fit a real network.

Filtering beyond a saturated access link cannot reclaim bandwidth already consumed there. Upstream protection, connection-state limits, and application controls address different bottlenecks; ample bandwidth does not guarantee connection-table capacity. Monitor concurrent activity because visible floods can coincide with theft or malware deployment.

### Adapt security to physical processes in OT

**Internet of Things (IoT)** devices include cameras, sensors, and access readers; **Industrial IoT (IIoT)** applies connected sensing to industry. **Operational technology (OT)** monitors or controls physical processes, making safety, integrity, timing, and reliability central.

**Supervisory control and data acquisition (SCADA)** coordinates **programmable logic controllers (PLCs)**, **remote terminal units (RTUs)**, and **human-machine interfaces (HMIs)**. Industrial zoning separates enterprise, supervisory, controller, and field systems; an industrial DMZ mediates selected business-to-operational exchanges.

**Treat safety and timing as design constraints.** No universal ordering places availability above integrity: command integrity may be essential to safety, and safety can require stopping a process. Evaluate controls against physical consequences and equipment requirements. [NIST’s OT security guidance](https://csrc.nist.gov/pubs/sp/800/82/r3/final)

Control loops must meet process deadlines with acceptable jitter, the variation in cycle time. Polling, propagation, controller processing, and actuation contribute differently in sequential, parallel, or event-driven designs. Scans, reboots, and inspection devices can interfere, so coordinate validation and maintenance. These constraints do not justify blanket prohibitions on patching, encryption, or active testing.

**Inspect traffic with an accurate protocol model.** Legacy protocols may lack authentication. Segmentation, restricted management, and monitoring compensate while equipment-specific improvements are planned.

For Modbus/TCP, detecting Write Single Register (`0x06`) and Write Multiple Registers (`0x10`) requires explicit function matching, correct message parsing, stream handling, and parser-compatible rules. An IDS `alert` detects rather than blocks; identifying unauthorized writes also requires source, destination, function, and operational context. [Snort `byte_test` semantics](https://docs.snort.org/rules/options/payload/byte_test)

### Protect people and physical access

**Social engineering** exploits decisions through impersonation, urgency, authority, and social expectations.

**Reduce phishing and impersonation opportunities.** **Phishing** uses deceptive messages or sites to steal credentials, deliver malware, or induce unauthorized action. **Spear phishing** targets a recipient or organization. Familiar logos and portal layouts establish no authenticity.

Check sender domains, actual link destinations, and request context. Typosquatting and look-alike characters disguise different domains, while legitimate accounts can be compromised.

| Mechanism | What it checks                                                           |
| :-------- | :----------------------------------------------------------------------- |
| SPF       | Whether the sending host is authorized for the relevant envelope domain  |
| DKIM      | Whether signed content verifies under the signing domain’s published key |
| DMARC     | Whether passing SPF or DKIM aligns with the visible From domain          |

DMARC requires either aligned SPF or aligned DKIM, not both. Receivers decide how to apply requested policy; rejection cannot eliminate look-alike-domain or compromised-account phishing. Provide practical, nonpunitive verification and reporting procedures.

**Reduce visual and physical leakage.** **Shoulder surfing** exposes screens or credentials. Screen placement, privacy filters, and awareness of windows and public spaces reduce exposure, but restricted viewing angles do not guarantee invisibility to observers or cameras.

**Tailgating** lets an unauthorized person follow an authorized entrant. Badges, visitor procedures, monitoring, and access-control vestibules provide complementary controls. Two-door interlocks normally restrict simultaneous opening, but designs must address obstruction, faults, occupancy checks, and emergency egress. Weight alone does not prove single occupancy.

**Dumpster diving** exploits discarded information. Match disposal to materials and retention requirements: magnetic-media sanitization methods do not automatically sanitize flash. Protect diagrams, paper records, and retired storage throughout disposal.

### Understand malware as a sequence of capabilities

Malware categories overlap: a trojan may deliver a keylogger, establish persistence, and download ransomware.

| Category       | Distinguishing behavior                                                   |
| :------------- | :------------------------------------------------------------------------ |
| Virus          | Replicates through an executed host file or carrier                       |
| Worm           | Propagates between systems with substantial autonomy                      |
| Trojan         | Appears useful or legitimate while performing unwanted functions          |
| Ransomware     | Denies access as part of extortion                                        |
| Rootkit        | Subverts trusted components to conceal activity or maintain access        |
| Keylogger      | Captures keystrokes through software or hardware                          |
| Spyware/adware | Collects information or presents advertising, potentially without consent |
| Logic bomb     | Activates malicious behavior on a condition or event                      |
| Bloatware      | Unwanted bundled software; not inherently malware                         |

Virus replication needs carrier execution, not necessarily fresh human action. Rootkits operate at different levels and do not universally require kernel privilege.

**Model propagation within its assumptions.** Infection models depend on susceptible hosts, connectivity, transmission, and removal. Logistic growth assumes conditions that permanent recovery, quarantine, or intervention may invalidate. Automated spread can outpace manual response; reduce reachable vulnerable hosts and interrupt propagation paths.

**Separate ransomware encryption from recovery.** One design encrypts files with a random symmetric key and wraps that key with an attacker’s public key. Strong implementation can make decryption infeasible without suitable keys. Backups, versions, implementation flaws, or recovered keys may still enable recovery. Restoring availability cannot undo prior data theft.

**Interpret local rootkit checks carefully.** A kernel symbol-map entry does not validate live function pointers. Module listings can differ legitimately and depend on a potentially compromised operating system. Clean comparisons or scanner results cannot prove integrity; investigation needs trusted baselines and appropriately independent examination.

Track incident transitions—phishing, downloading, C2, credential theft, lateral movement, and extortion—to guide response beyond labels.

### Turn security design into maintained controls

**Reduce unnecessary exposure.** **Hardening** removes unneeded services, interfaces, software, and privileges; replaces default credentials; restricts administration; and maintains configuration baselines.

TCP and UDP each have 65,536 port numbers, but exposure depends on application, binding, protocol, and reachability. A port identifies neither a trustworthy service nor its risk. **Common Vulnerability Scoring System (CVSS)** scores belong to vulnerabilities, not ports. Absence of known vulnerabilities does not establish safety.

Inventory listening sockets with:

```bash
ss -tulnp
```

Disable only services confirmed unnecessary. Distribution-specific unit names, included SSH settings, and `Match` blocks affect configuration. Before disabling password access, verify another access method; validate effective settings and establish recovery before restarting SSH.

Password-policy changes affect only authentication paths using the relevant modules. Appending PAM quality settings does not configure aging, and mandatory character-class rules conflict with NIST guidance. [NIST password requirements](https://pages.nist.gov/800-63-4/sp800-63b.html)

Disable unused switchports and place them in an unused VLAN. Fit active-port admission and learning policies to their endpoints; copyable MAC filtering remains supplemental.

**Manage keys as operational dependencies.** A **key management system (KMS)** coordinates creation, use, rotation, retirement, and auditing. A **hardware security module (HSM)** protects sensitive key operations. Certificate and SSH credential lifecycles are distinct capabilities that may integrate with a KMS.

Centralization aids ownership and expiry tracking but increases the importance of management access. Compromise impact depends on key hierarchy, permissions, export restrictions, and boundaries; it need not expose every organizational key. Recovery and resilience also matter: confidential data is unusable if authorized services cannot obtain keys.

**Use deception to create detection opportunities.** A **honeypot** is a monitored decoy; a **honeynet** combines decoys. Contacts can reveal reconnaissance, credential attempts, commands, and movement, but authorized scans and misconfiguration also reach decoys. Investigate signals rather than treating every contact as proof of intrusion.

Decoy value depends on adversary paths and reliable observation, not simply node count. Deployment requires isolation, egress controls, dependencies, and writable logs; installation alone establishes none of these boundaries. [Cowrie installation documentation](https://docs.cowrie.org/en/latest/INSTALL.html)

Feed observations into investigation and prevent decoy compromise from opening production paths. Like other controls, deception adds dependencies to manage. Distinguishing attacks from ordinary failures requires systematic troubleshooting.

## 3. Troubleshoot by testing one explanation at a time

Network design establishes how traffic should move; troubleshooting identifies where actual behavior departs from it. A slow transfer might involve a cable, queue, tunnel limit, or application dependency. Carrier does not establish VLAN correctness, and ping does not establish service health. Connect the reported symptom to a failed operation, then choose measurements that distinguish likely causes.

### Start with a testable problem

Turn “the network is down” into an account of affected users, devices, locations, applications, and traffic directions. Establish onset, frequency, and preceding changes. Widespread symptoms suggest a shared dependency without identifying it.

Use seven steps: identify and reproduce the problem; form a probable theory; test it; plan an intervention with expected effects and rollback; implement or escalate; verify recovery; document evidence and follow-up. A failed hypothesis returns the investigation to evidence gathering. Escalation depends on impact, ownership, and agreed response targets.

**Choose tests with the OSI model.** Work upward from absent carrier or downward from an application error when other connectivity appears healthy. Physical links, frame delivery, IP forwarding, transport connections, and application behavior require different evidence. Compare an affected and working host on one VLAN, or small and large packets on one path, while holding other conditions consistent.

A successful ping confirms one ICMP exchange at that time. Intermittent cable errors, congestion, large-packet failures, and other flows' routes remain possible. Failure may instead reflect filtering or an unresponsive destination. Real faults rarely divide cleanly along layer boundaries.

Measure detection, isolation, cause determination, remediation, and verification consistently. If summing phase averages into a recovery metric, use nonoverlapping phases from the same incidents. Documentation completed after restoration extends incident handling rather than downtime. An outage-cost estimate can multiply hours of downtime by hourly loss, but cannot capture every delayed transaction, recovery expense, or contractual effect.

### Read fiber links as optical systems

An optical link requires compatible transceivers, fiber, connectors, and received power in both directions. Typical core diameters—about 9 micrometers for single-mode and 50 or 62.5 for multimode—do not establish reach alone. Optical standard, fiber grade, wavelength, and transmitter and receiver limits also matter. Check specifications and markings rather than relying on jacket colors. A module fitting an SFP cage does not establish host support; bidirectional optics need complementary wavelengths.

**Compare the correct transmitter and receiver.** For one direction:

$$
P_{\text{RX}}(\text{dBm}) = P_{\text{TX,remote}}(\text{dBm}) - A_{\text{path}}(\text{dB})
$$

The difference between absolute powers in dBm gives loss in dB. A planning budget adds fiber, connector, and splice losses, plus reserved safety headroom. Exclude that margin when interpreting measured physical attenuation.

Digital optical monitoring exposes temperature, voltage, laser bias, and power:

```text
show interfaces TenGigabitEthernet1/0/1 transceiver detail
```

A receive reading of −18.9 dBm is 4.9 dB below a −14.0 dBm low alarm threshold. Obtain the **remote** transmitter's reading to estimate loss along the incoming path; local transmit power describes the opposite direction. An alarm threshold need not equal receiver sensitivity.

For example, a remote transmitter at −2.4 dBm and its corresponding receiver at −18.9 dBm imply 16.5 dB attenuation. Check that both readings describe the same direction and operating conditions before comparing them with the planned budget.

Inspect dirty end faces, poor connections, excessive bends, incompatible components, and the remote transmitter. Compare both ends and change one component at a time. For high received power, check overload specifications; an alarm alone does not prove damage.

A geometric core-mismatch approximation is $\eta=(d_{\text{rx}}/d_{\text{tx}})^2$ for a smaller receiving core. Loss is $-10\log_{10}\eta$: a 62.5-to-9-micrometer transition gives about 16.83 dB. Actual coupling also depends on field distribution, alignment, and numerical aperture, so use compatible components and measured loss.

An optical time-domain reflectometer (OTDR) locates connectors, breaks, and attenuation changes from returned light. Its measurements involve round-trip propagation, but instruments may already normalize reported attenuation. Avoid applying another factor of two. Pulse width, dynamic range, and dead zones limit event resolution; launch and receive fibers help expose end connectors. A calibrated light source and power meter provide complementary end-to-end insertion-loss measurements.

### Test copper beyond simple continuity

Continuous conductors may still fail Ethernet performance requirements. Differential signaling subtracts the two conductors' voltages, ideally rejecting interference coupled equally into both. Excessive untwisting, poor terminations, unequal coupling, and imbalance weaken that rejection.

**Preserve physical pairs.** T568A and T568B differ in their green and orange assignments:

| Pins | T568A pair           | T568B pair           |
| ---- | -------------------- | -------------------- |
| 1, 2 | White/green, green   | White/orange, orange |
| 3, 6 | White/orange, orange | White/green, green   |
| 4, 5 | Blue, white/blue     | Blue, white/blue     |
| 7, 8 | White/brown, brown   | White/brown, brown   |

A straight-through cable uses one scheme at both ends. An A-to-B crossover exchanges traditional 10/100 transmit and receive pairs and is not inherently defective. Auto-MDI/MDIX accommodates certain pair-role differences, but cannot repair split pairs or poor electrical performance.

A reversed pair exchanges conductors within one pair; swapping pins 3 and 6 is a reversal. A split pair uses conductors from different physical pairs and may pass a simple one-to-one continuity test while losing the intended interference rejection. Confirm the actual arrangement before retermination.

**Read crosstalk with the correct sign.** Near-end crosstalk loss measures coupling into another pair at the transmitting end; larger positive values mean less relative coupling. Record frequency and the applicable test limit. The near-end attenuation-to-crosstalk ratio is:

$$
\text{ACR-N} = \text{NEXT loss} - \text{insertion loss}
$$

Thus, 40 dB NEXT loss and 20 dB insertion loss yield 20 dB ACR-N. Higher values indicate greater separation between the attenuated signal and near-end crosstalk.

Passing length does not establish acceptable crosstalk, return loss, or delay skew. Certification must match the intended application's requirements. Category also does not prescribe identical construction; Category 6 cables need not all contain a plastic separator.

**Locate faults with TDR.** An electrical time-domain reflectometer estimates distance as $d=(\text{NVP}\times c\times\Delta t)/2$, where NVP is propagation speed relative to light speed. Incorrect NVP gives an incorrect estimate; division by two accounts for the round trip. Ideal opens and shorts produce opposite reflection polarities, but actual traces may contain multiple events.

```text
test cable-diagnostics tdr interface GigabitEthernet1/0/12
show cable-diagnostics tdr interface GigabitEthernet1/0/12
```

A reported open at $38\pm1$ meters could indicate cable damage or a disconnected termination. Follow the route and inspect connections. Check platform behavior because testing can interrupt service.

A toner and probe identify cable routes without certifying data performance. Use equipment suited to active Ethernet and PoE where present.

### Read switch state and error counters together

Interface status distinguishes physical carrier from reported line protocol. `up/up` establishes local operational state while leaving VLAN, IP, policy, and application access unverified. `down/down` can reflect disconnected media, a disabled remote device, or bad optics. `up/down` requires platform-specific interpretation. Establish why an interface is administratively disabled before enabling it.

Measure counter changes with timestamps under representative traffic. Cumulative errors cannot distinguish an old fault from a current one; preserve evidence before clearing counters.

Ethernet's CRC-32 frame check sequence detects corruption across header fields and payload. It provides error detection rather than cryptographic integrity, and cannot detect every corruption pattern. Rising CRC or FCS errors justify checking cabling, optics, connectors, interfaces, and negotiation. Correlate both endpoints' counters with traffic direction and link changes.

Use consistent frame boundaries: conventional untagged Ethernet frames span 64–1,518 bytes including FCS, while 1,500 bytes is the Ethernet payload limit, including the IP header when carrying IP. VLAN tagging adds four bytes; supported jumbo frames raise the upper limit. Interpret runt and giant counters against actual encapsulation and platform definitions.

**Check duplex at both ends.** Half duplex shares transmission opportunities and uses collision detection; full duplex permits simultaneous sending and receiving. A mismatch can preserve carrier while severely reducing performance. In classic 10/100 half duplex, late collisions occur beyond the 512-bit-time slot: 51.2 microseconds at 10 Mbps or 5.12 at 100 Mbps.

A forced 100 Mbps full-duplex endpoint can mismatch an autonegotiating peer that detects speed but defaults to half duplex. Late collisions support this hypothesis without proving it. Check both endpoints, establish compatible settings, verify negotiation, and observe new errors under load.

Output drops often indicate queue or resource pressure. Cable replacement cannot resolve sustained egress congestion, while larger queues cannot repair frame corruption.

### Check VLAN membership before IP routing

A workstation in the wrong access VLAN can have carrier and a learned MAC address while failing to reach its intended gateway. Equal VLAN membership permits ordinary bridging subject to spanning tree, isolation, access controls, port security, and forwarding state. Communication between VLANs requires suitable routing and policy.

Trace the workstation's port, MAC address, and VLAN:

```text
show interfaces GigabitEthernet1/0/5
show mac address-table interface GigabitEthernet1/0/5
show vlan brief
```

A MAC learned in VLAN 1 is evidence of misconfiguration only if the design calls for another VLAN. Confirm that assignment before changing the access port.

For a port confirmed to belong to VLAN 20, an illustrative Cisco configuration is:

```text
interface GigabitEthernet1/0/5
 switchport mode access
 switchport access vlan 20
```

Confirm the intended device and uplink before applying this configuration.

After a move, verify VLAN existence, uplink trunk membership, gateway state, and host addressing. Clearing learned MAC entries prompts relearning but does not renew DHCP; the workstation may retain its previous network's address.

For `err-disabled` ports, investigate protective triggers such as port security, BPDU guard, or repeated link failures before recovery. Automatically recovering every cause can repeatedly restore the fault.

### Separate PoE capability from available power

Power sourcing equipment (PSE) powers the powered device (PD). Spare switch capacity cannot compensate for a port lacking the required power class. Maximum capabilities distinguish source power from power reaching the device:

| PoE type                      | Maximum source power | Corresponding device power |
| ----------------------------- | -------------------- | -------------------------- |
| Type 1, originally 802.3af    | 15.4 W               | About 13 W                 |
| Type 2, originally 802.3at    | 30 W                 | 25.5 W                     |
| Type 3, introduced by 802.3bt | 60 W                 | 51 W                       |
| Type 4, introduced by 802.3bt | 90 W                 | 71.3 W                     |

Devices need not draw their maximum continuously; Type 4 does not universally deliver 100 W. [Ethernet Alliance's PoE technical brief]

Resistive losses follow $P_{\text{loss}}=I^2R$. Current and effective resistance must describe the same circuit: PoE uses parallel conductors and may energize multiple pair sets. Contact resistance, temperature, and imbalance also matter.

Budgeting depends on reservations, negotiation, per-port limits, power banks, priorities, and supply mode. A reported usable PoE budget usually already excludes system consumption. Redundant supplies need not provide their full combined wattage.

A 740 W budget accommodates twenty-four 30 W reservations, leaving 20 W. Conversely, a reported 54.8 W remaining cannot alone explain denial of a 30 W request. Inspect `show power inline`, port details, negotiated requirements, power domains, and logs for additional or transient constraints before reallocating power or adding a supply.

### Establish host addressing and neighbor state

Record the active interface, IP address, prefix, routes, DNS servers, and DHCP state. Compare them with the intended subnet and VLAN before tracing routers.

For a directly reachable IPv4 destination, ARP resolves the destination MAC. For an off-subnet destination reached through a gateway, ARP resolves the gateway MAC while the packet retains its final destination IP. The actual routing table controls this decision, including more-specific, VPN, multiple-interface, and policy routes. A wrong mask can cause ARP where routing is required; a missing default can prevent off-subnet delivery.

An automatically chosen `169.254.0.0/16` address often indicates unsuccessful DHCP configuration. Investigate the client, VLAN, relay, server, scope availability, and filtering. The address alone establishes neither physical failure nor IPv6 state; suitable IPv4 peers may still communicate locally.

Duplicate IPv4 addresses can destabilize neighbor mappings. They do not inherently cause MAC-table flapping, where a switch learns one MAC on changing ports, or physical link flapping.

In the simplest single-subnet IPv4 case, applying the host's mask to its address and the destination compares their network portions. This explains local-versus-gateway delivery, but always check the installed routes before treating that simplified comparison as the actual forwarding decision.

Inspect neighbor entries for address, MAC, interface, and reachability state. Cache behavior involves platform-specific timers and probes; refreshing a suspected stale entry gives more specific evidence than clearing everything. Compare gateway mappings with trusted configuration, including redundancy protocols' virtual MAC addresses.

### Follow routing decisions in both directions

IP forwarding chooses the longest matching prefix among installed routes: a matching `/32` precedes `/24`, `/16`, and `/0`. Administrative distance and protocol metrics help select installed candidates for a prefix; they do not make a default override a more-specific installed match.

```text
ip route 0.0.0.0 0.0.0.0 203.0.113.1
ip route 10.10.20.0 255.255.255.0 10.1.1.2
ip route 10.10.20.55 255.255.255.255 10.1.1.99
ip route 10.10.0.0 255.255.0.0 Null0 250
```

When installed, the `/32` serves `10.10.20.55`, the `/24` serves other addresses in that subnet, and the Null0 `/16` discards remaining `10.10.0.0/16` traffic. Distance 250 does not make it lose to the default. Aggregate discard routes can prevent loops while intentionally dropping traffic after a more-specific route disappears. Verify active forwarding entries: interface state, next-hop resolution, and tracking can determine whether configured routes are usable.

**Recognize loops without assuming their cause.** IPv4 TTL decreases at each router. Expired packets are discarded, normally with ICMP Time Exceeded when permitted; filtering and rate limiting can suppress replies. TTL limits circulation, and a unicast loop does not inherently multiply packets.

A traceroute alternating between two routers suggests a loop without identifying static routing as its cause. Inspect matching routes and forwarding policies on both devices against the topology. Each probe has its own TTL; final asterisks mean no qualifying reply arrived before timeout.

**Check return paths.** Asymmetric routing can work for IP while disrupting stateful inspection. A firewall lacking return-traffic session or NAT state may drop packets; policy and validation add further conditions. Inspect both directions and their processing devices. High availability alone does not establish that a firewall cluster synchronizes every relevant session and translation.

Different directional metrics can produce different paths, but policy routing, particularly BGP policy, need not reduce to an additive shortest-path calculation.

### Use ping and traceroute as focused probes

IPv4 ping uses ICMP Echo Request and Echo Reply. Interpret results for the tested source, destination, size, and time. RTT measures request-to-reply elapsed time; unanswered-probe percentage includes dropped, filtered, suppressed, or late traffic. Neither metric identifies where loss occurred or establishes an application's loss rate.

Average RTT describes received replies and requires at least one response. Report probe count and unanswered percentage alongside it so that a low average does not obscure missing responses.

Progress from loopback to gateway to remote address, then test the application. Loopback checks the local stack; later probes extend the tested path.

```bash
ping -c 5 -s 1000 192.168.1.1
traceroute -T -p 443 1.1.1.1
```

On Linux, `-s 1000` specifies 1,000 bytes of ICMP payload. The eight-byte ICMP header produces a displayed 1,008 bytes; a basic IPv4 header makes the packet 1,028 bytes. These boundaries matter for MTU testing.

Traceroute increases TTL and records responding interfaces and probe round-trip times. Traditional Windows ICMP probes reach the destination through Echo Reply; traditional UDP probes commonly receive Port Unreachable. TCP probes may recognize SYN/ACK or RST. Tools also stop at configured limits.

TCP port 443 probes can receive different filtering treatment without guaranteeing passage. Intermediate discovery still typically requires ICMP Time Exceeded. A silent hop could reflect filtering, rate limiting, or loss; later replies show that some probes progressed farther. Load balancing, return routes, and control-plane response time complicate interpretation, so differences between adjacent-hop RTTs do not reliably measure individual-link latency.

### Investigate packet size and aggregation limits

Small requests can succeed while large transfers stall. Encapsulation reduces available inner-packet space:

$$
\text{Inner MTU} = \text{Underlying IP MTU} - \text{Encapsulation overhead}
$$

Include all outer headers and trailers. IPsec overhead depends on algorithms, padding, ESP trailer fields, outer IP version, and possible NAT-traversal UDP. Derive the limit from the actual format.

Oversized IPv4 packets may be fragmented when Don't Fragment is clear. When set, routers ordinarily discard them and send ICMP Fragmentation Needed. Failed delivery or use of that feedback can create a path MTU discovery black hole. IPv6 routers do not fragment forwarded packets; they send ICMPv6 Packet Too Big.

When a connection establishes but stalls as packets grow, compare sizes, retransmissions, and ICMP feedback. For a 1,420-byte inner MTU, subtracting basic 20-byte IPv4 and TCP headers gives a 1,380-byte TCP MSS. A supported `ip tcp adjust-mss 1380` setting can adjust setup packets, but correct interface placement depends on the platform and encapsulation path. MSS adjustment applies to new TCP connections traversing that interface; UDP and existing connections need separate consideration. Verify tunnel sizing and repeat the original transfer.

**Understand aggregation.** LACP coordinates membership; the forwarding implementation distributes traffic, commonly hashing selected addresses and ports to a member. A stable assignment preserves flow order and can constrain one flow to one member's capacity. Aggregate bandwidth therefore does not establish single-flow throughput; other path bottlenecks also apply.

Inspect member state and counters, then test aggregate capacity with independent flows. Compare their distribution with the configured hash rather than assuming one transfer spans every active member.

### Distinguish capacity, delay, and delay variation

Bandwidth describes capacity; throughput describes achieved useful traffic. Latency measures delivery time, while jitter measures timing variation. High capacity can coexist with long propagation time or overloaded queues.

Each hop contributes processing, transmission, queueing, and propagation delay. Transmission time is $L/R$ for packet length $L$ in bits and rate $R$ in bits per second. Propagation is $d/v$ for distance $d$ and signal speed $v$. Higher rates reduce serialization time, while distance still governs propagation. Demand and scheduling change queueing delay.

RTT includes both directions and endpoint response behavior. Halving it estimates one-way delay only under justified symmetry and processing assumptions. Voice targets also depend on codecs, jitter buffers, loss, and application behavior.

**Use the application's jitter metric.** For RTP, let $D$ be the change in transit time between consecutive packets, calculated from sender and arrival timestamps in compatible units. The estimate updates as:

$$
J_i = J_{i-1} + \frac{|D|-J_{i-1}}{16}
$$

This smoothed measure differs from statistical delay variance and ping RTT standard deviation.

**Apply QoS at the bottleneck.** Classification, marking, queueing, and policing control treatment. Low-latency queueing can prioritize sensitive traffic within constrained capacity; a `priority 2048` allocation represents 2.048 Mbps and does not guarantee zero jitter. Scheduling, downstream congestion, and exceeded limits still matter.

If the provider's limit is below local interface speed, shaping may bring queueing under local control. Check platform support and counters under load, then verify voice and other traffic. QoS cannot remove propagation delay or create bandwidth.

### Treat Wi-Fi as a shared radio medium

Wi-Fi adds radio conditions, contention, client behavior, and mobility. Strong signal and high PHY rate alone do not establish usable throughput.

$$
\text{SNR}(\text{dB}) = \text{RSSI}(\text{dBm}) - \text{Noise floor}(\text{dBm})
$$

Both readings are required. Shannon's idealized capacity relationship, $C=B\log_2(1+10^{\text{SNR}/10})$, relates bandwidth in hertz to capacity in bits per second. Actual throughput also depends on modulation, coding, spatial streams, contention, overhead, and retransmissions; SNR guarantees no particular rate.

Devices sharing a channel compete for airtime, with hidden nodes and collisions potentially adding disruption. Partially overlapping channels can create interference that is harder to coordinate. Channels 1, 6, and 11 form a conventional 2.4 GHz plan for many 20 MHz deployments; country settings, modulation, and equipment determine permitted channels and widths. Wider channels increase potential peak rates while reducing independent channels for reuse. Dynamic frequency selection can trigger changes after radar detection under applicable rules.

```bash
iw dev wlan0 link
```

A −62 dBm signal and 866.7 Mbps transmit PHY rate do not establish SNR without a noise reading, or prove payload throughput. Scanning identifies nearby Wi-Fi networks without identifying every interference source. A spectrum analyzer adds non-Wi-Fi energy patterns; correlate frequency, duration, and location with failures before naming a source or changing bands.

Clients largely decide when to roam, with infrastructure assistance depending on capabilities. Record access point, channel, signal, authentication, and interruption timing. A nearby access point does not ensure prompt roaming. Association, addressing, and authorization are separate states: captive-portal access can expire while association and a DHCP lease persist. Management-frame protection covers certain exchanges without eliminating every disconnection or interference cause.

### Discover services and neighbors deliberately

Active probes identify responding IP services; link-layer advertisements describe adjacent attachments. In TCP SYN scanning, SYN/ACK indicates acceptance of the initial attempt, while reset indicates a closed port. “Filtered” means the scanner could not establish either state under the probing conditions; timeout does not identify a particular firewall. SYN scans avoid completing the handshake but remain detectable and loggable.

Service detection sends application probes; OS detection compares response fingerprints. Neither guarantees exact patch levels. Banners alone cannot establish vulnerability or exclude backported fixes.

```bash
nmap -sS -sV -O -p 22,80,443,53 192.168.1.1
lldpctl eth0
```

This scan tests TCP, including TCP 53; UDP DNS requires separate testing. `lldpctl` reads advertisements learned by a local LLDP service, requiring the relevant software and received advertisements. Its neighbor may differ from the scanned IP gateway.

LLDP and Cisco's CDP advertise local-neighbor information using link-layer multicast. LLDP carries chassis ID, port ID, and lifetime, with optional names, capabilities, and management addresses. LLDP-MED can support voice and power functions.

Compare endpoint-to-port and IP-path observations with configuration and inventory. Enable discovery where needed and limit metadata exposure appropriately; indiscriminate disabling can remove useful voice and power negotiation.

### Diagnose DNS by resolver, record, and response

Identify the exact name, record type, and responding server. Failures may involve client configuration, resolver reachability, caching, validation, or authoritative data. Successful access by address makes DNS a hypothesis, but HTTP hostnames, TLS names, certificates, and proxies can also change application behavior.

Authoritative servers answer from their zones; recursive resolvers obtain and may cache answers. Recursive replies are normally non-authoritative even after fresh upstream resolution. Absence of the authoritative-answer flag does not prove a cache hit.

TTL usually limits reuse, but resolvers may evict early, prefetch, forward, or serve stale data under defined conditions. Expiration need not restart resolution at the root. Authoritative changes also leave previously cached copies valid until their reuse ends. Record answers, TTLs, flags, and query times; split-horizon DNS may intentionally return different internal and external answers.

```bash
nslookup professormesser.com
dig @1.1.1.1 professormesser.com A +noall +answer +stats +comments
dig @8.8.8.8 widget.com MX +short
```

Querying Cloudflare's recursive service bypasses the local resolver while retaining Cloudflare's caching behavior. For authoritative data, identify and explicitly query the zone's authoritative nameserver, then inspect the response. `+comments` includes header information needed to inspect flags. [Cloudflare&#39;s resolver documentation](https://developers.cloudflare.com/1.1.1.1/privacy/public-dns-resolver/).

EDNS permits larger UDP responses; truncation can prompt TCP retries. Dropped large UDP packets or blocked TCP 53 can cause selective failures. A timeout supplies different evidence from a received truncation flag.

MX records advertise mail destinations and preferences. Lower values, including zero, are tried first; equal preferences, address resolution, SMTP failures, and retries also affect delivery. Preference 10 precedes 20, but returned MX records prove neither mail acceptance nor recipient deliverability. Ping success does not establish a usable SMTP destination.

### Inspect the host's transport state

Match sockets to local address, remote endpoint, process, and observation time. On a passive TCP open, a listening server receives SYN, sends SYN/ACK, and enters SYN-RECEIVED. It becomes ESTABLISHED upon receiving the client's valid final ACK. Distinguishing directions helps locate missing handshake steps. [TCP specification](https://www.rfc-editor.org/rfc/rfc9293.html#section-3.3.2)

| State        | Useful follow-up                                           |
| ------------ | ---------------------------------------------------------- |
| LISTEN       | Check bound address, port, process, and permitted access   |
| SYN-SENT     | Inspect outgoing SYN, return path, route, and service      |
| SYN-RECEIVED | Check SYN/ACK and final ACK paths                          |
| ESTABLISHED  | Inspect data, retransmissions, and application responses   |
| CLOSE-WAIT   | Check whether local application closure remains incomplete |
| TIME-WAIT    | Compare timing and volume with ordinary connection churn   |

TIME-WAIT retains protocol state after closure for twice the maximum segment lifetime; actual timers vary by operating system. Its presence alone does not indicate a leak. Persistent CLOSE-WAIT may suggest incomplete cleanup, but one snapshot is insufficient.

In a typical active close, sending FIN enters FIN-WAIT-1. Receiving its acknowledgment enters FIN-WAIT-2; receiving the peer's FIN and acknowledging it leads to TIME-WAIT. Simultaneous closure can follow another sequence. These states explain why protocol activity can continue after the application finishes sending, without establishing abnormal behavior by themselves.

On Linux, `netstat -tulpn` shows listeners. Use `netstat -tunap` or the corresponding `ss` view to include other socket states; interpret flags within the operating system's context. [Linux netstat manual](https://www.man7.org/linux/man-pages/man8/netstat.8.html)

These Linux commands separate listeners, active connections, and gateway neighbor mappings. Process details may require elevated privileges; replace `eth0` with the actual interface.

```bash
ss -tulnp                         # TCP/UDP listeners and process details
ss -tnp state established         # Established TCP connections
ss -tnp state syn-sent            # Pending TCP connection attempts
ip neigh show dev eth0            # Neighbor addresses and reachability states
```

A process name or SYN-SENT state does not establish malicious intent. Confirm identity and behavior separately. When SYNs leave without replies, follow host evidence outward. When the handshake completes and requests reach the server, inspect responses and dependencies. When no request occurs, application logs and local configuration may explain more than another router trace.

### Verify the user's workflow and preserve evidence

Verify recovery where the failure was reported. After cable replacement, observe carrier and error counters under traffic. After a VLAN change, confirm addressing and gateway access. After routing or MTU repair, repeat the failing transfer. After DNS repair, retry the named application from an affected client.

Match observation time and scope to the failure pattern. Five successful pings cannot establish that a daily intermittent failure has gone; one recovered workstation cannot establish department-wide recovery.

Document symptoms, scope, hypotheses, tests, intervention, rollback, and outcome. Support causal claims: interface status alone cannot identify an unauthorized MAC, and a failed port explains many affected hosts only if the topology establishes their dependency. Include port-security details or logs and application-level confirmation where relevant.

Preserve final configuration, evidence, remaining uncertainty, and preventive follow-up. Update diagrams and inventory when actual wiring or configuration differs from the design, retaining useful rollback and escalation history for the next investigation.
